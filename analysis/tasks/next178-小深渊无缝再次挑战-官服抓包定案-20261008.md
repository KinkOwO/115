## 1. 怎么把两个方向对齐（这步是全部结论的前提）

解密工具的输出（`session_s2_c2s.txt` / `_s2c.txt`）只有**流内偏移**（`frame N @0x...`），没有时间；
`pcapng` 里有时间。所以自己写了两段脚本（`runtime/seamless/`）：

1. `pcapng_reasm.py`：解 pcapng → 按 **TCP 序号**重组两个方向（**不能按抓包顺序直接拼**：
   重传会把字节数撑大，v1 得到 c2s 52290/s2c 143183，而工具报 50838/143087）。
2. `merge_frames.py`：用「密文偏移 → 最近跨度」把时间补回每一帧。

**自检**：重组出的 s2c = **143087 字节，与工具报的完全一致** ⇒ 偏移 1:1 对齐；
c2s = 50844（+6 字节，误差不超过一个包，不影响时序判断）。

踩过的两个坑记在这里，省得下次重来：
- 按抓包顺序拼载荷 ⇒ 被重传污染（+1400 字节）。
- 乱序分支把**绝对序号**当偏移用 ⇒ 出现 `off=0xFFFFFFFF` 的垃圾跨度，时间全崩。

> ⚠️ 工具 txt 里的 `plain=` **被截断成 36 字节**（长帧只剩 `..`），`session_s2_*.bin` 是**加密流**、
> 不是明文档。要全量明文用本仓工具：
> `wiredecodedump <key.bin> <stream.bin> s2c out.txt`（`cmd/wiredecodedump`，注释里就写了
> 「prebuilt wiredecode.exe truncated plain= at 37 bytes」）。

## 2. 官方的结构：3 次进图，帧集合完全相同

`NOTI27 / 28 / 29 / 30` 各出现 **3 次**，构成 3 次完整进图：

| # | NOTI27 | 触发它的客户端命令 | 性质 |
| --- | --- | --- | --- |
| 1 | 26.5s | 无（城里选副本） | 冷进场 |
| 2 | 51.9s | **CMD72 `01 05 …` ×2** | 无缝再次挑战 |
| 3 | 69.7s | **CMD72 `01 05 …` ×2** | 无缝再次挑战 |

→ **触发点是 CMD72 的第 2 个字节 = 0x05**（`01 05 01 00 …`，客户端连发两次，后面跟一个
CMD2062(61B)），与本仓既有判断一致 ✓。

另有一对与再挑战**不同时刻**的东西：`CMD46`(141B，每次通关一次) → 服务端回
`NOTI2836`(征兆 UI) + `NOTI261`(EPLP_RECHALLENGE 继续挑战入口)，那是「通关结算 + 亮出继续挑战按钮」，
玩家随后点按钮才发 CMD72。

### 再挑战的服务端帧序（#3，与 #2 逐帧一致）


**#2 与 #3 的同 id 帧载荷逐帧相同**（`sha1` 比对），只有每局随机量不同：
`NOTI29` 的迷宫位置、`NOTI2838` 的珠子档位（#1=43 传说 / #2=42 独有 / #3=40 普通）、
`NOTI2837` 的序号、`NOTI2` 里的玩家名牌记录。

⇒ **官方没有为「无缝」精简或新增任何进图帧**。「无缝」不是靠省帧实现的。

## 3. ★ 区分「冷进」与「继续」的**唯一稳定信号**

把冷进的 NOTI27/28 与两次再挑战逐字节比：

| 帧 | 偏移 | 冷进 | 继续 | 说明 |
| --- | --- | --- | --- | --- |
| **NOTI28**（body 48B） | **byte 30** | `00` | **`05`** | **就是 CMD72 的选项号 5** ⇒「这是继续」 |
| NOTI27（body 48B） | byte 1..2 | `00 00` | `01 c3` | 头部随冷进/继续变化（`00000001` vs `0001c301`） |

其余差异（NOTI27 byte 40..45、NOTI28 byte 41..45）是每局的随机尾（nonce/时间戳）。

**这是本轮的核心结论**：官服把「继续」写进 **NOTI28 的 body[30] = 0x05**，而不是靠不发某些帧。

## 4. 另外两条硬事实

1. **NOTI1361（增益强化注册）在整条抓包里出现 0 次** —— 官服冷进场也不发它。
2. **NOTI2 是「角色记录通道」不是一个包**：1008B 那条是 zlib（`789c…`）压缩的角色对象，
   **两次再挑战逐字节相同**；其余 768/784/880/928B 的是**玩家名牌记录**
   （`[u32 长度][ascii 名字]`：`qunoif` / `XSpeedHuntersX` / `CuteYanDFO` / `peldita`）。

## 8. B 的结论：位移对上了（2026-10-08）

`internal/game/protocol/testdata/native_dungeon_info_cursor.json` 是**本仓客户端**读 NOTI28 的
原生读点表（26 个读点、`consumed=41`）。把它与官服那 48 字节并排：

| 偏移 | 本仓客户端 | 官服 |
| --- | --- | --- |
| 0..3 | 副本号 u32 | 副本号 u32（官服小深渊 = 100000918，与本仓 100005014 是不同版本的不同号） |
| 4 | 难度 | 难度 |
| 5..6 | u16 | `00 00` |
| 7 | 迷宫号 | `00` |
| 8,9 | Boss XY | `00 00` |
| 10,11 | 随机深渊位置（255/255 = 无） | `00 00` |
| 12,13 | 0,0 | `00 00` |
| 14..17 | u16 ×2 | `00 00 00 00` |
| 18 | 1 字节 | `00` |
| 19..22 | `ffffffff` 哨兵 | `ff ff ff ff` ✓ **同一个哨兵** |
| **23..30** | **八个各自独立的单字节**（读点 `0x1452ad3dd/3ec/3fb/96d/998/9c3/a0f/a9e`） | 23..25 = `ff ff ff`、26 = `00`、27 = `01`、28 = `00`、29 = `00`、**30 = 入口类型** |
| 31..36 | u16 ×3 | … |

顺带发现两处**值**不同（本轮不动，记为候选）：官服 23..25 = `ff ff ff`（像是三个「无」哨兵）
而本仓写 `00`；官服 37..40 = `ffffffff` 而本仓写 `00000000`。

### A2（**本轮故意没做**，等 A1 的实机结论）

把无缝续刷时「跳过 NOTI2」的抑制去掉（官方是照发 992B zlib 角色对象的）。
