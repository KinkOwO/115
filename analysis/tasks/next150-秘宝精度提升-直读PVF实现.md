## 2. 源（`etc/115lvability/soleequipmentsystem.cos`）

```
[infos]
 [info]
  [item index] 100354181        ← Venus
  [max quality] 100
  [quality need materials]
   [group] 0
    10404807 8                  ← 模板 数量（模板 0 = 金币）
    10404719 20
    10401346 800
   [/group]
   [group] 1
    10404807 8
    10404719 20
    0 4000000                   ← 用金币替代第三项
   [/group]
  [/quality need materials]
  [quality group]
   0 25 / 25 50 / 50 75 / 75 100   ← 分档边界（0/25/50/75/100）
  [/quality group]
  [quality ability] …           ← 精度 → 属性（客户端算面板，服务端不消费）
  [create need materials] …     ← 秘宝「制作」，与精度提升是另一套（未实现）
 [/info]
```

三件的成本（直读结果，与交接书一致）：

| 模板 | 名称 | 组 0（精度 < 50） | 组 1（精度 ≥ 50） |
| --- | --- | --- | --- |
| `100354181` | Venus | `10404807×8 + 10404719×20 + 10401346×800` | 同上但第三项换成 **金币 4,000,000** |
| `100391142` | Nabel | `10407241×8 + 10404719×20 + 10401346×800` | 同上但第三项换成 **金币 4,000,000** |
| `100346156` | Diregie | `10413524×30 + 10361515×40 + 10401346×800` | 同上但第三项换成 **金币 4,000,000** |

**两组成本是"玩家选的付法"，selector 与面板显示一一对应**（2026-10-02 业主受控实验判定）：

客户端这块面板第三项材料有**切换按钮**，请求明文 `+16..19` 的 **selector 就是面板当前显示的选项**：

```
selector = 0  →  组 0：面板显示实物（10401346 巡礼之印 ×800）
selector = 1  →  组 1：面板显示金币（4,000,000）
```

⇒ **玩家在面板上看到什么，服务端就扣什么。**

判定方法只能这么做（**受控对照**）：重启客户端 → 打开窗口**不切换**点一次 → 记下面板显示与请求字段；
再切换一次点一次 → 再记一对。**不能用扣料结果反推映射** —— 那会被旧映射污染：
最初正是按"日志里 selector=1 的几次扣的是实物"反推成 `1 → 组 0`，于是面板显示实物时服务端却扣金币，
业主看到的现象是「材料没扣（金币反而在掉）」。已按对照结果修正（见 `protocol.SoleMaterialGroupForSelector`）。

`10361515`（史诗灵魂）等同时是**账号共享材料仓库**的固定格 ⇒ 整笔事务走
`CommitAccountMaterialEvent`（与装备调适同一套幂等/事务设施，账号仓库优先、背包兜底）。

## 3. 协议（实机抓包 + 客户端契约）

**C2S（负载固定 24 字节，含 13 字节信封）**：

```
[0..12]  信封（50 02 + 6×00 + 会话令牌 + 01）—— 令牌每局都变，整段跳过
[13]     container u8（03 = 已穿戴）
[14..15] slot      u16 LE（交接书实机判定：22 = Diregie、23 = Venus、25 = Nabel）
[16..19] selector  u32 LE（实机恒 0）
[20..23] 补零
```

**S2C（kind 1，`CLIENT-MECHANICS §4`：命令回包体首是 `u8` 状态字节）**：

```
body = 01 | container(u8) | slot(u16 LE)      ← 回显客户端自己报的定位字段
```

**为什么必须回包**：客户端的「期望回包树」以 opcode 为键，handler 收包先清它，
**清不掉就整个 handler 跳过** ⇒ 不回 2288 则精度窗口卡在等待态（交接书症状 1）。

## 5. 与交接书的差异（有意为之）

1. **不新增 `configs/sole.json`** —— 规则改由 Go 直读内层 PVF（本仓库硬规则），
   数据与交接书的 JSON 逐字段一致；解析失败直接报错，不会静默用旧表。
2. **不加 `BagEquipment.SoleQuality` 镜像字段** —— 精度唯一真源是 `Record[172]`（名望侧
   早已按这一格结算），加镜像会引入"两处不一致"的风险，且本仓库刚因同类不一致踩过坑
   （见 `next149`：单件装备记录不一致会让整个角色进不去）。
3. **失败分支也发 2288 回包**（状态 1、回显 container/slot）—— 交接书建议"失败只记日志、
   不发包"，但那样客户端窗口会卡在等待态；而 2288 的失败语义（状态 0 + u16 错误码）
   **没有反编译依据**，发一个无依据的失败码风险更大。选择发回显包：客户端会刷新精度条，
   玩家看到"数值没变"，真实原因记在 `sole_quality_refused` 事件里。
4. 复用装备调适已有的 **`healAwakeningRecord` 自愈**（实例行 `+2` 与 `Template` 不一致时
   只修行内模板字段），避免同一类脏记录让秘宝也点不动。

## 8. 成功率：源里的事实与决定（2026-10-02）

排查"精炼是否像强化那样有内部概率"时的全量结论：

| 系统 | PVF 里有成功率吗 | 本项目口径 |
| --- | --- | --- |
| 装备调适（CMD2258） | **有** `[rates]` 段 | 全量 84 条（21 组 × 4 阶段）**全 = 100%** ⇒ 必成功；若源出现 <100%，`PlanAwakening` 会**明确拒绝**而不是静默当成功 |
| 秘宝精度（CMD2288） | **没有**（搜 `rate`/`prob`/`success` 零命中） | 必成功；随机只在**单次增量 5..20**（`soleQualityGain`，含两端） |
| 强化 / 增幅 | **没有**（项目早前已证实：`amplify_upgrade.go` 的注释与测试） | 按官方页数据（内置常量） |
| 增幅券 | **有**（券自身的段值 `<目标等级> <成功率> 'fixed' -1`） | 券写多少就多少 |

**决定（业主 2026-10-02）**：**不**给秘宝引入失败概率 —— 源里没有依据，且"失败时扣不扣料、
掉不掉精度"没有任何客户端表现证据（按 `AGENTS §0.2 禁止猜包`）。保持"**每次必成功、增量 5..20 随机**"。

⚠️ 另外澄清一个易混点：面板上那个 `14%` / `29%` 是**精度本身**（0–100 的进度），**不是成功率**。

**唯一的例外是上限截断**：精度到 `[max quality]` 前最后一次提升会被截断
（例如 95 + 掷出 20 ⇒ 记 100，实际增量回填 5）—— 这是必须的，不能越过源声明的上限。
