## 3. ★★「累计时长奖励一直有问题」的根因：**动作门禁只认 1**

`cmd/wireprobe/honey_time_claim.go`：

```go
if kind != protocol.HoneyTimeClaimKind {   // HoneyTimeClaimKind == 1
    return ignore("unknown claim action kind")   // 记事件后 dispatchNext，什么都不回
}
```

上游的 IDA 结论（UI 虚拟回调 `14412c770`）：**四个 group 数组对应 action `1, 2, 3, 5`（跳过 4）**，
`offset` 是"选中那个 UI 数组里的 0 起下标"。

本季 `honeytime.evt` 实测（`runtime/pvfcand/00-honeytime.evt.txt`）只有两个 `[reward info]` 块，顺序是：

| `[reward info]` 序号 | `[reward type]` | `[loop]` | 行数 | `[max reward offset count]` |
| --- | --- | --- | --- | --- |
| 0 | `daily` | 3（3 个 `[reward data]` 块） | 首块 4 行 | `daily 4` |
| 1 | `period` | 1 | 5 行 | `period 5` |

`period` 那块的 5 行（每行 5 个数字，末位是毫秒）：

```
0 10420527 1 0 72000000     ← 20 h
1 10421322 4 0 72000000
2 10421302 1 0 72000000
3 10420522 1 1 72000000
4 10420523 1 1 72000000
```

⇒ **action 1 = `daily`（面板上面那行）、action 2 = `period`（下面那行「累计在线时长」）**。
点下面那行发的是 `(313, 2, 0..4)` —— 我们的门禁把它当"未知动作"放行了，**所以永远没反应**。
（我们原来还去读偏移 12 那一格当"轨号"，实机两次样本都是 0 ⇒ 那一格不是轨号。）

## 4. 第二条可动的地方：期间轨进度很可能在**尾部 `@60`**

`DFO_HONEYTIME_PERIOD_SLOT` 的 `probe` 探针（2026-10-10）结论是「期间轨**不是** 1/2/3 那三条」，
于是缺省改成了 `off`（不伪造进度）。

上游把 **`@60` 那个 u32 命名为 `PeriodSeconds`** —— 与那条实机结论**正好互证**：
期间轨的累计秒数在**尾部**，不在三个 group 的 `Seconds` 里。`@64` 的 4 个 u32 是
`LoopCounts`（4 条轨各自的 loop 计数）。

## 5. 拟改动（最小、分三步，需业主确认后动手）

   `offset` 直接当该轨的 0 起下标；**删掉"读偏移 12 当轨号"的猜测分支**。
   同时保留"实机 16 字节帧"的宽松度（上游写死 `len == 12` 会被真实帧拒掉 —— 我们这边有实机反例）。

   `DFO_HONEYTIME_PERIOD_SLOT` 从"选轨"改成"开/关 + 诊断"。
3. 把协议文件的注释按上游命名补齐（Enabled/Seconds/Step/Values/Mask/Limit、PeriodSeconds、
   LoopCounts、SourceFlag/FinalFlag），并把 `specified`/`extend_daily` 两个 group 名登记进自检
   （本季 evt 没有，出现即报错、不猜）。

**明确不做**：不照搬上游的 `internal/activity` 包（我们已有等价且更完整的目录 + 接线）；

## 8. ★★ 期间轨按钮点不动的根因：1294 的 `@47`（格 1 的「轮数」）我们从来没写过

### 8.1 先纠正一条旧的结论

业主实机截图显示下面那行**已经**变成 `Completed 80h Honey Time!` —— 说明我们推的 `PeriodSeconds`
**一直在驱动那一行**。2026-10-10 那次探针之所以"看起来没变"，是因为它故意写的是 `287700 s`
（离 80 h 门槛差 300 s）⇒ 下一档仍是 80 h、文字不变。**"期间轨不由 1/2/3 轨驱动"这个结论是错的**，
应当撤回：`@60`（格 3 / 上游命名 `PeriodSeconds`）或 `@26`（脚本 `period` 组）就在驱动它。

用客户端算法反推也对得上（`sub_143CC72A0`，`next194 §12.5`）：`225678 s` 逐行相减 ⇒
`+148 = 4` ⇒ 下一档 = 第 4 行（`f0=3`，80 h）—— 与面板文字**完全一致**。

### 8.2 根因（L0，逐条带地址）

### 9.1 还没验的：领取到账

业主要接着点那 3 个亮的按钮。判据（服务端日志）：

```
honeytime claim track=1 row=N tier=… applied=true mail=…
```

- 期望 `row` = **0 / 1 / 2**（左起第 1/2/3 个），与上游那份的
  "zero-based position in the selected UI array" 一致；
- 若出现 `honey_time_claim_ignored action=2 reason="no period tier maps to this offset"`
  ⇒ 下标口径要再核（拿两个不同档的真实样本一比即可）；
- 若 `honeytime claim track=1` 出现但 `applied=false` ⇒ 是幂等键（该档今天已领）或门槛判定；
- 邮件模板应为 period 行的物品（`10420527` / `10421322` / `10421302` …）。

### 9.2 方法论留档

**"进度能显示"≠"按钮能点"**：这两件事在 313 里由**不同字段**驱动 ——
