## 2. 「没接线」到底是哪一帧（C1 / C2）

### 2.1 怎么找到的（可复跑）

1. `E:\迅雷下载\实时抓包\opcodes.tsv` 给出每个包的**名字 + string_va + table_slot_va**（运行时态，来自 dfocap 挂进程读内存）。
2. `table_slot_va` 落在 `.data` 的 BSS 里（全是 FF）⇒ 派发表**运行时才填**，静态读不到处理函数。
3. 但客户端把**注册调用**写成了统一形状：

   ```
   lea  r8, <handler>
   mov  edx, <packet id>
   call sub_14599D5D0      ; 注册 S→C（noti）
   ```

   ⇒ 在 `DFO.exe` 里搜 `BA <id 小端 4 字节>`，往后找 `E8 → sub_14599D5D0` 就是注册点；
   往前找最近的 `4C 8D 05 <rel32>` 就是 handler。
   **自检**：用已知的 `2838 → sub_140656A00` 反查，命中一致 ⇒ 方法成立。
4. 产物：`analysis/dumps/ida-attunement/scan-register.py`、`scan-handler-ptr2.py`。

### 2.2 结果

| 包 | 名字 | 处理函数 | 注册它的模块 |
| --- | --- | --- | --- |
| noti 2836 | OMEN_OF_ORDER_PARTY_INFO | `sub_140656A80` | 边界之守（小深渊） |
| noti 2837 | ENDKEEPER_OF_ORDER_INFO | `sub_1406568F0` | 同上 |
| noti 2838 | ENDKEEPER_OF_ORDER_REWARD | `sub_140656A00` | 同上 |
| noti 2839 | OATH_SYSTEM_INFO | `sub_1405757F0` | 誓约系统 |
| noti 2756 | FORTIFIED_DISCIPLE_OF_DOOM_REWARD | `sub_1406B18D0` | **调律共用模块**（`sub_1406B1520`） |
| **noti 2859** | **BOUNDARY_OF_ATTUNEMENT_REWARD** | **`sub_1406B18D0`** | **同上** |
| cmd 2343 | FORTIFIED_DISCIPLE_OF_DOOM_HIDDEN_SELECT | （functor `sub_1406B1860`） | 同上 |
| **cmd 2406** | **BOUNDARY_OF_ATTUNEMENT_HIDDEN_SELECT** | （同一个 functor） | 同上 |

`sub_1406B1520`（调律模块 init）里能读到它的身份常量：

```c
*(a1 + 228) = 100004768;
*(a1 + 232) = 100005068;     // ← 调律之边界（史诗）副本号
*(a1 +  80) = 72;            // ← 2859 的三个档位字段，不发包时就是 72/72
*(a1 +  84) = 72;
*(a1 +  88) = -1;
sub_14599D5D0(qword_14E66C090, 2756, sub_1406B18D0, 0);
sub_14599D4D0(qword_14E66C090, 2343, &functor);
sub_14599D5D0(qword_14E66C090, 2859, sub_1406B18D0, 0);
sub_14599D4D0(qword_14E66C090, 2406, &functor);
```

### 2.3 `NOTI2859` 的报文形状（**12 字节，3 × u32**）

`sub_1406B18D0` 的完整反编译（`runtime/ida-attunement/probe7-out.txt`）：

```c
__int64 sub_1406B18D0()
{
  int v1, v2, v3;
  v1 = 0; v2 = 72; v3 = 72;          // ← 短包时的兜底
  sub_146EA0BE0(&v1, 12);             // ← 从包里读满 12 字节：v1=packet[0:4] v2=[4:8] v3=[8:12]
  *(_DWORD *)(sub_1406B1BD0() + 80) = v2;
  *(_DWORD *)(sub_1406B1BD0() + 84) = v3;
  *(_DWORD *)(sub_1406B1BD0() + 88) = v1;
  return sub_1406B1BD0();
}
```

⇒ **字段映射：`module+88 = packet[0]`（与 2838 的第一个数落同一个槽位）、`module+80 = packet[1]`、`module+84 = packet[2]`。**
`module+88` 与 2838 处理函数写 `+88` 是**同一格** ⇒ 它俩是同一套「档位」语义的两个入口（一个是边界之守，一个是调律之边界）。

> ⚠️ 三个数的**具体语义（哪个是珠子 / 哪个是誓约 / 第三个是什么）尚未取证**。
> 按 §0 硬约束「禁止猜包」，本轮**不落默认发送**，先做成诊断开关供实机试（见 §5）。

## 3. 动画由谁驱动：**不是掉落物**（C3 / C4）

### 3.1 客户端手里有且只有四档掉落动画

字符串表（`analysis/dumps/xorstr_addr_to_text.json`）里，这四个 `.ani` 的唯一引用者是
`sub_140657920`（边界之守模块 init，与 2838 的解析器 `sub_140656A00` 紧邻）：

```
Contents/2026/EndkeeperofOrder/Common/UniqueDrop_00.ani      +  OB_RARITY_SKY_DROP_UNIQUE
Contents/2026/EndkeeperofOrder/Common/LegendaryDrop_00.ani   +  OB_RARITY_SKY_DROP_LEGENDARY
Contents/2026/EndkeeperofOrder/Common/EpicDrop_00.ani        +  OB_RARITY_SKY_DROP_EPIC
Contents/2026/EndkeeperofOrder/Common/PrimevalDrop_00.ani    +  OB_RARITY_SKY_DROP_PRIMEVAL
```

⇒ 演出只有 **unique / legendary / epic / primeval** 四档（没有 normal/rare），
正好是深渊该有的那四档产出。

### 3.2 但实机掉的装备**并不恒定高档**

把 `roles_persist_..._20261007_210421_873031_next37` 的四次通关（NOTI38 掉落帧）逐条解出来，
再按 `items.index.json` 取路径、从内层 PVF 读 `[rarity]`：

| 场次 | 副本 | 掉落实物 | 最高 rarity |
| --- | --- | --- | --- |
| 1 | 100005067（传说砝码） | 102020842 | **4** |
| 2 | 100005067 | 100251125 / 100313551 / 100345982 | **6** |
| 3 | 100005068（史诗砝码） | 100401592 / 100391036 / 100161045 / 100201080 / 108040815 | **4** |
| 4 | 100005068 | 101040830 / 100151120 / 100251136 / 100201105 / 100401638 | **4** |

**四场不恒定**，而业主看到的是**恒定太初**。⇒ 动画与掉落**不是同一条线**，
必然另有一个「档位信号」在告诉客户端该放哪一档 —— 而我们现在能想到的候选只剩：

- **`NOTI2859`（没发，模块里留着 `72/72/-1`）**；
- 以及 `NOTI2838`（发了，但值是从 fixed 池随机掷的，见 §4）。

## 4. 第二处错位：珠子档位的**来源**错了（C5）

官方口径（业主 2026-10-07 提供的 6 张图）：

> 根据「调律砝码」入场材料的不同，会出现不同的珠子，**保证获得对应稀有度以上的道具**。
> 传说砝码 ⇒ 保底 **传说~太初**；史诗砝码 ⇒ 保底 **史诗~太初**。

源数据（`configs/attunement-rewards.generated.json`）里，三个副本各有自己的 CTP，
而**每张表 fixed 池的最低档正好就是那个保底档**：

| 副本 | CTP | fixed 池的档位 | 最低档 |
| --- | --- | --- | --- |
| 100005066 | `skyofathousandseasofborder/unique.ctp` | unique / legendary | unique |
| 100005067 | `.../legendary.ctp` | **legendary** / epic / primeval | **传说** ✅ |
| 100005068 | `.../epic.ctp` | **epic** / primeval | **史诗** ✅ |

⇒ **砝码 = 副本号**（`100005066` 无砝码 / `100005067` 传说 / `100005068` 史诗）。
业主说的「靠客户端的选择判断用的是哪种砝码或者没选砝码」，在当前接线里
**就是客户端 `CMD16` 选的那个副本号 + 难度字节**（`CMD16` = 32 字节，
`u32 副本号 | u8 难度 | … | u16 队伍 0xFFFF`；实测两场大深渊难度都是 0，只有副本号不同）。

而我们的 `internal/loot/attunement_plan.go:PlanRun` **把 primer 从 fixed 池按权重随机掷**
（实机日志：`primer=epic(44)` / `primer=legendary(43)` / `primer=epic(44)`），
**没有把「砝码对应的保底档」当作下界**。⇒ 客户端看到的珠子档位与官方口径不一致。

> ⚠️ 这一条**本轮只定案、不改**：改「档位来源」会同时动掉落分布与 2838，
> 需要业主先确认「砝码 → 珠子档位」是**固定取保底档**还是**保底 + 向上随机**。
> 官方文案「保证获得对应稀有度**以上**的道具」两种解释都通。

## 5. 本轮落地

### 5.1 ★ 真根因修复：`[booster info]` 的 `-1` 占位符被吃掉（C6 / C7）

`internal/catalog/booster_import.go` 的 `parseBoosterInfo` 用 `Value > 0` 收集池正文，
把源里代表「本次没有」的 **`-1`** 丢掉了。池正文的形状是

```
<drawCount> [ <template> <weight> <count> ] …
```

丢一个数 ⇒ **整体错位一格**。以真实源 `stackable/10419001/10419725.stk` 为例：

```
[booster info]
[etc]    1 10362432 10000 30                                    [/etc]   ← 银币×30（本来就对）
[etc]    1 -1 911200 1 10420672 60000 1 10420673 18000 1 …      [/etc]   ← 「91.12% 什么都不给」
[etc]    6 -1 474500 1 100401592 272000 1 10419720 253500 1     [/etc]   ← 「抽 6 次」
[etc]    1 10362484 76923 1 10355161 76923 1 10362485 846154 1  [/etc]
[/booster info]
```

旧读法（丢掉 −1 后剩 15 个数，`(15-1)%3≠0` ⇒ 退回「两两成对」分支）得到：

| 读出来的候选 | 真实含义 | 实机后果 |
| --- | --- | --- |
| `template 1` weight 911200 | 池开头的 **drawCount 1** | 地上掉 **`stackable/coin.stk`（复活币）**，权重 91.12% ⇒ **几乎每把都掉** |
| `template 6` weight 474500 | 池开头的 **drawCount 6** | 地上掉 **`stackable/cash/store_silver.stk`（金库升级道具）** |
| `template 12` | 池开头的 **drawCount 12** | 目录里没有 ⇒ 被当「空面」丢掉（启动日志 `1 empty-face templates: [12]` **早就在报**） |

修法：

1. `boosterNumber(int32) uint32`：**负数保留**，映射成 `BoosterNoDropTemplate = 0xFFFFFFFF`
   （「抽中了但什么都不给」，它占的还是那份概率）；0 仍然过滤。
2. `IsBoosterNoDrop()`，在两条付费路径上跳过：
   `internal/loot/reward_box.go`（掉落期展开）与 `cmd/wireprobe/booster_flow.go`（玩家手开）。
3. 回归测试 `internal/catalog/booster_import_test.go`（3 条，纯合成 cell，不依赖 PVF）：
   - 占位符必须留住、且**候选里不能再出现 1 / 6**；
   - `[draw count] 6` 必须被当成**抽 6 次**，而不是「模板 6」；
   - 0 仍然不进池正文。

**顺带的正向收益**：誓约池的 `[draw count] 6 / 12` 恢复 ⇒
`100401592` / `10419720` 这条线从「1 次」回到「6 / 12 次」。

## 10. 怎么启动（业主问：平时走 `调试启动-本地构建.cmd`）

### 10.1 关键限制：`launch` 子命令**不透传**未知参数

`cmd/dfolauncher/main.go` 的 `runLaunch` 用**固定 flag 集合**（`--root/--check/--dry-run/--server-only/--client-only/--storage-only/--json-mode/--source-build/--repair-profile/--tag`），
`flags.Parse` 之后**没有**把剩余参数交给网关。所以 `调试启动-本地构建.cmd -attunement-reward ...` **到不了**网关。

但网关子进程**继承父进程环境**：

```go
// internal/launcher/serverrun.go:112
env := newChildEnv(BuildServerEnv(CurrentEnv(), report.ProfileEnv, opts.JSONMode))
// internal/launcher/env.go:74  func CurrentEnv() []string { return os.Environ() }
```

⇒ **走环境变量 `DFO_ATTUNEMENT_REWARD` 即可**，不用改任何 profile / 配置。

### 10.2 两条可用的启动方式

**A. 一键包装（新增，未跟踪）**：`scripts\launch-attunement-reward.cmd`

```cmd
scripts\launch-attunement-reward.cmd 44,43,0
scripts\launch-attunement-reward.cmd 2c0000002b00000000000000
scripts\launch-attunement-reward.cmd 44,43,0 --server-only
```

它做三件事：`set DFO_ATTUNEMENT_REWARD=<你给的值>` → 把 `runtime\dev-local\` 的 5 个本地产物拷回原位
（与 `调试启动-本地构建.cmd` 同一套拷贝，**全 ASCII 路径**，避免 cmd 对非 ASCII 字节的解码依赖）→
`server\work\dfo-lan\bin\dfolauncher.exe launch --root .`。

**B. 手工两行**（在同一个 cmd 窗口里，先设变量再跑原脚本，父环境会被继承）

```cmd
cd /d D://115us
set DFO_ATTUNEMENT_REWARD=44,43,0
调试启动-本地构建.cmd
```

## 12. 免重启试值模式（2026-10-08 09:2x）


- 文件里**第一个非 `#` 行**生效，写法与命令行一致（`42,42,42` 或 24 位十六进制）；

  `attunement reward (noti 2859): sending [0]=42(unique) [1]=42(unique) [2]=42(unique) hex=…`

  启动期那一次校验仍会挡住拼写错误/文件不存在（1 秒内失败）。
- 为什么用**绝对路径**：网关的 cwd 是 `D:/115us`，相对路径在它那里解析不了（老坑）。
