# next177 — 小深渊征兆「连续 30 次未触发」保底计数器（2026-10-08）

> 业主口径（2026-10-08 原话）：
>
> 小深渊征兆如果累计打了 30 次都不触发，保底帮玩家累计 1 阶征兆一次（说明角色维度应该
> 存在一个计数器，记录玩家没触发征兆的次数，一旦有征兆了就归 0，即便征兆当轮不结算，
> 直到征兆被结算后，重新计数）。
>
> 约束：**这个计数只针对小深渊的征兆系统，不要产生其他影响。**

## 1. 规则落成代码（`internal/loot/omen.go`）

征兆的阶段表一行一个门槛，`roll` 是百万空间的**三选一**（见 `omen.go` 文件头）：

| 命中区间 | 结果 |
| --- | --- |
| `< [obtain prob]` | 获得一个征兆（持有 +1） |
| `< [obtain]+[drop prob]` | 结算该阶段奖励，持有归 0 |
| 其余 | 无变化 |

小深渊（100005014）五行实测值：行 0 `obtain 100000 / drop 0`，行 1 `100000/600000`，
行 2 `100000/400000`，行 3 `100000/330000`，行 4 `0/1000000`（满档必结算）。
⇒ **只有行 0（持有 0）会产出「无事发生」占 90%**，所以「连续 30 次不触发」这件事只发生在
「手上一个征兆都没有」的那些场次。

`OmenPityMisses = 30`，推进逻辑（`AdvanceOmen`）：

- 获得一个征兆 → 计数 **归 0**（官方：「一旦有征兆了就归 0，即便征兆当轮不结算」）。
- 结算（含满档强制结算）→ 计数 **归 0**（「直到征兆被结算后，重新计数」）。
- 无事发生 **且本场开始前持有 0** → 计数 +1；加到 30 时**直接补 1 阶征兆**（`Pity=true`）
  并归 0。保底那一阶是「获得」，不掷 list、不发阶段奖励。
- **持有 ≥1 时计数不动**：那时还没结算，按口径要等结算之后才重新计数。所以计数到 30 只可能
  在持有 0 的场次发生 —— 保底不会在「已经拿着征兆」的时候再补第二阶。

随机数：保底发生在三选一的 `default` 支里，**不额外掷骰、不改分布**，种子链与旧行为逐字节一致。

### 只影响小深渊

计数写在 `AdvanceOmen` 里，而该函数在**没有 `[coupon drop table]` 的副本**上开头就原样返回
（连种子都不消耗）。实测只有 100005014 有行，大深渊 100005066/67/68 一行都没有
（`configs/attunement-rewards.generated.json`）。`TestOmenPityNeverTouchesDungeonsWithoutStages`
把这个隔离钉住。

## 2. 存档（角色维度）

列加在既有的 `character_omen_state`（按 角色 × 副本 记，见 `internal/database/omen_state.go`）上。

**⚠️ 必须新开一个小节，不能改 0030**：`migrateSQLite` 按**小节校验和**记账，改动已应用的
0030 会让既有存档以 `migration 0030_omen_state.sql checksum differs` 拒绝打开。

```sql
-- migration: 0038_omen_pity.sql
ALTER TABLE character_omen_state ADD COLUMN misses INTEGER NOT NULL DEFAULT 0 CHECK(misses>=0);
```

- 新小节只应用一次：既有库补列，新库（0030 建表之后）补列，两边都成立。
- SQL 文件必须**纯 ASCII**（规则 D23，`TestSQLDialectFilesAreASCII`），所以注释用英文。
- 查询面：`OmenState` 的 SELECT 多一列，新增 `SaveOmenMisses`（**单列** upsert，
  理由与 `SaveOmenHeld` 相同：各列由不同时刻推进，整行回写会盖掉对方刚写的）。
- 生成代码是两个包（`sqlcgen` + `sqlcgensqlite`）**手工镜像**的 —— 本机没有 sqlc 可执行文件，
  且 `GOPROXY=off`。两包之间还有 `queryset.go` 的接口与 `sqlite_adapter_gen.go` 的适配函数，
  都必须同步，`generated_parity_test.go` 会比对两包的 API 面。

## 3. 诊断开关（实机验收用）

`-omen-misses <0-29>`（`DFO_OMEN_MISSES`）：把小深渊的未触发计数直接摆到某一格并**写回存档**，
与 `-omen-hold` 同一套（每会话只应用一次）。**为什么需要它**：在行 0 上每次通关有 10% 概率
获得征兆，而「连续 30 次都不触发」的自然概率只有 `0.9^30 ≈ 4.2%` —— 靠自然通关验证要几百场。

一轮验收（`-omen-state -omen-misses 29`）：

1. 启动日志应出现 `omen state: diagnostic -omen-misses pinned dungeon 100005014 to 29 misses`。
2. 进小深渊打一场（任何一个「无事发生」的通关即可）。
3. 事件流里那一场应当是 `"pity": true`、`"gained": true`、`"misses": 0`、`"after": 1`。
4. 客户端 noti 2836 的征兆 UI 应亮起 1 阶（下次进本/刷新时按存档里的 held=1 下发）。
5. 反例：`-omen-misses 28` 那一场应当 `"pity": false`、`"misses": 29`。
