## 1. ⚠️ 重要纠正：`[角色 + 0x697C]` **不是**扩展槽解锁状态

早前（next50）把它当作"扩展槽解锁标志"是**错的**。证据：

四个"读点"实为**同一类查询的包装**（`0x145cdd020` / `0x145cf15b0` / `0x145cdcda0` / `0x145d20e80`）：

```asm
loop:
  call 0x145a89860                 ; 条件检查
  jne  → r8d = [rdi + 0x697C]      ; ★ 把 +0x697C 当"参数"传下去 ★
  call 0x145cdc8e0                 ; ★ next47 的"装备对比查询"入口 ★
  cmp rax, rsi ; je → 返回 ebx
  inc ebx ; cmp ebx, 0x1a ; jl loop  ; 循环 0x1A = 26 次
```

`0x145cdc8e0` 正是 **next47 里"Query(id) → 已装备对象"**（`0x145cdca30` 的入口 stub）。
→ `[角色+0x697C]` 属**升级箭头（装备对比）领域**，与装备栏的锁**无关**。

**因此**：`NOTI328`（写 `+0x697C`）、探针观察到的 `+0x697C` 反复被刷新，都不能用来判断解锁状态；
next50 里 attempt 1/2/3 围绕它的尝试，方向本身就是偏的。

## 4. ★ 判据已定位（2026-09-22 静态确认）

**装备栏格子的"锁 / 开"由一次容器查找决定**，函数 **`0x142384990`（4184 字节）**：

```asm
0x1423849d2  mov r12, rcx                       ; r12 = this
0x142385011  cmp qword ptr [r12 + 0x668], 0     ; this+0x668：旁路/强制标志
0x14238501a  setne al
0x142385025  cmp r15d, 1
0x142385029  cmovge r9d, ecx                    ; r9d = (r15d >= 1) ? al : 0
0x14238502d  mov edx, dword ptr [rbx + 0x1c]    ; ★ 取一个 id ★
0x142385037  mov r8, qword ptr [r12 + 0x660]    ; ★ this+0x660 = 按 id 索引的容器（树）★
   ...（红黑树/有序树查找：按 edx 比较 [node+0x1c]）...
0x14238506f  movzx edx, byte ptr [rcx + 0x20]   ; ★ 命中 → 取节点 +0x20（byte）★
0x142385075  xor dl, dl                         ; 未命中 → 0
0x142385077  mov r14d, edi
0x14238507e  cmp dl, 1
0x142385081  cmovne r14d, eax                   ; ★ r14b = (dl != 1) ? r9b : 0 ★
```

**使用点**（三处结构相同，控制在 `[rbp-0x68]` / `[rbp-0x78]` / `[rbp-0x48]` 三个元素上）：

```asm
0x14238517e  test r14b, r14b
0x142385181  je  0x1423851d5        ; r14b == 0 → 走"隐藏/另一分支"
0x142385185  call qword ptr [rax + 0x10]   ; 虚调用(dl=1)
0x14238518e  call 0x146af10b0              ; ★ 显示该元素 ★
```

**结论**：
- **解锁判据 = "在 `this + 0x660` 的容器里，存在 id（`[源对象+0x1c]`）对应的节点，且该节点 `+0x20` 的 byte 为 1"**；
- 存在 → 显示 `equip_slot_open`（开）；不存在 → 显示 `equip_slot_block`（锁）；
- `this + 0x668` 是另一个相关标志（非 0 参与 `r9d` 的计算）。

### 4.1 容器类型确认（补充）

从判据里的树遍历指令序列（`[+0x0]`/`[+0x8]`/`[+0x10]` 左右子与父、`+0x19` 红黑标志、`+0x1c` key、`+0x20` value）
可确认：

- **`[this + 0x660]` 是一个 `std::map<int, byte>`**（key = id，value 为 0/1）；
- **`[this + 0x648]` 是一个步长 `0x10` 的数组**，其元素的 `+0x1c` 被当作上面那个 map 的 key 轮询。

**完整语义**：遍历 `[this+0x648]` 的每个元素 → 用其 `+0x1c` 查 `[this+0x660]` 的 map → 查到且值 = 1 → 该格显示「开」，否则显示「锁」。

### 4.2 未闭环：数据源（本文档的停止点）

**已知缺口**：谁把 id 填进 `[this+0x660]` 这个 map（以及谁填充 `[this+0x648]` 数组）。

静态尝试与结论：
- `0x142384990` **没有 `call` 引用、不在任何虚表里**（已扫 `e8`/`e9` 与数据段指针）→ 属内联/近邻调用，无法由它反推类归属；
- 用"同时访问 `+0x648` 与 `+0x660`"过滤 → **1076 个函数**，无法收敛（这两个是通用偏移）；
- 用"访问 ≥2 个 `+0x648`/`+0x660`/`+0x668`"过滤 → **1998 个函数**，同样无法收敛。

**因此静态路线在此遇到收敛瓶颈**，需换手段（见下）。

## 4d. C 方案三层反推结果（2026-09-22，静态）

按"最多三层"推进，结果如下：

**第 1 层 —— 判据的入口（ctor 风格 thunk）**

扫"目标落在 `0x142384990..0x1423859e8` 范围内任意位置"的 `call`/`jmp`（精确地址扫描曾漏掉，因为入口是 thunk）：

```asm
0x142383c9e  jmp -> 0x142384990   (调用方 fn 0x142383c30)
0x142384986  jmp -> 0x142384990   (调用方 fn 0x142384970，27 字节 thunk)
```

两个入口结构一致（`mov rbx,rcx` / `call 0x1423859f0` / `mov rcx,rbx` / `jmp 0x142384990`），属同一类。
**注**：thunk 本身不出现在数据段（不是虚表项），说明调用方是普通调用而非虚调用。

**第 2 层 —— `0x1423859f0`（1215 字节）**

它是**初始化/更新**，但**不写 `+0x660` 那个 map**：全函数扫描确认没有任何
`+0x660` / `+0x648` / `+0x668` 访问。它的实际动作是：取全局单例 → 按 id 做 `sprintf` 格式化
→ 查/设置 UI 元素（如 `[this+0x5F8]`）。

**第 3 层 —— 全局单例 `0x14e638088`**

判据函数 `0x142384990`、两个 ctor 入口、以及 `0x1423859f0` 都引用同一个全局单例 **`0x14e638088`**
（构造点 `0x1422af680`，另见 `0x1422b2580` / `0x1422b1eb0` / `0x1422a7a60` 等访问器）。

**结论**：三层内没有直接到达"写 map"的点，但**收敛到一个固定地址的全局单例 `0x14e638088`**——
其形态符合"玩家/装备数据管理器"：**服务端数据灌进该单例，各类 UI 从它取数**。

**这比继续追 map 的插入点更有价值**：单例是**固定地址**，动态观察成本最低（无需先拿 `this`）。
后续动态方案可优先盯 `0x14e638088`，而不是 `0x142384990`。

## 4e. C 方案第二组三层（2026-09-22，静态，未提交）

承接 §4d，继续三层：

**第 4 层 —— 判据入口是虚函数**

`0x142383c30` 位于虚表 **`0x149993888[8]`**。该类在同一代码区的方法仅 4 个：

| 虚表项 | 地址 | 大小 | 说明 |
| --- | --- | --- | --- |
| [1] | `0x1423826d0` | 105B | 析构（`mov edx, 0x6a8` → 揭示类大小） |
| [6] | `0x142384420` | 108B | 与 UI 元素交互（访问 `+0x628`） |
| [7] | `0x142383cb0` | 73B | 查 UI 元素后尾调用 `0x141bb64f0` |
| [8] | `0x142383c30` | 115B | **判据入口** |

**第 5 层 —— `0x142383c30` 是"单例懒初始化 + 初始化 + 判据"三合一**

```asm
0x142383c3f  mov rbx, rcx
0x142383c47  mov rcx, [rip+0xc2b443a]   ; 全局 0x14e638088
0x142383c4e  test rcx, rcx
0x142383c51  jne skip                     ; 已存在 → 跳过
0x142383c53  mov ecx, 0x2E90              ; new 0x2E90 字节
0x142383c6a  call 0x1422af680             ; 构造该单例（虚表 0x14995e710）
0x142383c76  mov [rip+0xc2b440b], rcx     ; 存全局
skip:
0x142383c89  call 0x1422b3440
0x142383c8e  mov rcx, rbx                 ; ★ this = rbx（另一个对象）★
0x142383c91  call 0x1423859f0             ; 初始化
0x142383c9e  jmp  0x142384990             ; 判据
```

**关键**：它**顺手构造了全局单例 `0x14e638088`**（0x2E90 字节，虚表 `0x14995e710`），
但**判据的 `this`（`rbx`）不是该单例**，而是另一个对象。

**第 6 层 —— 类大小与实例来源**

- **该类大小 = `0x6A8`（1704 字节）**（析构 `0x1423826d0` 的 `mov edx, 0x6a8`）；
- `+0x648`（id 数组）/ `+0x660`（解锁 map）/ `+0x668` 都在 1704 字节内；
- 实例由**虚表调用**创建（`0x142383c30` 在虚表里，非直接 `new`）。

**结论**：`0x142383c30` 是"某个面板/列表类"的初始化方法——它初始化自身（1704 字节，
内含 id 数组与解锁 map），并顺带懒构造全局单例。

**下一步靶子**：找"**谁创建这个面板实例**、**谁往 `+0x660` 插数据**"。
两者之间：前者给出"面板由哪条数据链驱动"，后者直接等于"服务端该发什么"。

**RTTI 不可用**：该类虚表的第 0 项 RTTI（`0x14bc05150`，`pSelf` 校验通过）其 `type_info.name`
读出来是乱码 `'..\r'`，此 PE 的 RTTI 名称被裁剪/混淆，无法用类名辅助定位。

**说明**：本轮及此前若干轮的改动**均只留在工作区，未提交**（按用户要求，等修复确认后统一提交）。

## 4f. C 方案第三组（第 7 层，静态收敛失败）

**纠正上一节的一个错误推断**：`0x6A8` **不是类大小**。
`0x142372640` 里是 `cmp byte ptr [rcx + 0x6a8], 0` —— 它是一个 **byte 成员偏移**。
析构 `0x1423826d0` 里 `mov edx, 0x6a8` 的用途并非 `operator delete` 的大小参数，
不能据此推断类大小；**§4e 的"类大小 = 0x6A8 = 1704 字节"作废**。

**偏移特征过滤结果（均无法收敛）**：

| 过滤条件 | 候选函数数 |
| --- | --- |
| 访问 `[reg+0x660]` | 281 |
| 同时访问 `[reg+0x648]` 与 `[reg+0x660]`（同一基址寄存器） | 30+ |
| 同函数内访问 `+0x648`/`+0x660`/`+0x668` 中 ≥2 个 | 1998 |

**根因**：这些偏移在大量无关类里都存在，纯静态"按偏移找"缺少区分特征。

**另两条辅助线索也断了**：
- **RTTI 不可用**：该类虚表（`0x149993888`）第 0 项指向的 RTTI（`0x14bc05150`，`pSelf` 校验通过）
  其 `_TypeDescriptor.name` 读出为乱码 `'..\r'` —— 此 PE 的 RTTI 名称被裁剪/混淆；
- **虚表设置点找不到**：全 exe 扫描 `lea <reg>, [rip+X]` 指向 `0x149993888` 的结果为 **0**，
  说明该类的实例很可能是**别的对象的成员子对象**（内嵌），或虚表为数据段静态初始化。

**结论**：静态路线到此**收敛极限**。从"判据函数"再往外的两层
（"谁创建该对象"、"谁往 `+0x660` 插数据"）**缺少静态区分特征**。

**下一步必须动态，目标明确且低风险**：

> hook 判据入口 `0x142384990`（或其在虚表里的 thunk `0x142383c30`）拿到 `this`，
> **只读** `[this+0x648]`（id 数组，步长 0x10，元素 `+0x1c` 为 id）与
> `[this+0x660]`（`std::map<int,byte>` 解锁集合），把内容打出来。

**那些 id 就是"服务端该发什么"的答案** —— 该步骤**只读内存、不写任何状态**，
风险显著低于此前两次探针（NOTI328 attempt 1 的闪退、`MemoryAccessMonitor` 的卡死）。

**说明**：本轮改动**仍只留在工作区，未提交**。
