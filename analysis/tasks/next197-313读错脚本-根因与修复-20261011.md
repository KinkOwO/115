# next197 — 313（HoneyTime）「图标与奖励对不上」根因：脚本路径写死成了**另一份没有被索引引用的脚本**（2026-10-11）

> 触发：业主实机领取期间轨 3 档后报告「图标明显 3 个产物对不上」，怀疑"读的时候有偏移"。
> 结论：**不是偏移，是读错了文件**。整条 313 实现建在了 `live/event/kor/2026/0326_honeytime/honeytime.evt`
> 上，而客户端按 `list/event.lst` 读的是 `Live/Event/Kor/2023/1026_HoneyTime/HoneyTime.evt`。

## 0. 一句话

**`list/event.lst` 是"活动号 → 脚本路径"的唯一权威**。仓库里同时躺着两份 HoneyTime 脚本，
索引只认 2023 那一份；我们写死了 2026 那一份 ⇒ 面板（客户端）与发奖（我们）用两套物品号。

**★★ 时区坑（差点写错）**：本机 Git Bash 的 `TZ=Asia/Seoul` **不生效**（打印出来还是 09:00 UTC），
第一版我按它算出了 `1783587600 / 1785834000`，**两个都错 9 小时**。正确做法：
`.evt` 里的时刻按 **KST(UTC+9)** 折算，即 `script(HH:MM) → epoch(HH:MM KST) = UTC(HH:MM − 9h)`。
用 `date -u -d @<epoch>` 反向核对，别信 `TZ=`。

**两条独立交叉验证**（都与官服数据对得上）：
1. 新 end = `1785801600` 与本文件战令的 `aradPassEventStart` **是同一个数**；
2. `1785801600` 同时是 **331 官服 op108 行的 start**（`event_info_activity_test.go:139` 钉着它）。
⇒ HoneyTime 结束日 == 下一个版本日，两期活动首尾相接。

**进度迁移（走审计路径，不裸改库）**：GM 工具原来只有 `-clear-claims` / `-clear-period-claims`，
没有"把已领位图设回去"的开关 ⇒ 补了对称的 `-set-claimed` / `-set-period-claimed`（`main.go`），

## 8. 教训（写进长期约定）

- ★★ **活动脚本路径必须从 `list/event.lst` 解析，不许写死**。目录名/日期/"看起来最像"都不是权威；
  仓库里可能有**没被索引引用的同活动脚本**，写死它 = 面板与发奖两套物品号。
- ★★ **"索引里写着" ≠ "接线了"**：本次事实在 `event_info_activity_constructed.go` 的注释里躺了一整天。
- ★ 判定"客户端读的是哪一份"的捷径：**索引 → 路径 → 导出 → 与实机现象对账**（本机面板第 3 档是自选箱，
  2026 那份的第 3 档不是 —— 一条就能定性）。
- ★ **1294 帧里没有物品 ID** ⇒ 「面板图标 = 我们推的帧」不成立；面板是客户端自己按脚本画的。
  凡是"面板显示 vs 实际发放"不一致，第一嫌疑是**两边读的源不同**。
