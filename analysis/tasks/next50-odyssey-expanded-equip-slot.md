## 0. 一句话结论

**奥德赛模式下的三个扩展装备槽（辅助装备 / 魔法石 / 耳环）锁着，原因不在"服务端漏发某个包"。**
客户端的槽位状态来自装备栏"槽行对象"的只读字段 `[obj + 0x358]`，该字段在对象**构造时**即确定，
**整个会话内 0 次写入**（实测 53 万次读取、0 次写入），且登录路径上的同类判据函数
`0x14018e630` 是一个恒返回 0 的空实现（`xor eax, eax; ret`）。

## 2. 已确证的机制（全部有地址级证据）

### 2.1 状态落点：角色 +0x697C

```
0x145c4de40  mov dword ptr [rcx + 0x697C], edx   ; 写
0x145c49190  mov eax, dword ptr [rcx + 0x697C]   ; 读
```

### 2.2 每帧刷新：状态来自 model + 0x358

```
0x1458d09e6  call 0x1421b2820        ; → eax
0x1458d09d1  mov ebx, 4              ; 默认 4
0x1458d09d8  je   → ebx = 0          ; eax == 0 → 状态 0
0x1458d09dd  jne  → ebx 保持 4       ; eax ∉ {0,1} → 4
0x1458d09df  mov ebx, eax            ; eax == 1 → 1
0x1458d09f0  call 0x145c4de40        ; 写 [角色 + 0x697C]
```

即状态映射：`0 → 0`、`1 → 1`、**其它（含 -1）→ 4**。

### 2.3 判据链的两端

- **装备栏刷新路径**：`0x1421b2820` 只有一条指令
  `mov eax, dword ptr [rcx + 0x358] ; ret` —— 状态存在 `[[装备栏窗口 + 0x498] + 0x358]`。
- **登录路径**：`0x145641a4d` 调 `0x14018e630`，同样的 0/1/其它 → 0/1/4 映射；
  而 **`0x14018e630` 的函数体是 `xor eax, eax; ret`（恒返回 0 的空实现）**。

### 2.4 槽对象来自"槽行数组"

```
0x140584ed0  imul rbx, r9, 0x1A0     ; 行指针 = r8 + r9 * 0x1A0（每行 416 字节）
0x140584ee4  cmp qword ptr [rbx+0x20], 0
0x140584ee9  je  → 整行跳过           ; [行+0x20] == NULL 不处理
0x140584fb1  mov rcx, qword ptr [rbx+0x20]
0x140584fb5  call 0x1421b2820        ; 查 [obj+0x358]
```

寄存器实测（frida 探针）：`rdx` = 槽号（从 12 起）、`r8` = 行数组基址、`rdi` = 行索引。

### 2.5 NOTI328 的真实作用（**不是解锁通道**）

```
0x1452cffa0（handler，240B）
  ReadU16 actor → 查表比对是否本角色
  循环 3 次:
    ReadU8 state（>= 4 丢弃）
    call 0x145c4de40        写 +0x697C（临时）
    call 0x1452c1540        刷新一次（该函数继续消费同一个包）
  0x1452d006b  mov edx, esi     ; esi = 进入时的原值
  0x1452d0070  call 0x145c4de40 ; ★ 把 +0x697C 恢复原值 ★
```

**即：该帧的语义是"按给定状态刷新一次显示"，不是持久设置解锁。**

顺带纠正：`CMD 390`（`EXPAND_EQUIPSLOT_FLAG_UPDATE`）是 UI 交互上报，payload 仅 1 字节且 handler
只接受 `1`/`2`（值 0 直接丢弃），与解锁无关。

### 3b. 「任务路线」对奥德赛角色不可达（2026-09-22 实机确认）

> ⚠️ 表述修正：本节最初写成"任务手册的 Season 就是奥德赛的章节系统"，**这是错的**。
> 经用户指正：**篇章（Season）是剧情角色的主线任务系统，奥德赛角色根本没有这套系统**。
> `AradOdysseyChapterRewardWindow.xui` 那批字符串位于 `AradOdyssey` 目录，只能说明
> **奥德赛有自己的章节奖励 UI**，不能据此推断"任务手册的篇章属于奥德赛"。
> 下面的结论成立，但理由以本修正为准。

用户的思路（用剧情角色完成 649/650 来侧面观察槽位）本身合理，但**无法用于推断奥德赛的解锁机制**：

1. **篇章（Season）是剧情角色专属**：剧情角色有主线任务系统（Season.1~5）；
   **奥德赛角色没有**——任务手册直接显示
   **"阿拉德奥德赛模式不提供任务篇章。请在模式结束后查看篇章。"**（用户实机截图，2026-09-22）。
2. 因此两个模式是**两套独立机制**：
   - **剧情角色**：槽位走任务（`[slot expansion]` 奖励，quest 649/650/2636）
   - **奥德赛角色**：槽位**不走任务**，靠通关副本（anton / luke / gaebolg）
3. 结论：**"任务路线"对奥德赛角色不可达——因为奥德赛没有任务/篇章系统**，
   而不是"Season 属于奥德赛"。这也正式解释了早前观察到的"奥德赛模式不显示我加的任务"。
4. 由此可知：**不能靠"剧情角色的任务实验"来侧面推断奥德赛的解锁机制**（缺少可比的任务系统）。

**附带确认**：服务端侧 `Available()` 在 65 级时确实把 649/650 判为可接（临时测试实测：可用任务 237 个，
`649`/`650` 排在最前），所以**服务端过滤无问题**；剧情角色看不到它们是客户端按篇章/进度过滤的结果。

## 4. 探针给出的终结性证据

| 探针 | 观察 |
| --- | --- |
| `slot_state_probe.py` | 一个会话内 `+0x697C` 被写 115 次：**110 次来自 `0x1458d09f5`**（客户端自己的刷新链）值恒 0；我们发的 328 写了 1/2/3 后立刻被恢复 |

## 8. 闭环（2026-09-22 实机验证通过）

**根因（实时监听实锤）**：服务端**根本没有"通关奥德赛副本 → 解锁槽位"这条逻辑**。清关时该发的帧
一样不少（`boss_check_confirmed` / `dungeon_clear_enabled` / `dungeon_play_result` /
`dungeon_clear_reward` / `clear_available_quests`），但**没有任何解锁动作**；生产代码里
`100004950 / 100004953 / 100004969` 从未出现（只在测试与注释里）。全仓唯一的解锁入口是任务奖励
`quest/finish.go → inventory.UnlockEquipSlots`，而奥德赛角色不走任务（见 §3b）。

**实现**：

| 文件 | 改动 |
| --- | --- |
| `internal/inventory/expand_slots.go` | 导出解锁位常量 `ExpandSupport/ExpandMagicStone/ExpandEarring`（位值的家） |
| `internal/quest/index.go` | 常量改为引用 `inventory.*`（消除重复定义，值不变） |
| `internal/character/odyssey.go` | 新增 `OdysseyExpandEquipMask(副本ID)`；在 `OdysseyClear` 的**同一个事务**里调用 `inventory.UnlockEquipSlots`（失败一起回滚；重复通关只是 OR 位，幂等） |
| `cmd/wireprobe/dungeon_flow.go` | ~~通关后把新字节随 USERINFO1（`entry_addition`）重发一次~~ —— **已移除**，原因见下「重发的坑」 |

映射：`100004950`→mask `1`(support/槽 22)、`100004953`→mask `2`(魔法石/槽 23)、`100004969`→mask `16`(耳环/槽 25)。

**实机证据**：

- 服务端日志：`13:58:09` 盖波加 `100004969` 清关（新二进制）；
- **存档实测**（PostgreSQL `characters.state`）：角色 10 的 `inventory.expand_equip_flags = 16`，
  即 bit 4 = 耳环，与预期一致；
- 客户端：装备栏耳环槽点亮（用户截图确认）。

**与 §2/§4 探针结论的关系**：探针证明"槽位状态在装备栏行对象**构造期**决定、运行期只读"，因此解锁位
落库后**需要重登或进新副本重建装备栏**才可见 —— 本次实测正是重登后点亮，与该结论一致。

**新增测试**：`internal/character/odyssey_expand_slot_test.go`（映射 + 位值，并断言三槽全开 = 19）。
验证：`go build ./cmd/... ./internal/...`、`go vet`、`go test -count=1 ./internal/... ./cmd/...` 全绿。

### 重发的坑（2026-09-22 实机发现，已回退）

曾在通关时把新的槽位字节随 USERINFO1（`entry_addition`）**重发一次**，想让解锁当场生效。实测后果：

- 清关瞬间客户端**装备栏显示被清空**（角色身上/格子里的装备全空）；
- **存档毫发无损**：PostgreSQL `characters.state.inventory` 里 `equipment=10 / worn=10 / items=3 / gold=3587`
  一直完好，客户端全程**没有回拨任何装备变更**；
- **离开副本地图后显示即恢复** → 纯客户端显示层问题。

原因判断：`entry_addition` 是**进图/登录**时的帧，在**副本内**重发会让客户端重建装备栏显示。由于客户端的
槽位状态本就由"装备栏行对象构造期"决定（§2/§4），**解锁位落库后重登/进新副本自然带上新值**，
重发这一帧既不必要又有副作用，故移除：解锁只做"写进同一个角色事务"这一步。

**教训**：涉及装备栏/角色外观的帧不要在其常规时机（进图/登录）之外补发；服务端只负责落库，
让客户端在它自己的重建时机去读。

### 就地重同步（id-13 + id-14）实测：显示正常，但喂不进客户端（2026-09-22，待修复）

回退 `entry_addition` 后，改为补发与 **entry / 装备变更（`equipment_flow.go`）完全同款、同顺序**的两套通道帧：
`equipment_bag_resynced`(13) → `equipment_worn_resynced`(13) → `equipment_slots_updated`(14) →
`equipment_worn_window_refreshed`(14)，期望等价于"就地重登"。

实测（卢克 `100004953` 清关）：

| 观察点 | 结果 |
| --- | --- |
| 装备栏显示 | ✅ **正常**（不再像 `entry_addition` 那样被清空） |
| 魔法石槽当场点亮 | ❌ 否 —— 仍需**重登/重选角色** |
| 存档 `expand_equip_flags` | ✅ **19**（耳环 16 + 魔法石 2 + support 1 全部写入） |

**结论**：客户端**只在登录/选角那种时机构造槽行对象**，副本内补发 id-13/id-14 **无法触发重建**
（与 §2/§4「构造期决定 + 运行期只读」一致）。这两个帧暂时保留（无害，且可能在玩家主动重开装备栏时被采用 —— 未验证）。

**待修复（未闭环）**：解锁后的"**当场可见**"。当前玩家路径 = 通关后**重登或重选角色**。
想真正解决有两条路：
1. 解开 §5 未解项 —— 反向出"装备行记录（181B）里哪个字段映射到槽对象 `+0x358`、解锁值是多少"，然后确认客户端是否有"重建槽行数组"的入口；
2. 换锚点：看客户端是否有别的命令会让它重新构造装备栏（例如某种窗口刷新），用 frida 在"重登""重开背包"两条路径上对比 `0x140584ed0`（槽行数组遍历）的调用差异。
