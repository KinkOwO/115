## 1. 这条线是什么

DFO 的**战令 / 阿拉德通行证**：一条**周期 + 分档**的成长线。玩家做任务拿通行证经验 →
升级 → 按等级在**普通轨**（免费）与**皇家轨**（购入通行证后解锁）上逐档领奖。

真源是本仓 PVF 里的**文本脚本**：

```
live/else/univ/2026/0804_2026_aradpass_season3/newaradpassevent.evt
```

关键段（逐条实测读出来的）：

| 段 | 内容 | 我们的用途 |
| --- | --- | --- |
| `[event period]` | `2026-08-04 09:00:00` → `2026-10-20 09:00:00`（KST） | op108 活动行的运营窗口 |
| `[pass level info]` | 1..50 级各自的**累计**经验，满级 50000 | `Catalog.LevelFor(exp)` |
| `[reward table]` | 51 行 × 7 token：`<轨> <槽> <物品> <数量> <等级> <标题> <文案>` | 普通轨 25 档（track 0）+ 皇家轨 25 档（track 2） |

## 2. 协议（0x08A1 / 0x08A2，均纯 S2C）

| opcode | 名字 | 正文 | 布局 |
| --- | --- | --- | --- |
| `0x08A1` = **2209** | 账号级状态 | **760 B** | `u8 等级@4`、`u24 累计经验@5`、`×256 定点@8/@12/@16/@20`、`u8 任务数@0x1A + 16×7B`、`u8 任务数@0xED + 12×7B`、`u8 标志@0x1C2` |
| `0x08A2` = **2210** | 角色槽级状态 | **1104 B** | `4B 头 + 20×55B`；空槽 `charID = 0xFFFFFFFF` |

交叉校验（18/18 份抓包自洽）：`u24@5 == u32@12/256`、`u32@12/256 + u32@16/256 == u32@8/256`，
且 `u32@8/256 == 源 50000`、`u32@20/256 == 源 5000`。全部写在
`internal/game/protocol/aradpass115.go` 的头部注释里，`aradpass115_test.go` 逐字节钉住。

**领奖（CMD680 / CMD681，与 331/313/662 同一族）**：抓包 16B 正文
`<赛季 516> <轨道> <奖励槽> <保留>`；回包沿用活动族的 `EventReply115`
（`01 <事件号> <10×u32>`，45 B），第一格 = 请求的第二个字（轨道）。

## 4. 与来源实现的**有意分歧**（每条都有理由）

| # | 分歧 | 理由 |
| --- | --- | --- |
| 1 | `internal/loot` 里**不放 `Store`**：纯计算层用 `inventory.Awarder.Grant`，事务层在 `internal/workflow` | 本仓 §7.2 E13 两层的既定分工；来源那把 `Store` 塞进 `loot.Service` 是它的栈 |
| 2 | 奖励**直接落背包/装备栏**，满包整笔回滚，**不做邮件兜底** | 战令奖励是即时物；来源的 `landBoosterOrMail` 在本仓不存在，且"未经实证的邮件兜底"违背 fix-at-root |
| 3 | 领奖帧序 **推送先于应答**（`2210 → 2209 → 14 → 680 应答`） | 来源自己的注释写的抓包序就是"重推在应答之前"（21:34:51.829/837 vs 51.938），但它的代码把应答排在最前。331/313 的实机结论是**应答回调只清在途标志、界面全靠推送** ⇒ 按抓包序 |
| 4 | **680 的 8B 形态不回应答**，只记事件 + 放行 | 与 313 同款结论（进城自动帧；回了会给玩家弹无意义提示） |
| 5 | **681 只重推状态、不发奖** | 抓包只有 680 一个样本。来源对 681 也走发奖路径 ⇒ 一个查询可能白送一档奖励。宁可少做 |
| 6 | `0x08A2` **全槽留空**，不把当前角色登记进第 0 槽 | 抓包 21 份在玩家本人在线时**每一条都是空槽** ⇒ 那 20 槽不是"账号角色列表"；非空槽的 46B 无实证 |
| 7 | 修了来源 `sectionRaw` 的 bug：**段没有收尾标签时会读到 EOF** | 本仓脚本里 `[pass item index]`/`[db table name]`/`[max level display]`/`[weekly gainable exp]`/`[purchase pass exp]`/`[ui file]` 都**没有** `[/…]` ⇒ 原实现把后面所有段的数字都吞进 `PassItem`（实测 20 项，断言 `len==1` 当场炸）。改成"没有收尾标签时以下一个段标签为界" |
| 8 | `[reward table]` 的**轨道号在每一行都重复写**，不是只在换轨处写一次 | 本季实测 357 token = 51 行 × 7（普通 26 + 皇家 25）；按"只写一次"解会错位 |
| 9 | `[daily/season reward list]` / `[royalpass first reward]` 是**四列一行**，只取物品列 | 直接"取所有数字"会把**数量列**（1）当成物品号 ⇒ 发金币（模板 1） |
| 10 | 活动行 id **516 与 10005 都下发** | 抓包确认 516；10005 是同一活动的另一个开放时段（来源的开放时段基线表里两者都有）。都下发免得页签门禁查的是另一个 |

## 5. 门禁与不变量（测试钉住）

- **等级**：`st.Level(c) < row.Level` ⇒ 拒绝（`below the reward level`）。
- **皇家轨**：`track == TrackRoyal && !st.Royal` ⇒ 拒绝（`royal track is not owned`）。
- **重放**：纯计算层拒绝"同档二次领"；事务层同键重发走**收据回读**，回执与首次逐字段相同。
- **满包**：`inventory.Awarder` 报错 ⇒ 事务回滚 ⇒ **不写"已领"标记**（不消费资格）。
- **激活**：`arad-pass-activate-v1` 幂等键；`Royal` 已为真时纯计算层**零写入**返回（购票经验不翻倍）。
- **任务**：`arad-pass-mission:clear:<runID>` 幂等键；周计数/周上限按 `WeekKey`（ISO 年-周）跨周清零；
  只有**真的做满一条任务**才追加 0x08A1 刷新帧。

> 来源里那些**硬编码上界**（`next194 §23.3(2)` 点名的坑）逐条查过：本移植里
> `Claimed` 是 map 键、任务计数按源里的 `Count` 走、奖励表按 `RewardAt(track, slot)`
> 精确匹配 —— 没有"长度上界导致整条被静默拒绝"的写法。

**(c) 反汇编（L0）** —— headless IDA（`D:/tools/ida94/idat.exe`），脚本
`analysis/tools/ida_probe_aradpass_2209.py` / `ida_probe_aradpass_2210.py` /
`ida_probe_registry_map.py`：

| 事实 | 证据 |
| --- | --- |
| handler 登记 | 扫三个注册助手：**2209 → `sub_14229E480`**、**2210 → `sub_14229E3F0`**（`probe-registry-map.txt`）|
| `516` 是客户端内部的通行证对象 id | **两个** handler 都 `sub_145693930(singleton, 516)` 取同一个单例 |
| 2209 正文 = **760 B** | 缓冲在 `obj+0x7D0`，2210 缓冲在 `obj+0xAC8` ⇒ `0x7D0+760 == 0xAC8` **严丝合缝** |
| 2210 正文 = **1104 B** | `sub_146EA0BE0(a1+0xAC8, 0x450=1104)` |
| 任务行起点 | 普通行 `obj+0x7EB`（= +**0x1B**）、赛季行 `obj+0x8BE`（= +**0xEE**）—— 与文档偏移**完全一致** |
| 收行循环 | `cmp byte ptr [row], 0 / jz 停` ⇒ **序号字节写 0 会让后面所有行被丢掉**；循环上限 30 |
| 行宽 7 B 的字段 | 拷贝是 4+2+1 字节；"变化检测"只读 **u16@+3** 与 **u16@+5** |
| 2209 解析函数**只**碰这些偏移 | `+0x7D0`(缓冲) `+0x7D4`(等级 = body[4]) `+0x7EB` `+0x8BE` ⇒ 保留区（0x8B…、0x142…、0x1C3…）**没有任何读者** |
| 2210 的 55B 记录字段 | `sub_1422A1770`：`u8@+0`、`u32@+1`（两者是红黑树键）、`u32@+5`=**charID**、`u32@+9`=种类(1/2/3)、`u8@+15`=标志、`u32@+17` |
| 记录"算不算存在" | `if (u8@0 \|\| u32@1 \|\| u32@17)` —— **三者全 0 的记录被整条跳过**（哪怕 charID 有效）|
| ★ 客户端会**主动发 681** | charID 解析不出角色时：`681, 516, 7, u8@0, u32@1` ⇒ **681 = "问服务端要这条记录"**，不是领奖（我们当初"681 不发奖"的判断**正确**）|

> 顺带修掉一条**错误的自以为**：上一轮那个"已购皇家候选字节 0x20"其实**落在任务行区里**
> （0x1B..0x8A），永远会被任务行覆盖 ⇒ 用例已改到真正的保留区 `0xC0`。
> 教训：写"候选偏移"时必须先核对该偏移**属于哪一段**。

### 10.2 三处修正

## 12. 第四轮：Receive All + "买好了"的回调排查（2026-10-11 01:4x）

### 12.1 ★ 客户端真的发了领奖帧，而且是 `slot == 0`

```

          = 事件 516, 轨道 0, 槽 0, 保留 0

```

抓包里那次成功领奖是 `516, 0, **1**, 0`（槽=1）。⇒ **槽 0 = 通配**（面板右下角的

### 12.2 "买好了"的回调在哪里（业者的直觉很准，但结论出人意料）

- 全库 `opcodes.tsv` 里带 `ARAD_PASS` 的只有 **6 条，全是 `noti`（S2C）**：
  1885/1886（旧家族）、**2209/2210（我们在用）**、2318（CHARAC_DETAIL）、2428（EVENT_CHARAC_DATA）。
  **没有任何 c→s 的"购买"命令** —— 购买动作完全在 Web 端完成。
- ★ 2318/2428 **在本客户端根本没注册**：扫三个注册助手，它们的 opcode 一次都没出现
  ⇒ 枚举名来自别的构建，**发了也没人收**（所以别再往这个方向加包）。
- ★★ 但**客户端自己有一条"要数据"的出口**：`sub_1422A1770` 的 `else` 分支 ——
  当某条 2210 记录的 `charID` 解析不出角色时，客户端会发
  **`681 : 516, 7, u8@0, u32@1`**（注释里记过）。这就是"服务端告诉我这条记录是什么"的回路。
  ⇒ **"买好了"不是靠一个新的 opcode，而是靠 2210 记录本身**；面板的
  `Royal Pass Character(n/10)`、Royal 轨的锁，都读这份记录。

## 20. ★★ 结案：两条轨的"已领"标记在**两个不同的基址**

### 20.1 定案布局（0x08A1 正文，**每档 1 字节**，非 0 = 已领）

| 轨 | 档数 | 基址 | 实机证据 |
| --- | --- | --- | --- |
| 普通（Free）| 25 | **`0x1C2`** | Lv1/3/5/7 与 Lv5/7/9/11 两轮共 8 格吻合（含负例）|
| 皇家（Royal）| 25 | **`0x28A`** | 窗口计数法二分 + "连尾部都亮"判据（见 20.2）|

**两段不相邻** —— 早先按"普通 25 字节之后紧跟皇家"写的 `0x1DB`/`0x1F4`、以及"紧挨在普通之前"的 `0x1A9`
**全部不亮**，这三个反例是定位过程中最关键的排除。

### 20.2 `0x28A` 是怎么钉死的

1. 宽扫（`1DB-2F7` + `142-1C1` + `8B-EC`）**点亮全部皇家格** ⇒ 标记确实在正文里；
2. 用"已打过一定重叠就至少亮一格"反推候选基址 ⇒ 收敛到三段，其中 C∪B 同打**不亮** ⇒ 在 A 区；
3. 100 字节窗口 `20D-270` 全 Get ⇒ `B > 0x270`；25 字节窗 `271-289` 全 Get ⇒ `B ≥ 0x28A`；
4. "打 `X..末尾`"⇒ `2B5-2F7` 全 Get ⇒ `B ≤ 0x29C`；
5. 回到 25 字节窗 `28A-2A2` ⇒ **全部 Complete**。25 字节窗只能覆盖 25 个基址，
   而"**连第 22..25 档都亮**"只在**数组起点恰好等于窗口起点**时成立 ⇒ **`B = 0x28A`**。

### 20.3 落地（不再依赖任何环境变量）

| 改动 | 内容 |
| --- | --- |
| `protocol.aradPassOffsetClaimedNormal = 0x1C2` / `aradPassOffsetClaimedRoyal = 0x28A` | 两条轨各自的标记基址；`aradPassClaimedPerTrack = 25` |
| 编码器 | `ClaimedSlots`（索引 0..24 普通、25..49 皇家）**按轨拆写到两个基址**；调用方不需要知道布局 |
| 挪位开关 | `DFO_ARAD_PASS_CLAIMED_OFFSET` / `DFO_ARAD_PASS_CLAIMED_ROYAL_OFFSET` |
| 用例 | 断言普通写在 `0x1C2`、皇家写在 `0x28A`、且**皇家不写 `0x1C2+25`**（那个位置实机证明不亮）|
| `调试启动-本地构建.cmd` | 临时诊断块**已删除**（只留 ASCII 说明注记），复验 4932 字节纯 ASCII、`set` 只剩 DEV/RC |

### 20.4 方法论沉淀（这一轮最值钱的三条）

1. **"非零位数"与"点亮格数"对不上时，先怀疑容器类型**（位图 vs 每档 1 字节），别急着调索引公式；
2. **窗口长度取"数组长度"时，结果永远可解**：亮的格数直接给出基址（`B = X + 25 − N`），
   且亮的永远是**最低等级**那几格 ⇒ 不用滚动；
3. **"打了候选区却不亮"本身就是信息**：用"已打过的窗口必须重叠过数组"反推剩余候选基址，
   比盲扫快一个数量级。"

## 21. ★★ 结案：任务行三字段实机定案 —— 进度在 `@+1`，不是 `@+3`

### 21.1 判别探针一轮读出全部字段

探针（`DFO_ARAD_PASS_MISSION_PROBE=1`）给**每一行**写三个互不相同的哨兵
（`@+1=41`、`@+3=42`、`@+5=43`），面板一次读出：

| 面板列 | 探针下的显示 | 结论 |
| --- | --- | --- |
| `n / m` | **`41 / 100`**（另有 `20 / 20`、`5 / 5`、`4 / 4`、`3 / 3`）| **`@+1` = 进度**；客户端**按脚本目标截断**（41 在目标 20/5/4/3 的行上显示成满值）|
| `k time(s)` | `43 time…` | **`@+5` = 完成次数** ✓（原来就写对了）|
| `Total` | `420` | **`@+3` = 累计经验**（非 0 时状态列还会变成 **Completed**）|

⇒ **根因**：第一版把"进度"写在 `@+3`（那其实是累计经验），而客户端读的是 `@+1`
⇒ 任务页永远 `0 / m`。这也解释了为什么"数据明明是对的"却显示不出来。

### 21.2 落地

| 层 | 改动 |
| --- | --- |
| `protocol.AradPassMissionRow` | 字段改为 `Progress`(@+1) / `TotalExp`(@+3) / `Times`(@+5)，并删掉那个"保留"字段 |
| `aradpass.MissionProgress` | 增加 `Exp`（源 `<次数> <经验>` 的后者），供调用方算 `Total` |
| `cmd/wireprobe` | `TotalExp = Times × Exp`；探针哨兵常量改名 `aradPassProbeProgress/Total/Times` |
| 用例 | 断言进度写在 `@+1`、`@+3` 为累计经验、`@+5` 为次数 |
| `调试启动-本地构建.cmd` | 诊断块撤掉，并把累积的多段注释**合并成一段 ASCII 结案注记**（4414 字节，`set` 只剩 DEV/RC）|

### 21.3 顺带确认的显示规则

- `n / m`：`n` 由 `@+1` 给出，**客户端自己截断到脚本目标** ⇒ 服务端不需要自己截；
- 状态列：`In progress` → **`Completed`** 的切换由 `@+3`/`@+5` 的非零值驱动（"完成过"这件事）；
- `Total` = `@+3`（累计经验），我们的模型是 `次数 × 单次经验`。

## 26. ★★ 每日礼包「已领」的闸门找到了：`body[0x1C0]`（2026-10-11，IDA 静态）

### 26.1 先排除一个假线索：`+1768h` / `+176Ch` 是**点击防抖**，不是已领态

发送点 `sub_14235DAF0`（就是那个发 `680(516,3)` 的分派 case）里的两条判据读的是
`[rdi+1768h]`（一个结构体的起点）和 `[rdi+176Ch]`。反编译 `sub_146E9FA80` 后看清了：

```c
// sub_146E9FA80 —— 通用「条件求值器」，不是战令专用
v2 = *(DWORD*)(a1 + 4);
if ((v2 & 3) != 3)              return *(DWORD*)(a1 + 16) <= 0;
if ((v2 & 4) != 0)              return *(DWORD*)(a1 + 12) >= *(DWORD*)(a1 + 16);
if (*(DWORD*)a1 == 9999)        return (a1+8) + 动态值 >= *(DWORD*)(a1 + 16);
return (a1+8) + sub_146EA8FC0() >= *(DWORD*)(a1 + 16);
```

而发送成功后紧接着 `sub_146E9FBD0(&a1[149].retval, 1000, 0)` —— **把该结构重置为 1000ms 冷却**
⇒ `+1768h` 是「这次点击的节流器」。**不是"已领"**。

### 26.2 真正的闸门：`sub_1422A07B0(passObj) == 0`

发送点的完整前置：

```c
if ( sub_14229E570(v42) == 2                       // 2209 正文[0] == 2（已购）
  && sub_1422A07B0(v43) == 0                       // ★ 这才是"能不能领"
  && (HIDWORD(a1[149].retval) & 2) != 0            // 节流器 bit1
  && sub_146E9FA80(&a1[149].retval) == 1 )         // 节流器已过冷却
{ 发 680: 516, 3 }
```

`sub_1422A07B0` 是 thunk，真身在 `sub_1422A0940`：

```c
char sub_1422A0940(__int64 a1)   // a1 = 战令对象
{
  if ( *(DWORD*)(a1 + 2000) != 2 )                 // 2000 = 0x7D0 = 2209 正文起点
    return 1;                                      // 没买皇家 ⇒ "别领"
  ...
  v5 = *(QWORD*)(a1 + 72);                         // 事件管理器
  if ( v5 != 0 && sub_147619FF0(v5, &word_14E651FB0, 1) != 0 )
    // word_14E651FB0 = u16（表查出来的）
    return (u8)word_14E651FB0 + *(u8*)(a1 + 2750) <= *(u8*)(a1 + 2448);
  else
    return ...;
}
```

换算成正文偏移（正文基址 = 对象 `+0x7D0`）：

| 表达式里的对象偏移 | 正文偏移 | 含义（推断） |
| --- | --- | --- |
| `a1 + 2000` | `0x000` | u32 头 == 2（已购） |
| `a1 + 2448` | **`0x1C0`** | ★ **上次领取的"日"（u16，0x1C0..0x1C1）** |
| `a1 + 2750` | `0x2EE` | 另一个 u8（同日内的补偿/计数位） |

`sub_147619FF0(manager, out, 1)` 是一张 **map 查表**（按 dword 键 = 1 找节点，
读节点的 `+0x20` u16 与 `+0x22` u8）。那个 u16 来自**活动表**（运营数据）⇒
语义上是"**今天该是多少**"。

⇒ 合并读作：

```
word(今天) + body[0x2EE]  <=  body[0x1C0](上次领取日)   ⇒ 客户端**连包都不发**
```

**这就是"一天一次"的实现方式**：领过之后 `body[0x1C0]` 被写成当天的值，
当天再点就被自己的闸门挡住。**我们一直把它写成 0**，所以客户端永远认为"还能领"。

### 26.3 为什么这也解释了面板：一个谓词两处用

同一个 `sub_1422A07B0` 既是**发送前的门禁**，也（几乎必然）是**面板画按钮时读的状态**——
官方客户端不需要第二套状态。所以把 `body[0x1C0]` 写真，按钮与门禁一起变。

### 26.4 一次重启即可判定（探针已就位，未改一行业务代码）

`调试启动-本地构建.cmd` 里已把诊断换成**单变量**：

```
set DFO_ARAD_PASS_BODY_POKE=1C0-1C1:255
```

（`0x1C0/0x1C1` 不在探针的**保护段** `04-17/1A-8A/ED-141/1C2-1C8` 里，能写进去；
`1C0-1C1:255` 把那个 u16 置成 `0xFFFF` ⇒ 强制走"已领"那一支。）

判定读数是**双通道**的：

| 观察 | 结论 |
| --- | --- |
| 面板那行变"已领/不可点" **且** 点击时服务端**不再出现**任何 `arad_pass_request*` 日志 | ✅ `body[0x1C0]` = 闸门，按"已领日"实现即可 |
| 面板仍显示 `Get`，但点击时服务端**也没有**日志 | 闸门确认，但**按钮文案另有来源**（需再找显示侧） |
| 面板与日志都不变（点击照旧发包） | ❌ 推断不成立，回到 2209/2210 的其它字节 |

### 26.5 已落地的实现方案（等 26.4 确认后再改代码）

`AradPassProgress` 增一个 `RoyalDailyDay uint16`（正文 `0x1C0..0x1C1`）：

* 当天已领 ⇒ 写 `0xFFFF`（**不需要知道官方那个 day 的刻度** —— 只要保证
  `word + body[0x2EE] <= body[0x1C0]` 恒真，就能让客户端认"已领"）；
* 跨日 ⇒ 写 `0`，闸门自动放开。

即**用"饱和值"表达已领**，避开"日序号刻度未知"这个唯一的不确定点；
`RoyalDailyKey`（`state.go` 里已有的 09:00 UTC 换日键）正好是这一位的真值来源。
