# next202 — 奥拉蔻 685：生产打通后的「面板费用显示」修复（2026-10-12）

> 前置：`next201-奥拉蔻史诗装备模块研究-权威规格-20261012.md`（权威规格 / PVF 证据 / 帧清单）。
> 本文只记**生产链路打通之后**业主实机发现的最后一个数字问题，以及顺带修掉的一个流错位隐患。

## 0. 一句话结论

业主实机：「生产可以连续成功，但面板下方的材料计数显示 **10010**，这个应该是消耗吧（疑似偏移读错）」。

根因**不是偏移读错**，而是服务端把 2806 里的「本周已产次数」**硬编码成了 1000**：

* 面板/按钮上那个数字 = `ProductionCostFor(produced)` = `基准 × (produced + 1)`，基准 = 10；
* 1000 ⇒ 10 × 1001 = **10010**；
* 改成下发**角色存档里的真实 `produced`** 之后即为 `10 × (produced + 1)`。

⇒ 同一公式、同一个字段，只是喂进去的是占位常量而不是真值。

## 1. 量化证据（来自实机会话，不是推断）

最后一次成功会话：`runtime/roles_persist_select_actor_town_world_live_detail_dungeon_manual_20261012_180633_694982_next37`

```
oracle_production_done  cost=510  produced_after=51  module=590015756  result_item=590015809 x5
oracle_production_done  cost=520  produced_after=52  module=590015757  result_item=590015809 x5
oracle_production_done  cost=530  produced_after=53  module=590015758  result_item=590015809 x5
```

* 第一条 cost=510 ⇒ 生产前 produced=50 ⇒ `10 × (50 + 1) = 510` ✓（与 `ProductionCostFor(n)=10×(n+1)` 完全吻合）
* 而面板显示 10010 = `10 × (1000 + 1)` ⇒ **面板读的就是 2806 里那个「已产次数」字段**，
  而该字段当时是硬编码 1000 ⇒ 10×1001 = 10010 闭环成立。
* 会话事件计数也一致：`sim_research_frames_local`=1（登录推了 2806/2809）、
  `sim_research_etc_sent`=4（登录 1 + 生产后 3）、`sim_research_inven_all_sent`=3（每次生产后 1）。

## 2. 根因与修法

`cmd/wireprobe/simresearch_flow.go :: simResearchEtcPayload`

2806 的 21 字节整块落到客户端 `obj+1240`；IDA 给出的对象布局：

```
[+1240 : 8B][+1248 : 4B][+1252 : 1B][+1253 : 4B][+1257 : 4B = 2]
```

其中 `+1244`(= raw[4:8]) 与 `+1253`(= raw[13:17]) 就是客户端算这个数字用的字段。旧代码两处都写死 1000（占位）。

**修法（只填真值，不猜解释）**：`simResearchEtcPayload(produced uint32)` 把两处 dword 都写成真实 `produced`；
`raw[17:21] = 2` 保持不变（它与客户端 handler 自己的默认值同源）。

两个调用点：

| 调用点 | 取值 |
| --- | --- |
| `simresearch_actions.go`（2412 生产成功后推 2806） | `producedAfter` = `receipt.Produced`（服务端扣费/推进后的事务结果） |
| `client_entry.go`（登录时推 2806） | `oracleresearch.ReadState(role.State)` → `.Normalize(WeekStartOf(now))` → `.Produced` |

⇒ 生产后与登录后都由**同一个真值**驱动，不再有第二处口径（本仓的老教训：同一笔数据别判两次、判错一次）。

## 8. ★★★ 追加（同日 20:1x）：IDA 实证了「费用公式」，但**我们的字段没生效**

> 业主复测：**仍是 10010**，且右侧图鉴/格子打开时也不显示。以下全部是实证，不是推断。

### 8.1 面板那个数字的**确切公式**（从 IDA 反编译读出）

`sub_1404255D0`（被面板刷新 `sub_1406169B0` 调用）：

```c
if ( (*(_BYTE *)(a1 + 1064) & 1) == 0 || (…向量 a1+112..a1+120 为空…) )
{
    if ( (*(_DWORD *)(a1 + 1064) & 0x20) != 0 )
      return (unsigned int)*(unsigned __int16 *)(a1 + 476) * (*(_DWORD *)(a1 + 1253) + 1);
    else
      return 0;
}
```

⇒ **面板数字 = `u16@(evObj+476) × (u32@(evObj+1253) + 1)`**，`evObj = *(QWORD*)(win+1856)`
（`sub_1406169B0` 里：`if (*(u32*)(evObj+1240)==0) *(u32*)(win+2396)=3;`）。

10010 = 10 × (1000 + 1) ⇒ 画的那一刻 **`evObj+1253` = 1000**，不是我们送的 53。

### 8.2 关键事实：`evObj+1253` **只有 2806 一个写点**

* 2806 handler `sub_1404243D0(a1,a2)`：`sub_146EA0BE0(v4,21)` → `qmemcpy(a2+1240, v4, 21)`
  ⇒ 我们的 `raw[13:17]` **就是** `evObj+1253`。
* 位移扫描（`0x140423000-0x140428000` + `0x140600000-0x140630000`）里 `+4E5h]` 命中 6 条，
  **全是读、没有一条写**。⇒ 除 2806 外没有别的写点。
* 2412 handler `sub_140423D90` 只把应答第 2 个 u32 交给 `sub_140613BE0` → 写 **`win+2392`**，
  **不写** `evObj+1253`。⇒ **生产多少次都不会改这个数字**，与业主观察完全一致。

⇒ 结论：**我们登录时推的 2806 没有落到 `evObj` 上**。候选原因（尚未定案）：
① 派发器给 NOTI handler 的 `a2` 不是窗口 3956 挂的那个 evObj（NOTI 走**注册表**，IDA 里
   对 `sub_1404243D0` / `sub_140424460` **没有任何代码 xref**，无法静态确认）；
② 登录时 evObj 还没挂上 `win+1856`；
③ 2806 这个 noti id 的注册映射与我们的理解有偏差。

## 9. 追加（同日 21:2x）：PID 追到「对象归属」，仍**没有**一个写点能产生 1000

业主复测（21:16 那一局，客户端与服务器**一直在跑**）：点了一次 Produce，**数字仍是 10010**。

### 9.1 面板那个数字的控件找到了

`itemCreation.xui`（Produce 那一页，main.xui 用 UIContainer 引它）：

```xml

```

⇒ **就是它**（全页唯一的 `%d`）。**xui 里没有 10010**，所以它是代码算出来的。

### 9.2 全库确认：`evObj+1253` 只有两个写点

`grep` 全库反汇编里 `+4E5h]`（= obj+1253）共 **14** 条，其中**写**只有：

| 写点 | 位置 | 写的值 |
| --- | --- | --- |
| `mov [rdi+4E5h], ebp` | `sub_140422640`（685 子系统**构造函数**） | **0** |
| `movups [rbx+4D8h], xmm0` | `sub_1404243D0`（2806 handler，16 B 整块） | 我们 payload 的 `[13:17]` |

其余 6 条是别的类的**字节**写（`mov byte ptr [r14+4E5h], 0` 之类），不可能是 1000。
⇒ **除「构造置 0」与「我们的 2806」外，没有任何地方能把 1000 写进 `+1253`。**

### 9.3 构造函数把 21 字节块的默认值交代得很清楚

`sub_140422640`（685 对象的 ctor，0x140422640）：

```c

*(_DWORD *)(a1 + 1248) = 0;
*(_BYTE  *)(a1 + 1252) = 0;
*(_DWORD *)(a1 + 1253) = 0;     // ← +1253 默认 0（不是 1000）
*(_DWORD *)(a1 + 1257) = 2;     // ← 与 2806 自己的预填 [17:21]=2 同源
```

**⇒ 若 `+1253` = 0，面板就该显示 `u16@476 × 1`；脚本 `[cost]` = 10 ⇒ 应该显示 10。**
（`+472` 由脚本填成材质号 590015808 —— 这正是面板 "Owned Energy: 46,790" 与背包里
`590015808` 的数量**逐位相同**的原因，反证脚本数据确实进了这个对象。）

⇒ **10、550、10010 三个数里，能产生 10010 的只有 `+1253` = 1000**，而 9.2 说没人能写 1000。
⇒ **唯一自洽的结论：我们推的 2806 没有落到「面板读的那个对象」上。**

## 10. ★★★★ 真正的根因（2026-10-12 21:5x）：**是我们自己留的环境变量**

### 10.1 铁证

## 20. ★★ 神秘能量根本不掉的**真正根因**：装备判据查错了目录（2026-10-13 00:1x）

业主："我打了好几轮没有掉落这个神秘能量材料。" 查日志（会话 `…20261013_000708…`）：

### 20.1 根因（静态确认，不是推断）

`ExtraDropRewards.AwardsFor` 的装备判据是：

```go
item, ok := items[d.Template]            // items = LootCatalog.Items
if !ok || item.Kind == "stackable" { continue }   // 「只算装备」
```

而 `LootCatalog.Items` 是怎么来的：

* `internal/catalog/loot.go:232` —— `LootItem{Kind: "stackable", …}`（**硬编码**）
* `internal/catalog/item_index.go:114` —— 同样 `Kind: "stackable"`

⇒ **掉落目录本质是一张"堆叠物 + 掉落表"表**，装备（`10xxxxxxx`）要么不在里面、要么 `Kind` 就是
`"stackable"` ⇒ 上面那行判断**永远为真** ⇒ **装备一件都被 `continue` 掉、能量永远发不出去** ——
不只是这个副本，**任何副本都不会掉**。

### 20.2 修法（binary `cf2c484d…`）

装备的「是不是装备 / 稀有度」改用**装备目录**判：`EquipmentCatalog.DropPool()` 的每条正是
`{ID, Grade, Rarity, Durability}`（`Rarity` 直接读装备脚本的 `[rarity]`）。

1. `loot.Session` 建会话时把 `DropPool()` 折成 `map[模板]稀有度`（**每局一次**，不在每次怪死时重算）；
2. `AwardsFor` 多收一个 `equipRarity` 参数：**先按它判装备**，查不到才退回旧路径（掉落入库且非堆叠）；
3. 顺手加**诊断标记** `extradrop1093_scan:eq=<装备件数>,stack=<堆叠件数>,unknown=<两边都查不到>,awarded=<给的能量>` ——
   以后"匹配了却没给"能一眼看出卡在哪一类（这轮就是因为只有 awarded 标记、没给时是静默的，才多绕了一轮）。

单测：`./internal/loot`、`./internal/extradrop`、`./internal/inventory` 全过；`go vet` OK。

Primeval 5）⇒ **normal / uncommon 档的装备按设计就是 0**。

所以看 `extradrop1093_death` 的 `skipped`：

| 现象 | 判定 |
