## 0. 结论（先看这个）

**推荐：HoneyTime（活动 **313**，2026/0326 那一期脚本）。**

- 它是「累计在线」最直白的形态：**在线 10 / 20 / 30 / 60 分钟各发一档**，每天重置（`[reward type] \`daily\``）。
- 脚本属于 **2026-03-26 批次**，与刚打通的 331 同批 ⇒ op108 表里补一行即可，奖励**走邮件**（复用 `SendSystemMailWithCharacterUpdate`）。
- 领取大概率走**通用 op680**（与 331 同一条：`u32 活动号 + u32 行号`）——「行号」正好是那 4 个时间档。

**必须先证伪的两点**（⇒ 第一件事是 M0 取证，不是写代码）：

1. ★ `[pc room event] \`true\`` —— 客户端可能只在「网吧模式」下开面板。要么找到不 gate 的方式，
   要么改用不带该标签的脚本（备选 **387**）。
2. ★ **状态帧的 opcode 与布局未知**（签到那次是参考文档直接给了 op1379/680，这次没有）。
   要从 `[control panel]` 串键 / 事件号定位类 → 类构造里的 NOTI 注册三连 → handler → 载荷布局。

**零协议成本的并行项**：把 op108 从「19/77」补到全量（尤其 ~30 条常开功能开关），见 §4。

工具：`analysis/tools/ida_probe_event_opcodes.py`（按立即数反查注册/引用）+

   ⇒ 找到 HoneyTime 类构造就能一次拿到 **状态帧 opcode 与 handler**。
2. **拿载荷布局**：反编译该 handler，读它开头的 `sub_...(buf, N)` 系列调用（331 的经验：`1 + 4 + 28 = 33` 就是这么定下来的）。

**已知线索（本轮探针的副产品，别浪费）**：
`0x14004156b` 一带是一串**连续包 opcode 的 NOTI 注册簇**（`0x185=389`、`0x183=387` …，
都走 `qword_14E66C090` + `sub_14599D5D0`），handler 分别是 `sub_144EE4F20` / `sub_144EE4E80`。
⚠️ 注意「**opcode 387**」与「**活动号 387**」是两个不同的东西 —— 我这轮探针就是在

## 7. M1 探针已就绪：108 表里加了 313 行

### 做法与理由

**官服抓包（77 条）里没有 313** —— 那份表是 2026-10 那一期抓的，HoneyTime 当时不在线。
所以这一行是**按客户端的行长自己拼**的（新文件 `event_info_activity_constructed.go`），
与"逐字切片"的 331 严格分开：

- 行长与官方行**完全一致**：`u16 id, u8 present, u8 a, u8 b, str×3, u32 start, u32 end, str×2, u8 flag`；
- **四个串（s2/url/calendar/extra）一律留空** —— 按 `next192 §5 R1`，带 banner 或脚本串的记录是
  「选角屏崩」的风险面，探针阶段只开开关、不引资源；
- 窗口取脚本自己的 `[control panel]`（`2026-03-26 06:00:00 → 2026-05-07 06:00:00`，按 **KST** 折成 UTC
  ⇒ `1774472400 → 1778101200`；KST 的旁证见 331：`.evt` 写 09:00 而官服行 = 09:00 KST）。
  ⚠️ 客户端**不比较**窗口，所以它只是运营数据。
- 开关沿用既有的 `DFO_EVENT_INFO_ACTIVITY=off`（关掉即回到只有 331 的状态）。

### 自检

- 合并表 `rows 24 → 25`、`bytes 1583 → 1627`（+44 B = 这一行）。
- 用例：`TestConstructedHoneyTimeRowShape`（形状 + 取值 + **必须恰好吃掉整行**）、
  既有用例的期望行数改用 `activityEventInfoCount()`。
- `go build` / `go vet` / 定向用例全绿；exe sha `226bdf8b553cbc2b…`，

  （※ `honeyTimeEventStart` 在二进制里 **0 命中** —— 常量名不进二进制，这正是"自检只能数会进二进制的串"那条纪律。）

## 10. ★ 挡面板的回归：**1294 少了一个字节**（2026-10-10 10:37 定位并修复）

### 症状

业主实机：HoneyTime 本身**已经修好**（阶段退回 1、进度条正常走），但左上角多出一块
**Liberation Trace 面板**挡住 GET；而这块面板此前是被我们用 **NOTI398**（`displayValue=0`

### 根因链（三段，全部有证据）

1. **我把 1294 的载荷算成 80 字节，实际是 81。**
   漏的是 `#07` 那个 u8（写 `var_C4 + i`）：它**不只在 v8=2 读**——
   `0x1452d4c70: cmp ebx, 1 / jz loc_1452D4C7A`（块分支之后紧接着它），
   以及 v8>=2 那一支经 `jmp` 落到 `0x1452d4c75: cmp ebx, 2 / jnz` **也会走到它**。
   ⇒ v8∈{1,2} 各读一次。Hex-Rays 把这两条支路并成了 `if (v8 == 2)`，肉眼极易漏。
2. **少 1 字节 ⇒ 客户端读流游标越界。** 轨迹里：
   `[ETC] NETWORK>> PACKET OVERFLOW : ENUM_NOTIPACKET_HONEY_TIME_EVENT_INFO`
   ⇒ 客户端回 **CMD217 `ENUM_CMDPACKET_OVERFLOW_INFO`**；我们服务端收到的载荷是
   `000e050000000000`，其中 u32 = **`0x50E` = 1294 本人** —— 点名了。
   判据来自本仓既有文档：`docs/protocol/noti2639-row-width-authoritative-20261007.md` §2
   「**`PACKET OVERFLOW` 的成因是读不满、游标越界，不是帧太长**」。
3. **溢出后客户端丢弃当前 TCP 段里剩下的帧** ⇒ 紧跟 1294 发出的 **NOTI398 被吞** ⇒
   Liberation Trace 面板复活。服务端日志显示 398 **确实发出去了**（`booster_gage_hidden`
   `plain_bytes=14`），所以问题不在我们没发，而在它被客户端丢了。

### 修法

| 文件 | 改动 |
| --- | --- |
| `internal/game/protocol/honey_time115.go` | `NotiHoneyTimeEventInfoBytes` **80 → 81**；偏移表整体顺移（@47 之后每个字段 +1）；文件头写清「为什么是 81 不是 80」与完整证据链 |
| `internal/game/protocol/honey_time115_test.go` | **写死 81** 的断言（谁"简化"回 80 立刻红），注释里带那条 OVERFLOW 证据 |

### ★ 教训（比结果值钱）

**按 handler 重建载荷长度时，必须逐条核对循环边界的反汇编**（`cmp`/`jz`/`jnz`/`jl`），
不能只看 Hex-Rays 的 if/else 嵌套 —— 它会合并支路，漏一次迭代就**只少一个字节**，

## 12. 「GET 点了没反应」定论：服务端**没有**拒绝，是**根本没人受理**（2026-10-10 12:0x）

`sub_143CC72A0(obj, 档, 秒)` 里取奖励行表的代码（逐字照抄，注释是我们的）：

```c

sub_146E9FBD0(a1 + 80*档 + 104, *(u32*)(v23 + 21*v24 + 12));   // 下一行的阈值 → +104
```

| --- | --- |
| **行表** | **21 字节/行**（不是 24 —— 24 那套是 `sub_143CC7740` 夹序号用的**另一张**表，按档索引） |
| **阈值语义** | **每档时长**（逐行相减）⇒ 四档的**累计**门槛 = **10 / 30 / 60 / 120 分钟**（600/1800/3600/7200 s）。实机 17 分 35 秒时客户端发第 1 档 ✓ 与业主看到的"进入第二阶段、第 1 档可领"完全吻合 |

| **对应奖励** | 行号 `k` ⇒ 奖励 = `field0 == k-1` 的那一行（`k=1` ⇒ 第 1 行 ⇒ `10414136`，即 10 分钟档 ✓） |

## 19. ★★ 期间轨点不动的真因：**「标志」字节没写 = 整档被 UI 跳过**（2026-10-10 17:1x）

### 19.1 现象与证据

业主实机：日档一切正常，**面板下面那行（期间轨）点不动**。查本次会话推的 1294：

```
@0  39010000        313
@4  d7100000        4311      ← 日档秒数
@8  03              3         ← 日档"已领 3 个"
@9  01 01 01 00…    块[0..2]=1（日档 3 档已领）
@25 00              ★ 第 1 条轨的**标志 = 0**
@26 c14b0300        216001    ← 期间轨秒数（刷库值，确实推出去了）
@30 00              第 1 条轨的序号
@64 03000000        日档"每档已领数"
```

秒数推对了，但**第 1 条轨的标志是 0**。而 UI 填表循环（`sub_1413808A0`）第一句就是：

```c
for (j = 0; j < 4; ++j) {
    if (*(_BYTE *)sub_143CC62F0(obj, j) == 0) continue;   // ★ 标志 == 0 ⇒ 整档跳过
    ...
}
```

`sub_143CC62F0(obj, j)` 返回的就是 `obj + 80*j + 96`（标志字节的地址）。
而 handler 里那个标志的初值是 `v22 = 0x01000101`（LE 字节 `01 01 00 01`），
**只有 v8 ∈ {1,2} 才从流里覆盖它** ⇒

| 轨 | 标志来源 | 服务端能不能控 |
| --- | --- | --- |
| 第 0 / 第 3 条 | **常数 1** | ❌ 关不掉 |
| 第 1 / 第 2 条 | 流里的 u8（@25 / @48） | ✅ **能开也能关** |

我们整帧全 0 发下去 ⇒ 第 1 条轨的标志 = 0 ⇒ **整档被 `continue` 掉**，那行的 GET 自然点不动。
（这也解释了为什么日档一直正常：它的标志是客户端常数 1，与我们发什么无关。）

### 19.2 修法

`honeyTimeSlotFlagOffsets = [4]int{0, 25, 48, 0}`（0 = 该轨在流里没有这一格），
`honeyTimeTrackByte` 在**该轨有进度时**（秒数或已领不为 0）把标志置 **1**；没有进度就留 0
（= 这条轨不参与，正好也是 PC 房那两条变种该有的默认态）。第 0/3 条轨一格都不碰。

用例：`TestHoneyTimeStateBodyWritesPeriodFlag`（有进度 ⇒ 标志必须 1；无进度 ⇒ 0；
并钉住"第 0 条轨不该有标志格"），另外把"只写选中那条轨"那条用例的守卫放宽到
"允许写该轨自己的标志字节，但仍不许碰到别的轨"。

`build` / `go vet` / `cmd/wireprobe` 的 honeytime 定向用例全绿；

**（4）NOTI108 的两条边角语义**（他们的 `event.go` 写得比我们细）：
