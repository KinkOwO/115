## 1. 奖励池写在 PVF 的哪里

在副本自己的 `.dgn` 脚本里（`script.cells`），蔚蓝号 `100004131` 的相关段落：

```ini
[disable clear reward]
[dungeon clear result]
  [reward card] 1                      ← 翻牌张数 = 1
  [result board]
[/dungeon clear result]

[difficulty dropitem group list]
  [group info]
    [item index]          10326880  10326884  10403423  10419054
    [normal group index]  2 21251   3 1 21291        ← ★ 奖励池的真身
    [fame info]           0 0
    [special setinfo reward]      185747957  320 10326880  1  21279
    [special setinfo reward]      185756985  320 10326880  1  21468
    [special setinfo reward]      185757035  320 10326880  1  21470
    [special setinfo reward]      185748005  138 10326880  1  21310
    [special custom reward info]  185278915  320 10326884  1  21293
    [reward multiple info]  2 10 9
    [reward multiple info]  3 4 3
  [/group info]
  [custom group info] …（第二组，内容同上）
[/difficulty dropitem group list]
```

- `[normal group index]` 的读法（`internal/loot/dungeon_group_index.go`）：
  `2 21251 3 1 21291` = 两段 —— **2 个模板、组 21251**；**3 个模板、组 21291**。
- `[item index]` 的 4 个模板（`10326880 10326884 10403423 10419054`）**语义未取证**，先记录。
- 5 条 `[special setinfo reward]` / `[special custom reward info]` 的**首列是 `type=8`（引用/哈希键）**，
  与我们此前在别的副本见过的形态一致 —— **语义未取证**，先记录。

## 2. ★ 奖励池的实际内容（用探针从源展开）

探针 `runtime/azurerewardprobe`（只读，打开内层 PVF → `ImportDungeons` + `ImportLoot` +
`SupplementItemIndex` → `loot.DungeonGroupIndices` → `DropGroupByID`）：

```
== dungeon 100004131 ==
   MinimumLevel=115 BasisLevel=145 RewardCard=1 NoFatigue=true
   难度档 0..3 都是同一组: [21251 3 21291]
      组 21251: 11 条（smart=11）      ← 115 级装备，11 部位，每件 w=10
        100051304 100101187 100151128 100201100 100251140 100301847
        100313550 100323440 100345985 100354160 100391038
      组 3:     792 条（smart=792）    ← 100 级大池，每件 w=300
      组 21291: 3 条（explicit=3）
        10362429  stackable/[material]             ← 深渊入场（Doom Oracle / 终末之启示）
        10362432  stackable/[material]             ← 迷雾工商协会银币
        10404337  stackable/[upgradable legacy]    ← ★ 沉月湖的接线里没有它

```

**⇒ 与沉月湖 `100004137` 的声明是同一对组**（沉月湖也是 `[normal group index] 2 21251 3 1 21291`）。

## 3. 与现有接线的对照（这是「重新梳理」的入口）

| | 沉月湖 100004137 | **蔚蓝号 100004131** |
| --- | --- | --- |
| 奖励池声明 | `2 21251 3 1 21291` | 同左 |
| 固定产出（材料） | `moonFixedRewards = {10362429:60, 10362432:15}` —— **代码常量**，组只用来交叉过滤 | **没有实现** |
| 随机装备 | `MoonEquipmentPolicy`（件数 1..4 权重 {1,3,3,2}、等级 115、rank 3）—— **代码常量** | **没有实现** |
| 发放 | `moonClaim` → `ClaimMoonReward` | **没有** |
| 现有包 | `moon_clear_reward(35)` + 翻牌 69/70/71 | 只有 `azureRewardSnapshot()` = **N1726/N537 的「还能领 255 次」次数快照** ⇒ 只是 UI 門面，**不含任何奖励内容** |

**⇒ 两个缺口**：

1. **蔚蓝号完全没有奖励发放**（只有次数表）；
2. ~~即便照抄沉月湖，那份「固定产出模板 + 数量」也是**代码里的运营值**，不是从源推出来的~~ ——
   源里确实**没有**「这次给几张」这种表（沉月湖注释已写明），所以数量只能由策略给定；
   但**「哪些模板算固定产出」应当由源决定**。

★ **一处已经能确定的差异**：组 `21291` 的第 3 个成员 `10404337`（`[upgradable legacy]`）
**没有**进沉月湖的固定产出 —— 这是**有意**的（`MoonSettleableStack` 明确把 `[upgradable legacy]` 列为不可结算）。
蔚蓝号接线时须沿用同一判据，**不要**为了"齐"把它塞进去。
