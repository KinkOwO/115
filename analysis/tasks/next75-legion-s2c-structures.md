# next75 — 军团 S2C 包体结构（X9 / X11 / X5 / X6 取证）

> 方法：这些是**服务端→客户端**的包，客户端没有"写入端"可读，所以结构只能从
> **消费端**反推。全部证据来自 `analysis/dumps/legion-noti-consumers/`
> （脚本 `ida_legion_noti_consumers.py` + `run-legion-noti.cmd`）。
>
> 每个 handler 的形态都一样，先记一遍这个**通式**，后面逐个包只是它的实例：
>
> ```c
> sub_XXXXXXXX():                     // handler
>     默认值写入本地缓冲（初值来自常量或一个小初始化函数）
>     sub_146EA0BE0(buf, N);          // 从包体读 N 字节，整块覆盖
>     把 buf 交给某个子系统（虚调用 / 全局单例 / 模式对象）
> ```
>
> ⇒ **本地初值只在"读不满"时才有意义**；正常情况下整个结构由包体决定。

| **7** | **4 (u32)** | **4** | 读完后取出 ⇒ `sub_142AC2220(modeObj, 值)` |

**三个"取出"字段是重点**：`sub_142AC2220` / `sub_142AC2290` / `sub_142AC21B0` 三者的形态一致 ——
`sub_142AB29C0(manager)` 取**模式键** → 在 `manager+312` 的红黑树里查命中对象 →
对命中对象发起**虚调用（槽位 +48 / +56 / +64）**，把值塞进去。

⇒ 这三个值进的是**模式对象**，也就是 `next73` §1 门禁⑤⑥读计数器的那个对象
（`(*(vt+624))(modeObj, 8)` / `(*(vt+640))(modeObj, 0)`）。
**因此 2895 很可能正是让军团入口门禁拿到非零计数的那一个包** —— 这是下一步最该验的假设。

⚠️ 仍未定：`@3`/`@7`/`@11` 的**语义**（哪个是周入场次数、哪个是周奖励次数），
以及 6 × 12 记录里 12 字节的字段划分。**未定之前不要按语义填值**；
但"发够 204 字节、三个字段给合法非零值"这一步已经不需要猜结构了。

## 3. NOTI2896 LEGION_OPERATION —— 7 B **内容会被丢弃**

```c
v1 = 0;  sub_146EA1920(&v1);           // 读 u16，必须 == 107
if (v1 == 107) {
    v2 = 0; v3 = 0; v4 = -1;           // 本地初值
    return sub_146EA0BE0(&v2, 7);      // 读 7 字节到本地
}
```

**`v2/v3/v4` 读完后再也没有被使用** ⇒ 这 7 个字节**读完即弃**。

⇒ **结论：2896 的载荷内容无关紧要，只有长度（≥9，且首 u16 == 107）是契约。**
这是本次少见的"零猜测可用"项 —— 剩下的未知只是**该在什么时机发**（需实机）。

## 4. NOTI2252 LEGION_BASIC_CLEAR_REWARD —— 7772 B 记录几何

初始化循环把两块记录场的**步长与字段偏移**都写出来了：

```c
v0 = 40;  v1 = &v6[27];
do {                       // 40 条 × 40 字节，起始偏移 0
    *(u64*)(v1-27) = 0;    // 记录 +0
    *(u32*)(v1-19) = 0;    // +8
    *(u16*)(v1-15) = 0;    // +12
    *(u16*)(v1+ 9) = 0;    // +36
    *(u64*)(v1-13) = 0;    // +14
    *(u32*)(v1- 5) = 0;    // +22
    *(v1-1)        = 0;    // +26
    *(u64*)v1      = 0;    // +27
    v1 += 40;
} while (--v0);
v2 = 140;  v3 = &v6[1627];
do {                       // 140 条 × 44 字节，起始偏移 1600
    （与上同样一组字段，相对 +1 基准）
    *(u32*)(v3+13) = -1;   // 记录 +40 —— 44 字节记录独有的尾字段
    v3 += 44;
} while (--v2);
memset(v6, 0, 7772);  sub_146EA0BE0(v6, 7772);
(*(vt+248))(modeObj, v6);      // 整块交给模式对象的 vt 槽 124
```

**几何**：`40 × 40 B`（0..1599）+ `140 × 44 B`（1600..7759）+ **12 B 尾**（7760..7771）= **7772** ✓

40 / 44 字节记录的**字段偏移**已定，但**哪个字段是物品 id / 数量仍未定**。

## 5. NOTI2253 LEGION_ADDITIONAL_CLEAR_REWARD —— 2405 B 记录几何

```c
v4[0] = 0;
v0 = &v4[28];  for (i = 60; i; --i) { 记录清空（步长 40，起始 v4+1）; v0 += 40; }

sub_146EA0BE0(v4, 2405);
(*(vt+256))(modeObj, v4);      // 模式对象 vt 槽 128
```

**几何**：`1 B` + `60 × 40 B`（1..2400）+ **4 B 尾** = **2405** ✓
（记录字段偏移与 §4 的 40 字节记录一致。）

## 6. NOTI2254 LEGION_ENTRY_CHARAC_INFO —— 256 B 槽位布局

```c
sub_1424FD050(v1);          // 初始化：7 槽 + 88 字节常量填充
sub_146EA0BE0(v1, 256);
sub_142ABF5E0(manager, v1);
```

`sub_1424FD050` 给出精确布局：

| 偏移 | 内容 |
| --- | --- |
| 0 .. 167 | **7 个成员槽 × 24 字节**；每槽字段：`u16@0`、`u64@2`、`u32@10`、`u32@16`、`u8@20`（+21..23 填充） |
| **168 .. 255** | **88 字节**常量填充（`xmmword_1491B4820` 重复：16×5 + 4 + 4） |

（旧文档写的"7×24 + 84 哨兵 = 252"**不准**：实际是 **168 + 88 = 256**。）

**槽位字段语义仍未定** —— 哪个是角色 id / 名字 / 职业没有写者可对照（X6 的阻塞点没变）。
但"7 槽 × 24 B + 88 B 常量"这一层结构现在是确定的。

## 7. NOTI2568 PREPARE_LEGION_ENTER_DUNGEON —— 16 B 分支条件

```c
*(__m128i*)v19 = xmmword_1494B7AE0;   // 16 字节初值常量
sub_146EA0BE0(v19, 16);
if (*(u32*)v19 != 0) {                // ← ① @0 != 0 走"另一条"分支
      ... sub_146D0CBA0(...) ...  HUD 文案 id 145
} else {
      v9 = *(u32*)(v19+4);            // ← ② @0 == 0 时看 @4
      if (v9 == 1) {
          sub_146D0D2A0(obj, *(u32*)(v19+12), v9);   // ← toggle（X5 点名的那个）
          sub_140BA40C0(...)
      }
      HUD 文案 id 182
}
```

⇒ 这解释了 `next64` X5 的"toggle 风险"：
**要把准备房间界面上出来，应当发 `@0 = 0` 且 `@4 = 1`**，`@12` 是传进去的参数；
`sub_146D0D2A0` 是 toggle，**发偶数次会把界面关掉**。

⚠️ 触发时机仍未闭环，所以仍**不发**（保持 X5 的"有意不做"）。
