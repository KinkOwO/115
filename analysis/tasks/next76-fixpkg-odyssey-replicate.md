## 3. 修复 ①：`[correction equipped level]`

### 现象与根因（包内口径，已复核）
客户端把该字段显示成「装备等级限制-5」，有效使用等级 = `[minimum level]` + 修正；
服务端 `WearableBy` 只看 `[minimum level]` ⇒ 「客户端放行、服务端拒绝」，
客户端把拒绝码 `0x0004` 统一渲染成「目标背包已满…」。

旁证：`internal/inventory/wear.go:117` 调 `WearableBy` 时传的是**有效等级**
（`state.Level`，持有 `PremiumConqueror` 时 +10），这正是「38 级 +10 = 48」的来源。

### 独立复核
- `protocol.CurrentItemRecordSize = 181`、`protocol.OrdinaryItem` 把 `expireTime` 写进 **`p[56:]`（u32 LE）**；
  `cashshop.MaxExpireTime = math.MaxInt32`。
- `inventory.EquipmentRow`（装备行工厂）**从不写偏移 56** ⇒ 该格恒为 0；偏移 56 的既有写入者只有
  可叠加物路径（`Bag.Rows`）与商城时效道具。
- 宠物脚本实测：`100991331`（`equipment/creature/100991331.equ`）`[usable period] = 7`；宠物的确走装备行。
- 全量装备目录（424,216 条）按生物族统计（取 `items.index.json` 里 path 含 `creature/` 的 3,798 个模板逐条查真值）：
  **3,552 只没有任何期限段（永久）**、32 只有数值 `[usable period]`（值域 1/7/15/30/60/90/100 天）、
  约 138 只走 `[expiration date]` —— 后者**值是绝对日期文本**（如 `2020-12-31 06:00:00`，cell `Type=6`），
  与「天数」不是一回事。⇒ 查表只认 `[usable period]` 且要求 `Type == 0`，否则会把日期文本当天数。

### 偏移 56 的单位：由实机钉死为「剩余秒数」（2026-09-23 晚，用户实机反馈）
首轮只补哨兵 `MaxItemPeriod` 后用户实测：**过期提示消失，但面板变成「过期时间:24856天」**。据此定性：
- `2147483647 / 86400 = 24855.597…` 四舍五入 = **24856**，与面板数字逐位吻合；
- 客户端文案 `Expires in : %d Day(s)`（dstr id **1057**，源文件 `PopupWindow\CNRDItemInfoWindow.cpp`），
  另有 `Expires in : %d H`（id 1058）——两条都是「剩余时间」口径；
- 若按时间戳口径（减当前时间），`2038-01-19 − 今天` ≈ **4138 天**，与实测不符 ⇒ 不成立。

⇒ 该格是**剩余秒数**，客户端只做 `÷86400` 显示天数、**不减当前时间**。这也解释了为什么「填个哨兵值」
能骗过过期判定却骗不过面板：两者读的是同一格。**校准公式：面板天数 = round(值 / 86400)**。

### 落地（修正后）
- `inventory.SetCreaturePeriodSource(fn)`：启动期由 `cmd/wireprobe` 在装载全量装备目录后注入
  `[usable period]` 查表（走 `EquipmentCatalog.Definition` → `Full`）；未安装时退化为修复前行为，不 panic。
- `creatureRowPeriod(template, stored, existing)` 取值优先级：
  服务端 `Period` > 行内已有非零值（`Record` 保留的实例字节，不覆盖）
  > 脚本 `[usable period] × 86400` > `MaxItemPeriod`（兜底；脚本不声明期限时该行文案不渲染）。
- 只动宠物行：`space == 7`（生物栏）与 `space == 3 && Slot ∈ [26,29]`（已穿戴的宠物本体与宠物装备）。
  装扮的期限走**行尾那个 u32**、普通装备无期限语义 —— 两者保持原样。

### 已知边界（有意不做，均已写进代码注释与 CHANGELOG）
- **不倒计时**：服务端不存颁发时间，每次下发都是完整的 `N×86400`。做成倒计时要记录颁发时间，
  而服务端并不真的到期回收，归零会让「显示已过期但仍能用」自相矛盾 —— 要做得连回收一起做。
- `[expiration date]`（约 138 只活动宠物）继续沿用兜底值：其值是绝对日期文本，换算语义未取证，不猜。
- 装扮礼盒路径把 `BagEquipment.Period` 直接写成 `MaxExpireTime`，若装扮脚本声明期限会显示同类大数值；
  该值还关系到客户端对「无限期装扮」的判定，需单独取证与实机，本轮不动。

① 客户端脚本原文里已不再引用该 ID；② 该 ID 在新版脚本中无 `[need material]` 上游用途；
③ 官方给出 old→new 映射段（本脚本 `[legacy info]`）。本次 ① 就不成立（脚本原文仍在用），
⇒ **不需要**改服务端，任何「好心替换」都会与客户端脚本脱钩。
