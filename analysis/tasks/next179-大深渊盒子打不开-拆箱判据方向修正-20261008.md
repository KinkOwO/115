# next179 — 大深渊「只出盒子且打不开」：拆箱判据方向修正（2026-10-08）

> 业主反馈（附玩家截图）：上一个大深渊 MR 之后，**只会出盒子、而且这些盒子无法打开**
> ⇒ 玩家掉不出装备。业主怀疑「是不是对齐掉落的时候把一些盒子重新封回去了」—— 判断正确。

## 1. 现象与对位

玩家截图里两条：

| 屏幕上的名字 | 应当是什么 |
| --- | --- |
| `New Disciple of Doom Chance Reward Void Soul ×5` | 虚无之魂 ×5（即开类，标记 `[instantly open]` ⇒ 已经是内容物 ✓） |
| **`Verge of Order Guaranteed Reward (Epic Entry) Epic Equipment`** | **`10419728`（史诗砝码的史诗档保证奖励）** ⇒ **应当代开成史诗装备**，实际落地成盒子 ✗ |

## 2. 根因：判据方向搞反了

上个批次（`next176 §19.3/§20`）把「拆不拆包装」的判据从硬编名单改成**源标记**，但方向选错了：

```
旧判据：只有带 [instantly open] 的才由服务端代开，其余一律原样落地（让玩家自己开）
```

`10419728` **既没有 `[instantly open]、也没有任何客户端开箱入口标记**（`[oath item booster]` /
`[lottery ani info]`）⇒ 被原样落地 ⇒ **客户端根本不提供打开入口** ⇒ 死盒子 ⇒ 玩家掉不出装备。

★ **关键推理**：**「源里没有某个标记」不能推出「玩家能开」**。要证明「玩家能开」，必须有
**客户端入口的正面标记**。`next176 §19.3` 当时自己也标了
「⚠️『玩家能开』这一步还需要一次实机确认」——这一步没做就上线了，于是漏了这个洞。

## 3. 修正

判据改成**反向**：**只有声明了客户端开箱入口的才原样落地，其余一律服务端代开。**

| 层 | 改动 |
| --- | --- |
| `internal/catalog` | `BoosterDefinition` 新增 `ClientOpenPath`，由 `declaresSection(cells, "[oath item booster]") \|\| declaresSection(cells, "[lottery ani info]")` 填 |
| `cmd/wireprobe/booster_flow.go` | `boosterBoxSource.instantlyOpenOnly` → **`serverUnwrap`**，两处条件（`RewardBox` / `Container`）都改成 `if s.serverUnwrap && def.ClientOpenPath { … }` |
| `cmd/wireprobe/bootstrap.go` | 装配处跟着改名 |

⇒ 现在：`10419728` 这类**两个标记都没有**的礼盒由服务端代开（内容物落地，玩家拿到装备 ✓）；
光辉意志（`10419718..10419739` 族里带 `[oath item booster]`+`[lottery ani info]` 的那些）仍然原样落地，
玩家自己在 UI 里开、看抽奖演出 ✓。

## 4. 测试

`cmd/wireprobe/booster_instantly_open_test.go` 改成
`TestServerUnwrapUnlessTheClientHasAnOpenPath`，三类各一例：

- `[instantly open]`（无客户端入口）⇒ 代开 ✓
- **两个标记都没有（`10419728` 这一类）⇒ 代开** ✓（旧判据下它是原样落地 —— 就是这次的事故）
- `ClientOpenPath`（光辉意志类）⇒ 原样落地，且必须同时满足「RewardBox 不认 / Container 不认 / Item 认」✓

## 5. 实机验收

- 打一场大深渊（史诗砝码）：地上应直接出现**装备/材料**，不再有开不了的盒子；
  尤其 `Verge of Order Guaranteed Reward (Epic Entry) Epic Equipment` 这个名字**不该再出现在地上**。
- 反例（应保留）：光辉意志仍以**罐子**形态落地，且能在客户端里打开（带抽奖演出）。
- 小深渊不受影响（那条路径本来就没启用 `serverUnwrap`，见 `border_reward_flow.go` 的逐场选择）。

## 6. 遗留

- 客户端开箱入口的**完整标记集合**只取证了 `[oath item booster]` / `[lottery ani info]` 两个 ——
  若日后发现某个仍打不开的盒子，先看它有没有别的入口标记（`[mulit open limit]`、
  `[booster message show item]` 等，见 next176 §19.3）。
- 「哪些盒子的内容物应当即开」这件事现在由**源标记**决定 ✓，不再有硬编名单（除 `payAsIsWrappers`
  那一条具名豁免，它有自己的依据注释）。
