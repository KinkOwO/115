# 重登装备升级箭头修复 —— 动态探针定位与登录序列补帧（2026-09-21）

> 任务编号 next47。问题：重登进城后，装备栏里**每一件本角色能穿**的装备都显示"↑ 更好的装备"箭头，
> 与真实强弱无关；换装或切图一次后箭头立即恢复正常。实机验证已闭环（2026-09-21 22:12）。

## 一、最终结论

**根因**：登录序列从未下发 **id-14 槽位更新报文**（`equipment_slots_updated`，载荷携带每个 worn 槽位的**物品等级**）。
客户端箭头判定走"等级比较"分支（`mgr->vtbl[0xAB8]` 返回值 vs 格子物品等级），该分支依赖槽位级等级数据；
数据缺失时比较退化 → 全部画↑箭头。

**换装为什么能自愈**：换装处理器（`equipment_flow.go`）在 `equipment_move_committed` 后会补发该报文 ×2，
客户端借机重建全部槽位等级数据 → 全局重估 → 箭头恢复正确。与"客户端自己请求的应答才有效"的早期判断吻合。

**修复**：`entry_flow.go` 在 `enter_gameworld_complete` 屏障后、worn 窗口刷新前，插入
`equipment_slots_updated_entry`（id-14，space 3 全套 worn 行，`inventory.EquipmentPayload(3, bag.Worn, false)`，
与换装路径同构建器同格式）。**实机验证**：进城仅剩青铜护腿 1 个箭头——它是全身等级最低装备，
该箭头是"可换更好装备"的真实提示（换下它后箭头消失佐证），其余 7 格误亮全部消失。

## 三、方法论沉淀（可复用）

本次前三轮"报文镜像"全部失败，最终由 **frida 动态探针 + 服务端取证差集** 一次定位。复用要点：

1. **报文镜像法的上限**：镜像"换装自愈序列"逐帧重放是自然思路，但换装序列包含 5+ 种报文，
   逐个试错成本高；且缺的那帧（slot-update）在外观上与 worn-window 刷新同 id-14，极易看漏。
   三次失败后应立即转动态验证，不要继续猜。
2. **frida 安全探针守则**（本次闪退与修复经验）：
   - **只挂函数入口**。两个钩子点相距 5 字节时内联蹦床互踩，格子重绘风暴下直接闪退；
   - 按 PID 附加（`frida.attach(pid)`），游戏进程按名/枚举可能因权限差异不可见；
   - x64 上下文无 `edx`，取 `rdx.toInt32() >>> 0`；新版 frida 无 `Memory.readPointer`，用 `ptr.readPointer()`；
   - 后台运行 stdin 立即 EOF，用**停止文件轮询**控制生命周期；
   - 高频调用必须**按返回值去重**记录（本次每秒数万条 Query，不去重 20k 上限瞬间吃光）；
   - 入口钩不触发不代表路径不存在（可能被内联），对象实例可从其他钩子的 RCX 参数拿。
3. **events.jsonl 差集对账**：runtime 会话的 `events.jsonl` 记录了每帧名字+明文 hex。
   把"自愈时刻"与"故障时刻"的**报文名集合做差集**，唯一缺失的报文就是修复点——
   本次差集只剩 `equipment_slots_updated ×2`，一次锁定。探针证明"箭头走等级比较分支"后，
   在报文里直接找携带等级的载荷（`0x3C/0x32/0x28`）即可闭环。
4. **动态+静态+服务端三方交叉**：静态解出 Query 语义（A/B 表对比）→ 探针证伪"NULL 分支"假设 →
   服务端差集补上最后一块。单靠任何一方都不够。
