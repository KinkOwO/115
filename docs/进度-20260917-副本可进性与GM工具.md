## 一、副本"点了没反应 / 进不去"——根因与修复

### 1.1 三个导入层根因（`internal/catalog/dungeons.go`）

服务端拒绝选图只有三种原因（`internal/dungeon/session.go`）：
`ambiguous source maze` / `no resolved source maze for requested quest` / `quest is not accepted`。
实测 3,200 个副本后定位到**三种 PVF 写法我们的解析器不认识**，它们把 maze 判废或把 quest 归属搞错：

| # | 写法 | 实例 | 旧代码行为 |
|---|---|---|---|
| 1 | 一个房间节点挂**多张地图** | 副本 86 boss 房给了 20314~20317 四张 | 按固定 4 格分组 → `len%4!=0` → **整张 maze 判废、rooms 归零** |
| 2 | `[start map]` / `[boss map]` 有**多组坐标** | 副本 92 的 `[start map]` 是 (1,4)(3,4) | 只接受恰好 2 个数值 → **整张 maze 判废** |
| 3 | `[boss map] = -1 -1` 表示**没有 boss 房** | 副本 20000 | 被当成"非法坐标" → 判废 |
| 4 | 标签是 `boss_selection_probability`（带权重随机 BOSS 房，`地图ID,权重` 交替） | `contents/2024/snk/.../farming_1.dgn` | 位置不识别 → 判废 |
| 5 | `[quest connection]` 第三格**不是 -1**（实测有 `-1` 和 `2`） | 副本 86 index5（9 房间的完整 maze） | 整张 maze 判废、`Quest` 留在 0 → **反而又造出**一张 `quest==0` 的重复 maze |

修法：
- `[map specification]` 改为「标签 + 坐标 + **1..N 个地图 ID**」，地图 ID 个数由下一个标签界定；
  多出来的地图存进新的 `DungeonRoom.Alternates`（运行时用第一张，其余同样导入地图目录，**源数据不丢**）。
- `[start map]` / `[boss map]` 取第一组坐标；`[boss map]` 接受 `-1 -1` 哨兵（映射为协议层的 absent `255/255`）。
- `[quest connection]` 第三格作为 `QuestFlag` 原样保留，不再因为 ≠ -1 就整张判废。
- 新增 `boss_selection_probability` 标签支持（偶数个 cell，`(地图ID, 权重)`）。

### 1.2 服务端选取策略（`internal/dungeon/session.go`）

原来"匹配到第二张同 quest 的 maze 就报 `ambiguous source maze`"——实测 **288 个副本**的 `quest==0` 有多张
（通常是不同难度/随机版本），这些图**玩家点了完全没反应**。

改为：跳过 `Pending` 非空的 maze，**按 index 最小确定性选取**；起始房地图缺失时退到同一节点的备选地图。

### 1.3 地图补缺（新增 `cmd/dungeonmaps`）

旧解析器把整张 maze 判废时，那些房间引用的地图**从未导入**地图目录，运行时就会
`start map not imported`。新工具只做**补缺**：

```
dungeonmaps -catalog configs/dungeons.full.json \
            -source runtime/pvf_source/Script.inner.pvf \
            -dry-run=false -output configs/dungeons.full.json.new
```

**关键约束：绝对不动 `source.checksum`。** 服务端用
`q.ConfigVersion == w.dungeons.Source.Checksum` 过滤可用任务
（`cmd/wireprobe/dungeon_flow.go`），校验和一变，**所有任务副本会立刻全部被拒**。

### 1.4 效果（对照实验，`cmd/dungeonaudit` 用真实 `dungeon.Select` 审计 3,200 个副本）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 普通选图（quest=0）可进副本 | 1,555 | **1,638** |
| maze pending | 1,386 | 1,090 |
| 房间总数 | 23,863 | 26,262 |
| 地图目录 | 16,042 | 17,270（+1,228）|
| **回归**（原本可进、现在不能） | — | **0** |

定向验证：

```
dungeon  86: OK  maze=0 rooms=9  start=[6 0] startmap=20307 monsters=7
dungeon  92: OK  maze=0 rooms=14 start=[1 4] startmap=95149 monsters=5
dungeon  93: OK  maze=0 rooms=13 start=[0 0] startmap=95165 monsters=8
dungeon  88: OK  maze=0 rooms=12 start=[0 1] startmap=22428 monsters=5
```

**仍未可进**的 1,562 个（均非回归）：
1,337 个是"只能走任务进"或地图来自外部表（次元裂缝/绝望之塔那类）；
170 个起始地图**不在 `list/map.lst`** 里（2019~2022 活动/团本包，源索引里就没有）；
34 个教程本（走教程路径）；18 个起始坐标对不上房间；3 个怪物队伍解析不出。

新增测试：`internal/catalog/dungeons_test.go`（6 个，覆盖上述五种写法与"未知标签仍要报错"）、
`internal/dungeon/select_test.go`（4 个，覆盖消歧/跳过 pending/备选地图/重复起始坐标）。

## 二、GM 工具重做（38 万件物品库 + 与游戏一致的汉化名 + 部位/等级/品级筛选）

### 2.1 两个"拿错文件"的根因

**(1) 物品名对不上游戏。** `runtime/l10n/names.zh.json` 是汉化流水线的**中间产物**
（90 版中文词典 + 术语逐词对照 + 机翻），**游戏根本不加载它**。
游戏真正显示的是**客户端内层 PVF 的 `string/*.uv.str` 文本表**。
实测前 20 万件里 **156,914 件（78.5%）两份表不一致**：

| id | 游戏里显示 | 旧表（错） |
|---|---|---|
| 101001153 | **太初之星 - 短剑** | 原始的星辰 - 短剑 |
| 10420343 | 太初之星 - 短剑升品书 | 原始的星辰 - 短剑 Promotion Scroll |
| 1 | 复活币 | 生命 Token |
| 15 | 装备品级调整箱 | Kaleido 礼盒 |

**连品级中文名也是错的**。任务书里那份 `common_rarity_0..8 = 普通/高级/稀有/神器/史诗/纪事/传说/神话/原始的`
来自同一份错表；客户端 `string/ui.uv.str` 原文是
**`0普通 1高级 2稀有 3神器 4史诗 5勇者 6传说 7神话 8太初`**
（与 `101001153` 品级=8 且游戏名叫"太初之星"自洽）。

**(2) 装备发不出去（`equipment absent from source`）。** 发布包里的
`configs/equipment.current37.json` 是 **3,174 行的精简版**，而服务端认的是 **19,955 行**那份
（两者 `source.checksum` 相同，都是 `7ef2db59`，可直接替换）。掉落目录同理
（发布包 `maximum_grade=20` / 服务端 130）。对齐后：

```
换之前： id=101001225  不可发放: equipment absent from source
换之后： id=101001225  可发放 durability=48
```

### 2.2 实现要点

- 新增 `cmd/gmtool/names.go`：`-build-data` 从客户端内层 PVF 的
  `string/{equipment,stackable,setequipment,creature,skin,itemshop,ui,character}.uv.str`
  导出 `names.client.json`（**418,909 条** = 418,591 物品名 + 309 职业名 + 9 品级名），
  **100% 覆盖** `items.index.json` 的全部 386,230 件物品。
  名字优先级：**客户端文本表 → 旧汉化兜底表 → 英文名**。
- 装备**部位**：权威来源是服务端自己的 `configs/equipment-wear.current35.json`
  （槽位 12..25）与装备目录里的 `[equipment type]` 真实文本。
  逐行枚举 19,955 行得到 **22 种取值**（一个不漏、零猜测），
  映射为 14 个现役装备位 + 时装 + 其它装备；再补上游全量目录得到
  `equipment.slots.json`（139,638 件），装备 258,820 件里 **80,356 件**能定位到具体部位。
- `GET /api/filters`：部位 16 项 + 等级 7 档 + 品级 9 档，都带数量；
  `GET /api/items` 新增 `slot=` / `level_min=` / `level_max=` / `rarity=`，与 `q=` / `type=` **全部可叠加**；
  UI 三组 chip 控件 + 清除筛选 + 命中条数 + 品级色标 + URL 深链接。
- **可搬迁**：`items.index.json` / `names.client.json` / `equipment.slots.json` 不再写死绝对路径，
  按「显式参数 → 物品库同目录 → exe 的 `../configs` → exe 同目录 → `-root` 的 configs」顺序自动定位。
  实测**只给 `-storage` 也能跑**（自己找到旁边的 configs），整个文件夹可解压到任意路径。

### 2.3 验收


## 三、两个通用坑（建议写进上游的注意事项）

### 3.1 ★ 重编服务端二进制必须从本仓库编译 ★

本侧的 `D:\115us\server` 是**仓库副本的镜像但没有上游功能**（商店/金库/分身分解等文件只在仓库里）。
在镜像里 `go build` 会**静默丢掉这些功能**——本次真实发生过一次，靠对比 exe 内的函数符号才发现：

```
正确：cd <repo>/server/work/dfo-lan && go build -trimpath -o bin/wireprobe-handoff-source.exe ./cmd/wireprobe
自检：exe 里必须能搜到 internal/loot/shop、vault_flow、disjoint、empty_item 四个符号
```

### 3.2 ★ 客户端 `Script.pvf` 是加密外层，`Script.inner.check.pvf` 不代表客户端内容 ★

要拿客户端**当前**真实数据（物品名/职业表/装备需求）必须解密。
本机可用的路径（`server/reference/analysis-tools/unwrap_pvf.py`）：

1. 把脚本里的 `root` 改成客户端目录（含 `DFO.exe` + `sk.dat`）、`out` 改到一个**空目录**
   （脚本会拒绝覆盖已存在输出）；
2. 用带 `pefile` + `cryptography` 的解释器跑（本机 `tools/python` 有）；
3. **不要放在 `%TEMP%` 里跑** —— 那里可能有同名 `struct.py` 遮蔽标准库；
4. 产出内层 PVF 后即可用 `cmd/pvfinspect -tokens` 读。

## 四、未实现 / 已知限制

1. **角色转职/觉醒**：服务端在 `internal/character/detail.go` 与
   `internal/character/learning_catalog.go` **硬拒绝 `advancement != 0`**，
   直接改存档会让角色进不去游戏；且任务目录里没有 1 转任务。**未实现**。
2. **装备 强化/增幅/锻造/品级 未在服务端建模**：`BagEquipment` 只有
   `{slot,template,durability}`，那 181 字节里这些位置服务端根本不写，`Data` 恒为 0。
   已取证的字段偏移（供后续实现）：**强化/增幅等级 = offset 10 的 `ext_data1`**
   （bit0-4 = 0..31，bit5-7 = 再封装次数，**不是** `enchantUpgrade`）；
   `enchantIndex`@14(u32) 附魔卡、`enchantUpgrade`@18、`amplify_type`@19、`amplify_value`@20；
   锻造在记录尾部（0..8，仅武器）；品级疑在 `Data`@6（0..100）。
   证据：`internal/game/protocol/testdata/native_equipment_record.json`、
   `runtime/*/events.jsonl` 的 `worn_equipment_restored`、外部 `Liuxiny/86jp_DfoGmTool` 的 `ItemCore.cs`。
   **只差尾部 10 字节绝对偏移的实机判定**（客户端字段日志本身就是现成 oracle）。
3. GM 工具：装备 258,820 件里 178,464 件只能归「其它装备」（两份装备目录都没有它们的 `[equipment type]`）；
   等级只对 82,766 件已知，按等级筛选会排除未知等级的物品；
   物品库里大部分装备不在服务端现役目录（19,955 件）里，发放时服务端仍会拒绝（既有行为）。

```bash
# 副本可进性审计（真实 Select，3,200 个副本）
go run ./cmd/dungeonaudit -catalog configs/dungeons.full.json
go run ./cmd/dungeonaudit -catalog configs/dungeons.full.json -ids 86,92,93,88

# 地图补缺（不动 source.checksum）
go run ./cmd/dungeonmaps -catalog configs/dungeons.full.json \
    -source runtime/pvf_source/Script.inner.pvf -dry-run=false -output configs/dungeons.full.json.new

gmweb.exe -build-data -client-pvf <客户端内层PVF> -equipment-slots configs/equipment.slots.json

# GM 工具测试
gofmt -l cmd/gmtool && go build ./... && go vet ./cmd/gmtool && go test ./...
```
