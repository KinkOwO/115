# 背包物品分类错误 —— 实现报告与迁移方案

> 本报告基于逆向分析与源码追踪的已查明证据整理，用于指导服务端迁移/修复。
> 本地运行时文件损坏不影响本报告结论，结论均来自客户端权威 IDB、PVF 资源与参考服务端（ServerS4A21）的对照。

---

## 1. 问题描述

背包中大量明明是 **消耗品 / 任务物品** 的道具被错误分类显示在「材料」页签下，典型如：

- 药水（红蓝药、解毒药、力量药剂等）
- 礼盒 / 宝箱 / 福袋

---

## 2. 客户端渲染机制（关键前提）

DFO 客户端（115 级、90 级、经典版均一致）**不按物品自身标签自动归类页签，而是严格按槽位号（Slot Index）决定物品显示在哪个页签**。

服务端在同步背包数据（NOTI13 `ITEM_LIST` / NOTI14 `UPDATE_ITEM_LIST`）时，只要给物品分配了某个区间的槽位号，客户端就**无条件**渲染到对应页签。因此：

> 槽位号分配错误 = 页签显示错误。这是本次问题的唯一直接原因。

---

## 3. 权威槽位区间表

主容器（Main Inventory）各页签对应槽位区间如下（已由参考服务端 `ItemSlotBoundService.cs` 与客户端资源印证）：

| 页签 | 槽位区间 | 格子数 | 对应 PVF `[stackable type]` / 物品种类 |
| :--- | :--- | :--- | :--- |
| 快捷栏 QuickSlot | `3 ~ 8`（内部 `0 ~ 8`） | 6 | 拖入的药水/消耗品 |
| 装备栏 Equipment | `9 ~ 64` | 56 | 装备（weapon/armor/accessory） |
| **消耗品栏 Consumable** | **`65 ~ 120`** | 56 | `[waste]`、`[throw]`、`[booster]`、`[booster selection]`、`[booster random]`、`[cera package]`、`[usable cera package]`、`[etc]`、`[contract]`、`[recipe]` 等 |
| **材料栏 Material** | **`121 ~ 176`** | 56 | `[material]`、`[upgrade limit cube]` 等 |
| **任务栏 Quest** | **`177 ~ 232`** | 56 | `[quest]`、`[quest receive]` |
| 副职业栏 Profession | `233 ~ 288` | 56 | `[material expert job]` |
| 徽章栏 Emblem | `289 ~ 344` | 56 | `[avatar emblem]` |

**默认规则**：除上述明确分类外的其余可堆叠（stackable）物品，**默认应落入消耗品栏 `65 ~ 120`**（参考 `ItemMetadataResolver.GetSlotRange` 的兜底分支）。

---

## 4. 根因分析（已定位的缺陷点）

### 4.1 背包规则配置只定义了两类区间

配置文件 `configs/inventory.current37.json`（及 `inventory.next29.json`、`inventory.compat90.json`）中 `slots` 仅包含：

```json
"slots": {
  "[throw]": [65, 120],
  "[material]": [121, 176]
}
```

问题：

- 把 `65 ~ 120` 误命名成了 `"[throw]"`（投掷品），但实际 PVF 中投掷物仅 138 种；
- 药水是 `[waste]`（约 10,960 种）、礼盒是 `[booster]`/`[cera package]`/`[etc]`（数万种）、任务品是 `[quest]`（约 1,408 种），**均未建立到槽位区间的映射**；
- 完全没有 `[quest]`（`177 ~ 232`）、`[material expert job]`（`233 ~ 288`）、`[avatar emblem]`（`289 ~ 344`）的分类映射。

### 4.2 NPC 商店购买硬编码进材料栏

`internal/inventory/shop.go` 的 `Buy` 函数：

```go
// Award into the material category (slots 121-176).
matRange, hasMat := r.Slots["[material]"]
...
for n := uint32(matRange[0]); n <= uint32(matRange[1]); n++ {
    slot := uint16(n)
    if !occupied[slot] {
        b.Items = append(b.Items, BagItem{Slot: slot, Template: template, Amount: count})
        return b, slot, nil
    }
}
```

- 所有 NPC 商店**购买的物品一律写入 `121 ~ 176`（材料栏）**，与物品类型无关。
- 因此购买红蓝药等消耗品即被错误归入材料栏。

### 4.3 礼盒/魔盒开启兜底硬编码进材料栏

`internal/inventory/booster.go` 的 `addStackableFallback`：

```go
slotsRange, ok := r.Slots["[material]"]
if !ok {
    slotsRange = [2]uint16{121, 176}
}
// 全部落入 slotsRange[0]..slotsRange[1]（121..176）
```

- 开启礼盒/魔盒产出的可堆叠物品，兜底逻辑**强制分配到材料栏**。
- 导致开盒得到的药水、道具被错误归为材料。

### 4.4 掉落表导入过滤掉了消耗品/任务品

`cmd/lootimport/main.go` 导出 `configs/loot.next25.json` 内核信息已探明：

- 导入时排除了 `cash/`、`quest/`、`recipe/`、`temp/`、`event/`、`emblem/`、`monstercard/` 前缀的堆叠物品；
- 同时要求 `[creation rate] > 0`、`[grade] > 0`、`[rarity] 0..6` 等条件，过滤掉大量药水/礼盒；
- 导致 `loot.next25.json` 中 1022 个物品有 1007 个是 `[material]`，**基本没有药水/礼盒/任务品**；
- 结果通用 `Bag.Add` 查表时，大量真实物品无法解析到正确的 `stackable_type`，无法落入正确槽位。

---

## 5. 迁移 / 修复方案

### 5.1 扩展背包规则（`BagRules` + `inventory.current37.json`）

将 `slots` 从两类扩展为完整的分类→槽位映射：

| 分类键 | 槽位区间 |
| :--- | :--- |
| `[throw]`（投掷物） | `65 ~ 120` |
| `[waste]`（药水/消耗品） | `65 ~ 120` |
| `[booster]`、`[booster selection]`、`[booster random]`（礼盒） | `65 ~ 120` |
| `[cera package]`、`[usable cera package]`（福袋/券包） | `65 ~ 120` |
| `[etc]`、`[contract]`、`[recipe]` | `65 ~ 120` |
| `[material]`、`[upgrade limit cube]`（材料） | `121 ~ 176` |
| `[quest]`、`[quest receive]`（任务） | `177 ~ 232` |
| `[material expert job]`（副职业） | `233 ~ 288` |
| `[avatar emblem]`（徽章） | `289 ~ 344` |

> 建议在 `BagRules` 中新增 `DefaultStackableSlots [2]uint16` 字段，默认 `[65, 120]`，作为未命中任何分类时的消耗品兜底区间。

### 5.2 新增统一的「按物品类型分配槽位」函数

新增类似 `GetSlotRangeForItem(item) ([2]uint16)` 的函数（参考 `ServerS4A21` 的 `ItemMetadataResolver.GetSlotRange`，但需以 115 级客户端实际 IV 为准），按优先级：

1. 装备类（在装备目录 / ID 满足装备判定）→ `9 ~ 64`
2. `[material expert job]` → `233 ~ 288`
3. `[avatar emblem]` → `289 ~ 344`
4. `[material]` 系列 → `121 ~ 176`
5. `[quest]` 系列 → `177 ~ 232`
6. **以上均不命中 → `65 ~ 120`（消耗品默认兜底）**

### 5.3 修复 `shop.go` 的 `Buy`

- 移除对 `[material]`（`121 ~ 176`）的单一硬编码；
- 改为调用 5.2 的分配函数，根据物品 `stackable_type` 决定目标区间；
- 物品不在掉落地目录（NPC 商店物品使用不同 ID 空间）时，仍需通过 `items.index.json` 或 PVF 元数据解析其真实类型。

### 5.4 修复 `booster.go` 的 `addStackableFallback`

- 将默认兜底区间从 `[material]`（`121 ~ 176`）改为消耗品区间 `65 ~ 120`；
- 同时优先命中真实类型映射，材料类仍正确落 `121 ~ 176`。

### 5.5 修复掉落表导入（`cmd/lootimport`）

- 不再排除 `quest/`、`recipe/`、`event/` 等前缀，或单独为这些分类建立可解析的映射；
- 保留 `[stackable type]` 原始文本，供 5.2 的分类函数正确分配槽位。

### 5.6 同步 GM 工具配置

- 将更新后的 `inventory.current37.json`、`loot.next25.json`、`items.index.json` 同步到 `gm-tool/configs/`；
- 确保通过 `admin.exe` / `gmweb.exe` 发放药水/礼盒时也走同一套分配逻辑，直接落入消耗品栏。

---

## 6. 校验与回归

- 单测覆盖：`shop_test.go`、`booster_test.go` 需新增「药水落 `65 ~ 120`、材料落 `121 ~ 176`、任务品落 `177 ~ 232`」的断言。
- 全量 `go test ./...` 与 `go vet ./...` 通过。
- 实机验证（由用户手动操作）：购买药水、开启礼盒、发放任务品后，确认页签显示正确。
- 存档兼容：仅调整槽位分配逻辑与配置，不改动数据库结构；历史已错放物品需提供一次性迁移脚本（按 `items.index.json` 重算正确槽位并回写角色 state）。
