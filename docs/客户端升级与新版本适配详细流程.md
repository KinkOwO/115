# DFO 客户端升级与新版本适配详细流程

更新时间：2026-10-04。适用工作区：`D:\115us\NEW_DFO115`。

本文依据本地源码、2.38.2.34 → 2.38.3.25 的实际适配和用户进城确认编写。未来版本必须重新核对资源、协议和实机结果，不能把本版通过直接当成下一版通过。

## 1. 先看这一页：下一版应该怎么做

升级按以下顺序进行。某一步失败时停在这一层解决，不同时更换资源、协议和数据库。

1. 保留现有可玩客户端、已确认服务端程序、内层 PVF/manifest 和玩家数据库备份。
2. 把完整新客户端放到独立目录，例如 `DFO_下一版本号`；先取得同版官服“登录→选角→进入城镇”的抓包。
3. 记录新旧 `DFO.exe`、`sk.dat`、`Script.pvf` 的版本、大小和 SHA256；保持三件套配套。
4. 检查复制工作区的路径，特别是 `launcher.local.json` 的 client_dir，以及 `runtime/storage/local.json` 的 postgres_bin/postgres_data。
5. 验证 wrapper 密钥提取与新 PVF 解析，生成匹配新客户端的内层 PVF；先审计再放行内容哈希门禁。
6. 检索整条角色入场路径中的源身份校验，保证旧角色仍能投影技能与进入世界。
7. 执行测试和 vet，构建独立候选程序，复制默认 profile 并只改 binary。
8. 用 **profile 绝对路径** 做启动检查。注意 `--check` 不启动游戏/数据库，但在资源变化时可能生成内层 PVF。
9. 用户手动启动新客户端，先验收角色列表，再验收选角、城镇显示和移动。读取同一轮服务端日志和官服抓包作对照。
10. 用户确认后记录 confirmed baseline；再按发布流程升级默认程序。玩法回归分项记录，失败时按完整配套回退。

核心原则：**版本升级先处理资源和源身份，再判断协议是否真的变化。日志收到连接或持续扫描，不能等同于进城。**

### 4.3 数据库备份的两种方式

**逻辑备份：** 在旧环境数据库正常运行时，用同包 PostgreSQL 的 `pg_dump.exe` 生成 custom 格式。先确认 local.json 属于本工作区，端口/库名正确。以下示例从本地配置取连接参数，不在命令输出中打印密码，也不把密码写到进程命令行：

```powershell
$StorageCfgPath = Join-Path $GoRoot 'runtime\storage\local.json'
$StorageCfg = Get-Content -LiteralPath $StorageCfgPath -Raw | ConvertFrom-Json
$PgDump = Join-Path $StorageCfg.postgres_bin 'pg_dump.exe'
if (-not (Test-Path -LiteralPath $PgDump)) { throw 'pg_dump.exe missing' }
$DsnUri = [Uri]$StorageCfg.postgres_dsn
$LoginParts = $DsnUri.UserInfo.Split(':', 2)
$DbName = $DsnUri.AbsolutePath.TrimStart('/')
$SavedPgPassword = $env:PGPASSWORD
try {
    $env:PGPASSWORD = [Uri]::UnescapeDataString($LoginParts[1])
    & $PgDump -h $DsnUri.Host -p $DsnUri.Port `
        -U ([Uri]::UnescapeDataString($LoginParts[0])) -d $DbName `
        -Fc -f (Join-Path $BackupDir 'players.dump')
    if ($LASTEXITCODE -ne 0) { throw 'Database backup failed' }
} finally {
    $env:PGPASSWORD = $SavedPgPassword
}
```

该示例适用于当前 postgres://用户:密码@主机:端口/库名 格式；未来连接格式变更时先调整解析。可用 `pg_restore --list` 检查备份是否可读取。升级前最好在隔离数据库演练恢复，而不是等出故障才第一次恢复。

**物理备份：** 完全关闭游戏/网关后，让 PostgreSQL 正常停机并确认数据目录不再由 postgres 进程使用，再复制整个 pgdata 及配置。不能把运行中 pgdata 的普通文件复制当作可靠数据库备份。

现有 `停止游戏环境.cmd` 的实现按进程名称停止服务，可能同时影响旧工作区同名进程；其名单未必包含新命名的 `wireprobe-town-entry.exe`。执行前确认只有要停止的环境在运行；停止后检查候选进程是否退出，不要假设脚本已覆盖所有名字。

## 7. wrapper 密钥与内层 PVF：先离线打通

### 7.1 当前取钥策略

`scripts/pvf_archive.py` 和 `scripts/reinforcement_pvf_reader.py` 当前采用：

1. 旧版固定 VA 取钥快路径。
2. 失败后扫描 EXE 文件中的 PRIVATE KEY 文本块，并从其后窗口找 AES hex 候选。
3. 用配套 sk.dat 做 RSA 解密验证，剔除无关钥，不靠找到字符串就判定有效。

2.38.3.25 的旧 VA 槽位已失效，本次依靠扫描回退成功。文件偏移、密钥数量和窗口布局都是本版证据，不能硬编码为未来版本规律。不要把真实密钥打印到日志、文档或 Git。

### 7.2 先跑提取器回归

```powershell
Push-Location -LiteralPath $ScriptsRoot
try {
    & $PyExe -m unittest test_pvf_wrapper_keys -v
    if ($LASTEXITCODE -ne 0) { throw 'Wrapper key regression failed' }
} finally { Pop-Location }
```

单测使用合成密钥，证明提取策略，不证明新客户端真实三件套可用。接下来还需真实 PVF 解包和解析。

### 7.3 方法 A：升级检查走现有 ensure 门禁

从仓库根执行：

```powershell
& $PyExe (Join-Path $ScriptsRoot 'launch_local.py') --check --server-only
if ($LASTEXITCODE -ne 0) { throw 'Startup dependency check failed' }
```

当前实现先核对客户端和 profile 依赖，PVF 模式下调用 `ensure_inner_pvf`，随后才处理 `--check` 返回。因此该命令**不启动游戏/服务监听/数据库，但可能轮转并生成 PVF 和 manifest**。没有备份时不要把它作为完全只读指纹检查。

ensure 的四类判定：无内层文件→生成；无有效 manifest→重建；客户端三件套变了→重建；配套未变→复用。旧件正常情况下轮转为 `.stale-时间戳`，不需要手动删旧文件；失败时仍检查旧件实际位置，不依赖“肯定已备份”的假设。

### 7.4 方法 B：先生成完全独立的候选内层文件

更适合新版本未知、需要保持当前内层基线时。输出到刚创建的空候选目录，不覆盖当前 client-build：

```powershell
$CandidateInner = Join-Path $CandidateDir 'Script.inner.pvf'
$CandidateManifest = Join-Path $CandidateDir 'Script.inner.manifest.json'
& $PyExe (Join-Path $ScriptsRoot 'prepare_inner_pvf.py') `
    --client-dir $NewClient --output $CandidateInner --manifest $CandidateManifest
if ($LASTEXITCODE -ne 0) { throw 'Candidate inner PVF generation failed' }
```

prepare 拒绝已经存在的输出，也拒绝把输出放到客户端输入目录；父目录要先存在。需要重试时用新候选目录，不添加未经实现的 `--force`。

独立产物用于离线检查。当前 launch_local 的 ensure 仍维护固定的 `server/work/client-build/Script.inner.pvf`；仅修改 profile 的 DFO_PVF_ARCHIVE 并不能让 ensure 同步改输出目录。实机前应确认固定内层与选中的客户端也配套，避免新 archive 和旧 manifest 混用。

### 7.5 应看到什么

- wrapper 和内层头校验通过，manifest 包含三件套和内层大小/SHA256。
- 实际目录/文本/typed tokens 能由当前 reader 解析。
- 本版外层和内层等长属于当前分块解密实现的正常结果，不是“没解密”的证据。
- `MalformedFraming` 优先查取钥；`sk.dat` 候选解不开优先查配套；`unwrapped header...` 查解密链；父目录不存在/拒绝现有输出属于产物管理问题。

## 8. 新旧 PVF 的语义审计与哈希门禁

### 8.1 三种身份必须区分

| 身份 | 应解决的问题 | 升级时处理 |
| --- | --- | --- |
| 文件/原始脚本 SHA256 | 资源指纹、缓存与已审计向量 | 字节变化就变化，保留真实值 |
| 职业/内容引用，如 SourcePath、ID | 旧角色指向哪个职业/技能/物品 | 按引用和当前源查表，不能只靠资源字节 SHA 拒档 |
| 存档契约身份 SaveIdentity/ConfigVersion | 存档结构和执行契约兼容 | 保留校验，变化需无损迁移 |

本版 PVF 重建字符串池后，很多脚本嵌入的池偏移变化；职业脚本的解析文本和 token 语义可能相同，原始 SHA 却不同。**“SHA 不同”不能直接等于“规则改变”；“Path 一样”也不能证明规则完全相同。**

### 8.2 重点审计脚本

| 内容 | 本次位置/线索 | 为什么要查 |
| --- | --- | --- |
| 无色小晶块 3037 | `stackable/material/cubepiece_clear.stk`；inventory/clear_cube.go | 启动阶段原始哈希门禁 |
| 奥德赛成长 | `contents/2026/aradodyssey/etc/aradodyssey.etc`；catalog/odyssey.go | 启动阶段已审计 hash 集合 |
| 当前角色职业 | 由 ImportCharacters 和职业索引发现 `.chr` 路径 | 旧角色 SourcePath/技能/转职/觉醒 |
| 技能 | 职业与 skill 索引的 `.skl` 引用链 | 初始技能、自动技能、技能投影、预设、觉醒 |
| 启示录 | apocalypse.ctp、dungeonskillinfo.ctp 的真实索引路径 | 本次字节相同，下版仍重新核验 |
| 世界/城镇/任务 | world、town、quests 原生目录 | 当前出生位置、地图、NPC、前置任务变化 |

以上是排查入口，不是新增一套人工内容清单。新增规则先查当前 PVF 定义，再检查 Go/JSON 是否重复维护，优先复用 Source 和 reader。

### 8.3 用现有工具导出审计证据

统一工具入口已收敛为 `cmd/dfo-tool`，旧 `cmd/pvfinspect` 等入口不再存在。

```powershell
Push-Location -LiteralPath $GoRoot
try {
    & $GoExe run ./cmd/dfo-tool pvfinspect -h
    & $GoExe run ./cmd/dfo-tool pvfinspect `
        -source $CandidateInner `
        -output (Join-Path $CandidateDir 'audit-new-clear-cube') `
        -files 'stackable/material/cubepiece_clear.stk' -tokens
    if ($LASTEXITCODE -ne 0) { throw 'PVF inspection failed' }
} finally { Pop-Location }
```

对保存的旧内层文件用同样参数导出到不同目录，比较 raw bytes/SHA、解析文本和 typed tokens。不要把旧汉化文本变化误判为执行规则变化；区分标签/数值/引用和显示文本。

tokens 中涉及字符串索引的 Value 也可能随池重建变化。不能把 tokens.json 的原始 JSON 文件 diff 等同于语义 diff；应依类型比较标签/解析文本、实际数值、引用链和领域投影。保留 raw 变化作为审计指纹，不把池偏移删除后冒充原始相等。

### 8.4 门禁如何处理

- 若只是池偏移变化，证明对应字段和领域结果等价后，按现有实现登记新的已审计 raw hash。
- 若等级、费用、数量、技能、条件或动作发生变化，按当前 PVF 解析和实现真实变化，再验证旧角色存档兼容；不能直接加入白名单蒙混通过。
- 别把 clear cube/odyssey 的已审计集合无条件改成“任何 hash 都接受”。
- 保持原始 SHA 字段作为追溯，不把旧存档 SHA 批量改为新值来掩盖错误拒档。
- JSON 历史导出只作离线对照，不重新成为运行期规则源；新内容仍由内层 PVF 提供。

## 11. 实机验收：每个阶段需要什么证据

| 阶段 | 应有证据 | 不足以证明成功的现象 |
| --- | --- | --- |
| 客户端拉起 | 配套 DFO.exe 实际启动，probe 指向新目录 | 只出现启动器窗口 |
| 网关接入 | accept、client_frame、有合法请求 | accept 仅证明 TCP 连接 |
| 登录/角色列表 | 登录应答、character_response；界面角色可见 | character_response 不证明选角成功 |
| 选角准备 | CMD4 后 entry_preflight_passed | 没有 select_rejected 仍可能有 entry_skills_error |
| 入场发送 | select_parser_response、技能19、城镇24、完成124 | 服务端写成功不等同于客户端 reader 消费成功 |
| 客户端进城 | 用户看到城镇与角色，能移动/开背包 | DFO 进程还活着、持续 CMD2127 |
| 玩法/持久化 | 对应操作成功，刷新/落库/重登保持 | 一次进城不覆盖所有功能 |

建议顺序：一个已存在旧角色进城→移动→技能栏和背包→切第二个旧角色→退出重登→技能学习/觉醒→普通任务→普通副本→奥德赛/特殊玩法。每个项单独记录“通过/失败/未测”。不要为追求进度表全绿而把未测写成通过。

## 12. 如何查看服务端日志并与抓包对比

### 12.1 选择正确会话

```powershell
$RuntimeDir = Join-Path $GoRoot 'runtime'
$LatestSession = Get-ChildItem -LiteralPath $RuntimeDir -Directory -Filter 'roles_*' |
    Sort-Object Name -Descending | Select-Object -First 1
$LatestSession.FullName
Get-Content -LiteralPath (Join-Path $LatestSession.FullName 'gateway.err') -Tail 60
```

确认该会话确实对应刚启动的候选。老运行日志可能被复制到新工作区；目录 mtime 不足以证明新会话，结合会话名、事件时间、进程路径和程序 SHA 核对。

### 12.2 过滤关键事件，不打印大密文和凭据

```powershell
$Events = Get-Content -LiteralPath (Join-Path $LatestSession.FullName 'events.jsonl') |
    Where-Object { $_.Trim() } | ForEach-Object { $_ | ConvertFrom-Json }
$Events | Where-Object {
    $_.kind -match 'error|rejected|preflight' -or
    $_.kind -in @('select_parser_response','entry_skills_sent',
                 'town_entry_probe_sent','enter_gameworld_complete_sent')
} | Select-Object time, kind, character_id, id, error
```

服务正在写 JSONL 时尾行可能未完成；遇单行解析错误先复制稳定日志或跳过未完成尾行，不把解析异常当成游戏协议异常。

事件通常记录 UTC `...Z`，本工作区用户时间是 Asia/Singapore（UTC+8）。例如 09:46Z 对应 17:46，本次成功会话 10:05Z 对应 18:05。报告应写明时区，不能把 UTC 当作本地操作时间。

### 12.3 最小抓包概要

```powershell
$CapturePath = Join-Path $UpgradeRoot '实时抓包数据\frames.jsonl'
$Frames = Get-Content -LiteralPath $CapturePath |
    ForEach-Object { $_ | ConvertFrom-Json }
$Frames | Where-Object {
    ($_.dir -eq 'c2s' -and $_.op -eq 4) -or
    ($_.dir -eq 's2c' -and $_.op -in @(4, 19, 23, 24, 124))
} | Select-Object ts, dir, kind, op, len, crypto
```

对比键应包含方向、kind、opcode、连接和操作阶段；不是只看 opcode 数字。当前抓包 op_name 有按 NOTI 表解释 kind1 结果的情况，kind1/id4 不能因名称显示 STAMINA 就误判。

相同功能包长度不同还需排除账号角色数量、背包/技能内容、padding、加密正文、不同连接/不同版本等因素，再下字段变化结论。找真正的客户端明文与 reader，不把两段密文 diff 当作字段 diff。

**CMD2127 = PROCESS_SCAN。** 它可以出现在登录、等待和城镇阶段；持续发送只能作为进程活动线索，不能作为城镇成功判据。

### 12.4 如果确认协议真的变化

先收集新版本对应 reader 的入口、调用链、字段宽度/顺序/分支、解密方式和真实 plain/cipher 向量，再修改服务端。旧版 IDB/dumps 只作定位线索；不能把旧 VA 套用到新 EXE。保护旧权威 IDB，新增分析资产必须记录实际对应 EXE 指纹。

一次只改一个已证实假设。仓库规定同一 C2S 功能的运行路径尝试最多三次；每次记 `attempt N/3`、证据和回退点。第三次仍不闭环时收集新的取证，不能继续盲目叠包。客户端补丁/DLL 只有用户明确要求时才进入该路径，默认仍修 Go 服务端。

### 14.2 发布已确认的精确程序

### 14.3 回退顺序

1. 用户退出新客户端，停止本轮候选服务；确认端口和进程释放。
2. 恢复旧 client_dir；恢复其配套内层和 manifest、旧 profile、已确认旧程序。
3. 数据库没有结构/契约迁移时保持同库；若有迁移，先核对旧程序是否仍支持迁移后存档。
4. 需要恢复数据库时使用已验证备份；保留升级后原始数据副本，避免损失期间新进度。
5. 清楚记录退回的版本和原因，手动验证旧环境仍可进城。

自动轮转的 stale 是资源回退线索，不是数据库备份。不能随便选一份 stale 与任意客户端组合。不要删除缓存/备份来让哈希门禁“看不见问题”；派生缓存由源和程序身份失效，怀疑缓存时可使用既有 `DFO_PVF_CACHE_DIR='-'` 作诊断并在完成后还原。
