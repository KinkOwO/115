# hp-caller-probe — 定位「哪条调用点算出了怪物血量」的只读运行时探针

> 状态：**DLL 已构建并放入客户端插件目录，等待业主实机取日志。**
> 本探针**只记录、不改游戏行为**：不改返回值、不改任何寄存器语义、不改内存数据、
> 不改 `DFO.exe` 文件、不注册成 mod。

## 一句话

在血量 getter（VA `0x147220E40`）的**返回出口** `0x147221011` 的 `ret` 上装一个 5 字节跳转，
跳到我们自己新分配的一页代码里，把 **调用者返回地址 + 这次算出的返回值** 记进无锁环形缓冲，
后台线程定期汇总成日志。因为记的是「调用者的返回地址」，日志里出现的每一行就对应
离线取证列出的 23 个直接调用点 + 2 个尾调用之一，于是能直接看出**是哪个调用点**。

## 2. 它到底改了什么字节（唯一的运行时改动）

| 项 | 值 |
| --- | --- |
| VA | `0x147221011`（血量 getter 的第二个出口：`pop rdi; pop rsi; pop rbx; ret` 的那条 `ret`） |
| RVA | `0x7221011`（ImageBase `0x140000000`，无重定位 ⇒ RVA 即运行时偏移） |
| 文件偏移 | `0x7221011`（`.text` 里 `PointerToRawData == VirtualAddress == 0x1000`，已用节表核对；见 §5） |
| before | `C3 CC CC CC CC`（`ret` + 4 个**函数间对齐填充** `CC`） |
| after | `E9 <rel32>` → 跳到我方新分配的代码洞 |

- `0x147221012`–`0x14722101F` 共 14 字节 `CC` 是**函数间填充**，下一个函数从 `0x147221020` 开始；
  被覆盖的 5 字节里只有第 1 个字节 `C3` 是代码，后 4 个 `CC` 永不执行。
- **代码洞不借用可执行文件里的任何字节**：插件自己在主模块 ±1GB 范围内
  `VirtualAlloc` 一页 `PAGE_EXECUTE_READWRITE`（先扫描空闲区，只分配没人用的洞），
  所以不存在「洞里有别人的 `CALL` 目标」这类冲突（上一轮就是在这点上踩的坑）。
- **没碰**：getter 本体、`0x14BAF7F20` 的共享 `1.0` 常量、flag==0 路径、
  `DFO.exe` 文件本身（当前哈希 `e8f1aa28…` 保持不变）。

### 已知覆盖缺口（宁可少记，不许改坏）

getter 有**两个**返回出口：

```
0x147220FFF  ret        后面紧跟 F2 48 0F 2C C6（真实指令）-> 不能装 5 字节跳转，本探针不碰
0x147221011  ret        后面是 CC 填充                        -> 本探针装在这里
```

所以从 `0x147220FFF` 返回的那些样本不会被记录（那是 `+0x30`「打没了」那条分支的出口）。
两次打怪之间血量会变化，因此**怪物血量相关的那次调用仍然会出现**；缺口只影响计数完整性，
不影响「哪个调用点在算血」的判定。详见 `README.md` §「覆盖范围」。

## 3. 日志格式与判读

日志头部会先打印**已知调用点对照表**（RVA/VA/flag），随后是三类行：

```
[+   1234ms][t  5678] 新的调用点：caller=00007FF6XXXXXXXX (DFO.exe+0x5A06EB6)  第一条样本 ret_rax=12345 rcx=... rdx=... rbx=...
[+   1234ms][t  5678] 样本 #1 caller=00007FF6XXXXXXXX ret_rax=12345 rcx(desc)=000002...890 rdx=255 rbx=255
[+   5000ms][t  5678] ---- 调用点汇总（周期汇总）：共 3 个调用点，已消费 12345 个采样，落后丢失 0，半写重试 0 ----
[+   5000ms][t  5678]   caller=00007FF6XXXXXXXX (DFO.exe+0x5A06EB6          ) hits=9876   ret_rax[last=12345 min=12000 max=13000] desc=000002...890 rdx_evidence=255
```

| 列 | 含义 |
| --- | --- |
| `caller=…` | **调用者的返回地址**（就是「哪个调用点」）。括号里是 `模块名+偏移`，**RVA 直接和日志头部的对照表 / `FINDINGS.md` §2.1 对齐**；把 `DFO.exe+0x5A06EB6` 和表里的 `RVA 0x5A06EB6 (VA 0x145A06EB6)` 对上即可 |
| `ret_rax` | **这次 getter 算出来的数值**（返回给调用者的那个整数，`min`/`max`/`last` 三个口径） |
| `rcx(desc)` | 属性描述块指针。getter 入口的 `RCX` 被它自己保存在 `RDI`，出口处读 `RDI` 得到 ⇒ **与 entry 时的 RCX 相同**，可信 |
| `rdx_evidence` | 出口处 `RBX` 的值。**注意**：getter 用 `RDX` 当临时指针、且开头 `movzx ebx,dl` 覆盖了 `RBX`，所以出口的 `RDX`/`DL` **不是**入口那个 flag；这个字段只是旁证，判定调用点请以 `caller` 为准 |
| `hits` | 该调用点被采到的次数（说明它在你的操作期间有多活跃） |
| `落后丢失` / `半写重试` | 环形缓冲的丢样与半写重试计数。丢样不影响判定（每个调用点都会被采到多次）|

**怎么用**：
1. 在副本里**站定 10 秒**（不打怪）→ 日志汇总里出现的调用点 = 血条比例/面板/派生属性类的周期刷新；
2. **打两下怪** → 新出现、且 `ret_rax` 从大值掉到小值的那个 `caller`，就是**怪物血量**那条；
3. **开关一次角色面板** → 面板相关的 `caller` 会在那一秒前后 `hits` 突增，用来把面板路径排除掉。

## 4. 为什么它不会改变游戏行为（论证）

1. **返回值不变**：洞在保存 `RAX` 之后**再不写 `RAX`**（洞里的算术只用 `RAX` 做临时寄存器，
   写回的是从栈里读出的原值），最后 `jmp` 回原 `ret` 的下一条地址（`E9`/`call` 之后，运行期从现场字节算出）。
2. **寄存器全保**：洞保存/恢复 **8 个非易失通用寄存器**（`rbx, rbp, rdi, rsi, r12–r15`）
   与 **10 个非易失 XMM**（`xmm6–xmm15`），并保证 `RSP` 进出平衡；
   易失寄存器（`rax, rcx, rdx, r8–r11, xmm0–5`）按 ABI 允许被调用者破坏。
   洞需要调用一次 C 函数，这些保存是 ABI 要求的全部。
3. **不碰游戏数据**：C 函数只往插件自己的环形缓冲写；**绝不 deref 采到的指针**
   （描述块可能在 drain 时已释放，读它就有崩客户端的风险）。
4. **安装前逐字节自检**：若 `0x147221011` 的 5 个字节不是 `C3 CC CC CC CC`、
   或不在已提交内存里、或附近没有可用空洞、或内嵌代码洞镜像自检不过 ⇒ **什么都不装，只记一行日志**。
   换客户端版本时宁可失效也不崩。
5. **日志在后台线程**：热点函数里**只写内存**（`lock xadd` 取号 + 若干存储），
   不取锁、不做 IO、不调 CRT；落盘由插件自己的线程每 250 ms 做一次。

## 5. 离线验证（本轮实际做过什么）

| # | 验证 | 结果 |
| --- | --- | --- |
| 1 | PE 节表自行核对（`verify_site.py`） | `0x147221011` 在 `.text`，file off `0x7221011` == RVA；`DataDirectory[5]`（重定位）为空 ⇒ 固定基址，RVA 稳定 |
| 2 | 现场字节 | `C3 CC CC CC CC` ✔，前后 14 字节 `CC` 填充、下一函数 `0x147221020` 实测一致 |
| 3 | 拷贝打补丁往返（只改副本） | 只有 5 个字节变化（`0x7221011`–`0x7221015`），其余全部不变；`0x147220FFF` 出口未被碰 |
| 4 | 洞的机器码 | `tools/cavegen.py` 用 ml64 汇编 + `x86_64` 反汇编逐条比对：入口 `E9`、`FF 25` 桩、8 push/8 pop 镜像、10 movaps 镜像（`xmm6..xmm15`）、`sub rsp,32`/`add rsp,32` 对称、返回地址确实读自 `[rsp+0x40]`、`RAX` 只从 `[rsp+0x18]` 读回一次。任一不符 **拒绝生成头文件** |
| 5 | 环形缓冲/汇总逻辑 | `client-patchs/tests/hp-probe-selftest.c`：4 生产者 × 20 万样本 + 1 消费者，**收到的样本全部自洽、无错配、无重复计数**（此项已通过）|
| 6 | 洞的实机执行 | ❌ **未完成**（见下）|

### 未闭环项（明确写出）

1. **洞的运行期执行没有离线跑通**。我写的离线执行器
   `client-patchs/tests/cave-selftest.*`（把洞拷到私有页、喂已知寄存器、校验全部非易失寄存器）
   卡在一个我**尚未定位**的 `0xc0000005` 上：异常报在洞内 `cave+0x22`，但该处字节实测是合法的
   `push rbx`，页属性 `PAGE_EXECUTE_READ`，`RSP` 也正常。**卡点超过一次尝试，按指令停手并如实记录**
   （该离线执行器不属于交付物；`cave-selftest.c` 是实验性的，`build-cave-selftest.cmd` 默认失败即退出）。
   风险与缓解：探针自带 §4 的自检；洞的**静态**正确性已由第 4 项逐条证明。
2. **`0x147220FFF` 出口没被覆盖**（无填充可借），该出口的样本不计入统计。
3. **没有实机验证**：按约束未启动游戏，实机由业主操作。
4. **Themida 完整性校验未知**：客户端带 `.themida` 节，改内存页是否触发完整性检查，
   静态无法判定；若游戏异常，先删 DLL 复现一次即可区分责任。

## 7. 构建

```cmd
client-patchs\hp-caller-probe\build-dll.cmd        :: -> dist\HpCallerProbe.dll（静态 CRT，x64）
client-patchs\tests\build-hp-probe-selftest.cmd    :: 环形缓冲自测
```

环境：本机 MSVC（`vcvars64.bat`），`cl /LD /O2 /MT`，`/TP`（源码用 `extern "C"` 保持导出名不加修饰），
`/OPT:NOICF`（**必须**：洞镜像几乎全是零字节，链接器的相同数据折叠会把这些零串到别的零数据上，
实测会让桩里的跳转槽变成 0；插件里另有构建期完整性自检兜底），`/Brepro`（可复现构建）。
