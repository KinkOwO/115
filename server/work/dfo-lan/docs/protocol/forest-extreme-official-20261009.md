## 0. 一句话结论

极难度**不是**「普通难度换三个副本号」。它是一个独立内容（内容号 105），
状态包走 **N2565（64B）**、过段 tick 走 **N2566**、**没有选音符窗（无 CMD2226）**、
第 1 关用 CMD2045 进图、第 2/3 关由客户端 **CMD2062 直进**，通关奖励是官服
七行 N2252 + 一行 N2253。旧实现（第 13–21 轮）整场复用 Normal 包链
（N2563 + 选音符 + 内容号 104），与官服口径完全不符 —— 这就是业主所说的
「极难度是按普通难度做的」。

## 1. 取证方法（可复现）

抓包目录里只有 pcapng 与解密后的会话流，没有带时间戳的 `frames.jsonl`，
因此本轮自己把两者接起来：

1. 用仓库自带的 `dfo-tool framedump`（`internal/toolcmd/framedump`）把
   `session_s13_*.bin` 逐帧解出**完整明文**（`.txt` 里带 `..` 的是截断版）：
   `dfo-tool framedump s13 <key.bin> <stream.bin> all 16|13`（s2c 头 16B、c2s 头 13B）。
2. 解析 `official_20261008-220048.pcapng`（pcapng → EPB → 以太网/IPv4/TCP），
   按四元组重组 TCP 流，与解密流按**总字节数**配对（5/6 个方向精确命中），
   这样每个帧偏移都能取到 pcapng 的段首时间戳。
3. 两个方向按时间戳归并 → 完整时序（本次落在 `session_s13` 的森林段）。

主机侧其它连接（s20 = 巴卡尔攻坚、s3 = 登录/城镇）与本内容无关；
s13 里 CMD12 建队类型是 **0x19**、CMD2043 内容号是 **105**，即为 Extreme。

  @8..11 的 u32**（官服 = 4 秒）：客户端先把副本预加载好，然后在窗口内无缝切场景。
- 官服时序正好踩点：`22:05:41.514`（N2568）→ `22:05:45.514`（下一批）= **4.000s**，
  副本帧列在 `22:05:45.580`（+4.066s）。
- 我们第三版是 `4.1s 常数 + 1 秒 tick` = **+4.87s**，超出客户端自己声明的窗口 ⇒
  客户端退回非无缝路径，界面态留在「无缝加载中」，HUD 再也建不起来。
- 对照第二版（不发 N2568）：客户端根本没进无缝态，模块路径仍是
  `TOWN → SELECT_DUNGEON → FOREST_OF_AWAKENING_LEGION(40)`，HUD 正常 ——
  可见模块 40 本身没问题，出问题的是「无缝态没收尾」。

### 处理

1. `forestPurifyBannerSeconds` 固定为 **4s**，并新增
   `TestForestHardPurifyDelayMatchesVector` 断言它等于 N2568 正文 @8..11 的
   delay 字段（两个数不许漂移）；
2. 新增 `connection_session.scheduleForestBanner(delay)`：**精确定时器**到期后
   把时间戳发回主循环（`forestBanner` channel），主循环再执行 `forestEntryDue`
   —— 状态推进仍然只在主循环里发生，没有并发访问 `worldSession`；
3. 1 秒 tick 退化为兜底（`forestPurifyBannerFallback` = 6s）。

### 第四轮实机（2026-10-09，仍丢 HUD）→ 真因：缺了官服「军团帧列」

精确定时器让进图帧列**正好落在 4.000s**（客户端 trace 里
`[08:55:19] change module : TOWN(1) -> SELECT_DUNGEON(2) -> FOREST_OF_AWAKENING_LEGION(40)`
正好在 N2568 之后 4 秒），但 HUD **仍然全丢**。于是把「我们发的帧」与

差集就是答案：

仓库里 `internal/legion/ispins_replay_frames.generated.go` 的字节与官服

```

```

注入器 `injectForestLegionFrames` 找不到锚点会**报错**而不是静默跳过（静默少发
正是这一轮丢 HUD 的成因）；`TestForestLegionEntryFramesInjection` 钉住顺序、
字节（与官服抓包表比对）与「缺锚点必须报错」。

### 第五轮实机（补完军团帧列，HUD 仍丢）→ 真因：进图缺 **N23（area=0xff）**

补上军团帧列后客户端 RECV 里确实有
`UDP_HOST / INFINITE_DIFFICULTY_INFO_USER·CHARAC / LINKED_DUNGEON_INFO /
MONSTER_MOVE_SYSTEM / FATIGUE_ACCELERATION_STATE`，但 HUD **仍然全丢** ⇒ 帧集不是原因。

于是回头把两份官服抓包的**进图第一帧**摆在一起：

```
官服 Normal  21:42:18.422  s2c id=23  c401 c6000000 ff000000 b903da00 05 …   ← 进第一关
官服 Normal  21:43:32.985  s2c id=23  c401 c6000000 ff000000 ce03ed00 05 …   ← 第二关
官服 Normal  21:44:34.646  s2c id=23  c401 c6000000 ff000000 ce03ed00 05 …   ← 第三关
官服 Extreme 22:05:45.515  s2c id=23  4400 c6000000 ff000000 ee011f01 05 …   ← 进第一关
官服 Extreme 22:06:15.452  s2c id=23  4400 c6000000 ff000000 ee011f01 05 …   ← 第二关
```

**官服每次进图（Normal 与 Extreme 都一样）的第一个 s2c 帧都是
N23 `USER_AREA` 且 `area = 0xff`** —— 也就是「角色现在在副本区」这条状态，
离开时再发一帧 `area = 1/2/3` 切回待机区（官服 22:08:34.146）。

本仓此前**任何副本进图都不发这一帧**。这解释了三轮实机的全部现象：

| 情形 | 客户端自身行为 | HUD |
| --- | --- | --- |
| 非无缝进图（普通副本 / 不发 N2568 时） | 客户端自己的加载流程会把区域切成副本态 | 正常 |
| 无缝加载（N2568） | 客户端**等服务端把区域改成 0xff**；我们不发送 ⇒ 它认为仍在城镇 | 城镇界面收起、副本界面不建 ⇒ 全屏无 UI |

修法：`forestDungeonAreaNotice()` 用当前落点构造 `N23 + area=0xff`，
在极难度进图（CMD2045）与过段直进（CMD2062）两处都作为**该批次第一帧**下发
（官服位置）。`TestForestDungeonAreaNoticeUsesDungeonArea` 钉住 area/位置/actor。

### 第六轮实机（N23 也补了，HUD 仍丢）→ 真因：**N28 从 @26 起整段错位一字节**

改完 N23 后 HUD 仍然全丢，于是把两侧的 **N27 / N28** 逐字节摆开比 ——
官服两份抓包这一帧**除副本 id 与尾部动态值外逐字节相同**，而本仓从 @26 起错位：

| idx | 本仓（旧） | 官服 Normal = Extreme | 位置语义 |
| --- | --- | --- | --- |
| 19..25 | ff×7 | ff×7 | ✓ |
| **26** | **ff** | **00** | 旧实现多写了一个 ff，把后面全部推后一格 |
| 27..29 | 01 00 00 | 01 00 00 | ✓ |
| **30** | **00** | **05** | ★ 客户端 native **单独读这一字节**（`0x1452ada9e`，offset=30，`DungeonInfoState.Entry` 同源取证） |
| 31..36 | 05 01 00 01 00 01 | 01 00 01 00 01 00 | 官服常量块整体错位 |
| 37..40（旧为 38..41） | ff ff ff ff | ff ff ff ff | 同上 |
| 41..45（旧为 42..45+46） | 种子 | 会话动态值 | 同上 |

也就是：旧帧把那个 `05` 写到了 @31（客户端不读的位置），@30 反而是 `00`
（= 普通冷进本）。而客户端在 `[SEAMLESS LOADING]`（N2568）之后期待的正是
「这是继续、不是新副本」的信号 ⇒ 它一直停在无缝加载的界面态，HUD 不建。

N27 同样有三种官服形态，极难度两处各用一种：

| 场景 | 官服头四字节 | 本仓旧值 |
| --- | --- | --- |
| 冷进场（普通副本） | `00 00 00 01` | 同 |
| **极难度第 1 关（无缝加载后）** | **`01 00 00 01`**（22:05:45.580） | `00 00 00 01` ✗ |
| **极难度第 2/3 关（CMD2062 直进）** | **`00 01 01 01`**（22:06:15.456 / 22:06:46.792） | `00 00 00 01` ✗ |

**修法**：

1. `internal/game/protocol/forest_dungeon_info.go`：按官服两份抓包逐字节重排
   （@19..25 = ff×7、@26 = 00、**@30 = 05**、@31..36 = 01 00 01 00 01 00、
   @37..40 = ffffffff、种子移到 @41）；@45 官服是动态字节（Normal 0x36 /
   Extreme 0x42）、语义未回收，本仓写 0 并在注释里留证。
2. `internal/game/protocol/dungeon.go`：新增 `EnterDungeonSelectionSeamless()`
   （头 `01 00 00 01`）与 `EnterDungeonSelectionStageContinue()`（头 `00 01 01 01`）。
3. `cmd/wireprobe/forest_flow.go`：极难度 CMD2045 进图用前者、CMD2062 过段直进用
   后者（并把过段的选图层压成官服那样只有 N27）。
4. 新增 `TestForestDungeonInfoMatchesOfficialCapture`（钉住官服两份抓包的字节、
   @26/@30 语义字节、种子偏移）与 `TestEnterDungeonSelectionHeads`（钉住三种头）。

> 该 N28 修正对 Normal 森林同样生效 —— 官服两个难度这一帧本来就完全相同，
> 所以 Normal 也一并回到官服字节（顺带修掉旧帧的「消耗品许可块错位」）。

## 10. （已回滚）再次开战被客户端本地拦下：N2254 军团入场账本

> 本节描述的 N2254/N781/N782 重推**已按业主 2026-10-09 指示回滚**（不再处理
> 「通关后再开一局」）。以下帧级事实仍然有效，留作取证参考。

### 现象与取证（业主 2026-10-09 实机）

通关 → 退队 → 再建队 → 点「开始作战」**没反应**。客户端帧列表显示：第二次建队
之后 **23 秒内一条 CMD2043 都没有**（整段会话 `id=2043` 只出现一次）⇒ 请求根本没
发出来，是**客户端本地**把按钮拦下了，不是服务端拒绝。

拦它的是 `N2254 LEGION_ENTRY_CHARAC_INFO`（272B = 16B 头 + 每个内容 24B 账本行，
内容号 101..110）。内容 105 那一行**偏移 +5** 的字节：`7f` = 可入场、`00` = 已消耗。
客户端消耗一次后会把它标成已消耗，**必须由服务端重推才能刷回来**。

官服把这次重推挂在**退队应答链**上（两份抓包都有，间隔 0.2~0.3 秒）：

| 抓包 | 客户端请求 | 服务端重推 |
| --- | --- | --- |
| Normal 2026-10-02 | `21:47:03.283` c2s CMD13 退队 | `21:47:03.500` s2c N2254（104 行刷回可用） |
| Extreme 2026-10-08 | `22:08:44.728` c2s CMD13 退队 | `22:08:44.988` s2c N2254（105 行 = `69 …7f`） |

官服还在别处推：走进待机区（`21:39:40`）、每次进图/清关（Normal
`21:42:03/21:43:02/21:44:14/21:45:25`、Extreme `22:05:02/22:05:38/22:06:06/22:06:44/22:07:23`）。
本仓此前**只在进频道时推过一次**（`ispins_wiring.go` 的 login 路径），所以第一局能开、
通关退队之后就点不动了。

### 处理（B 方案：最小改动 + 官服口径）

`cmd/wireprobe/forest_flow.go` 新增 `forestQuotaRestorePackets(note)`，在**场景已装载**的
待机区路径上重推**三帧成套**（与伊斯 `ispinsRepeatRestorePackets` 同口径）：

| 帧 | 内容 | 官服证据 |
| --- | --- | --- |
| N2254 | 军团入场账本（105 行 = `7f` 可用） | Normal `21:47:03.500`、Extreme `22:08:44.988`（都在 CMD13 退队之后 0.2~0.3s） |
| N781 | 周难度 USER 待机版体（272B） | Normal `21:50:15.999` |
| N782 | 周难度 CHARAC 待机版体（400B） | Normal `21:50:16.006` |

**为什么是三帧**：2026-10-09 第二轮实机只推 N2254 时，第一局开战恢复正常了，但
通关退队再建队后客户端**仍然不发 CMD2043**。官服「两局之间」那一段（Normal
`21:50:14`–`21:50:16`）是 `N1336 → N2254 → N781 → N782` 连着推的，伊斯流程也是
三帧成套（其注释写明：缺周难度帧时客户端周本计数缺省 0，待机面板会本地拦下）。

挂点：

- **CMD13 退队应答链**（官服原位置）；
- **CMD12 建队应答**（单机无限刷的安全网：无论上一局怎么结束，建队这一刻三帧都重推）。

⚠️ **不挂进任何进图批次**：仓库有实测记录（2026-10-03）在副本装载期推 N2254 会**硬崩客户端**。

`TestForestPartyQuotaRestore` 钉住：退队与建队的应答都以 **N2254 + N781(272B) + N782(400B)**
三帧收尾、N2254 内容 105 行首是 105 且「可入场」标记 = `0x7f`；退队仍然清 run 与 hard 标记。

> 若复测仍点不动：下一个嫌疑是官服同一段里也推了的 **N1336（周本进出信息）+ N706（周本信息）**。
