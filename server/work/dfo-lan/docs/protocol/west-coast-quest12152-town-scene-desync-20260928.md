## Code-level defect

`dungeonGate` in `cmd/wireprobe/dungeon_flow.go` treats every nonzero CMD15 except a training room as a tutorial starting route. It does not recognize this quest-connected scenario dungeon. The main dispatch in `cmd/wireprobe/main.go` refuses CMD15, but then independently accepts CMD16. `selectDungeon` calls `dungeonGate` with an all-zero body for a normal dungeon; West Coast's base area is a `[dungeon gate]`, so this synthetic zero request passes even though the client's actual nonzero gate was rejected. Main dispatch then sets `activeDungeon`, and its world request path ignores town CMD35/CMD36 while that field is set.

The server's world catalog currently resolves West Coast 40/0 base walkable/portal geometry and only exports phase-map NPC rows, not active phase state or phase geometry. Quest 12152's completion NPC is in a West Coast phase map and absent from the base map. This is a separate area-model gap. The capture proves the erroneous `activeDungeon` state is the immediate server-side cause of the broad interaction lock; it does not establish the precise client-side reason the NPC menu never opens or prove that phase geometry caused the logged refusals. The quest corpus contains 38 `[move to dungeon]` scripts, 34 triggered by `arrive in town`; the bug class extends beyond this one quest, but each client-facing transition still needs its own evidence.

The source tags `[move to dungeon]`, `[/move to dungeon]`, and `arrive in town` have one xref each at `0x14766C86F`, `0x14766CB30`, and `0x14766CC1B`, all in `sub_147668960`. The opcode table identifies CMD15 as `ENTER_SELECT_DUNGEON`, CMD16 as `SELECT_DUNGEON`, and NOTI27 as `ENTER_SELECT_DUNGEON`. The runtime call path from the parsed quest arrival condition to CMD15, and the ACK15/NOTI27/CMD16 reader branch for this town-triggered scene, remain open questions.

MCP decompilation of `sub_146CCE3D0` (the known tutorial CMD15 path, including instruction `0x146CCE64A`) shows it selects tutorial IDs in the `10000`–`10006` range and sends opcode 15. The captured town-triggered request names `100004404`, which is source-linked to quest 12152 and outside that tutorial route. The server's tutorial-only interpretation of all nonzero CMD15 requests is therefore inconsistent with both the source quest and this native request. This does not by itself establish the S2C response layout for the town-triggered route.

The client also logged some missing animation/AI resources while loading, but the live `Script.pvf` and `sk.dat` hashes exactly match the frozen project copies; the trace alone does not establish that those missing assets caused this stall.
