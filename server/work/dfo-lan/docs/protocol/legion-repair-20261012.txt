二、审查发现与已修复项
1. [P1] 伊斯结算画面与真实存档脱节。
   上游 internal/legion/ispins.go 的旧奖励构造使用固定编号/数量；ispins_flow.go还回放官方角色的N14背包台账。
   这些显示不能证明玩家实际获得物品，直接叠加事务发奖又会让显示与入库不一致。
   已迁移R7的PVF奖励规则、奖励冻结、事务领取与收据去重；N2252/N2253使用同一冻结结果，N13和角色信息从提交后的角色构建。
   旧固定奖励构造仅留在历史布局测试中；生产路径不再使用。辅助表中的历史N14条目统一过滤，不发给当前角色。
   发奖失败时不推进阶段；已冻结奖励保留，背包腾出空间后重登补领。相同RunID重复结算不会再次发奖。
   只绑定上游已有执行证据的type6限时作战；未移植R7全部作战效果，不扩大声称所有卡牌可用。

2. [P2] 维纳斯结算请求可跳过真实清怪条件。
   venusRewardEnd原先只检查请求阶段与run.stage，就可将cleared置true并推进。
   当前副本缺失、未完成或完成的是别的副本，也会被接受。
   已补当前副本存在、Completed、阶段副本身份三项校验；保留已完成阶段的幂等应答和既有终局链。
   使用旧函数覆盖运行新增回归测试，三个负例全部失败；修补后三个负例通过。
   这不等于实现CMD2293第四阶段中止/降档分支。

3. [集成回归防护] PVF磁盘投影恢复时丢失新奖励规则。
   DungeonCatalog.LegionContents属于不序列化的运行时源；只补冷导入会导致暖启动没有奖励定义。
   RestoreRuntimeDungeons现在在校验归档身份后，从同一归档重新连接军团内容及作战奖励规则。
   实际PVF验证了冷导入→JSON投影→暖恢复，内容定义和作战表一致。
   两次导入的LoadedAt自然不同，不将加载时间当成玩法差异。

三、内容规则与存档链
contents/system/legionsystem/legionsystem.cos：
  [legion data set] Ispins → [reward data] solo/basic/difficulty、[phase reward count]、[dungeon info data]。
contents/2022/stolenlandispins/etc/stolenlandispins.etc：
  [operation table]难度映射、[operation data set]/[reward data]模板/数量/权重。
ImportLegionContents / ParseIspinsOperations → IspinsPhaseRewards → LegionRewardService.Freeze → 原生礼包展开 → Claim。
奖励源、背包目录与角色ConfigVersion绑定同一PVF身份；未知或无法展开的奖励显式报错，不回退硬编码内容。
周次数采用PVF PhaseReward与已有DFO_ISPINS_MODE运维策略。没有新增玩法开关。
新增角色JSON字段legion_phase_rewards，旧字段保留；使用既有SQLite CharacterEvent事务表，不改数据库schema。
事件键legion-phase-freeze:<RunID> / legion-phase-grant:<RunID>，模型legion-phase-source-v1。
已冻结计划只补领一次，重试不重新随机。切换PVF身份不会静默跨源发奖。
旧程序不负责补领新计划；回退程序后待领记录仍应保留，之后恢复修补版再补领。回退代码不撤销已经合法发放的物品。
