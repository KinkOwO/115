## 42. 【定案】副本内的「秘密商店」（`etc/secretshop.etc`）

> 业主 2026-09-27：深渊特殊商店要真的能刷出来、并且真的能买到东西。
> 结论是：**表在客户端 PVF 里，但客户端不读它** —— 摆不摆摊、摆什么，全由服务端推。

### 42.1 关键事实：客户端不读这份表

`etc/secretshop.etc`（422,410 字节，`sha256 759ff09cad59…`）躺在内层 PVF 里，于是很容易
误判成"客户端自己会读"。反证：

- 把客户端 114,614 条 xorstr 解出来，商店类文件的字面量**在的都在**：
  `/etc/itemshop/itemshopCategory.etc`、`Etc/MileageShop.etc`、`EpicPieceShop.etc`、
  `Etc/Raid/RaidShopInventory.etc`、`Etc/SecretShopAdditionalInfo.cos`；
- **就是没有 `secretshop.etc`**（大小写、下划线各种写法都没有）。

⇒ 它是**服务端数据**。所以服务端必须自己掷、并把结果推给客户端，这也正好解释了下面
那两条通知的存在。

⚠️ 顺带排除一个误导项：`contents/2022/dungeonandlife/itemshop/secretshop_lv1..lv4/*.shp`
（各 10 个）**不是**这套东西 —— 那是 2022 年「地下城与生活」商店（客户端会读
`Contents/2022/DungeonAndLife/Ui/ItemShop.xui`），跟深渊无关。

### 42.2 表结构

脚本是平坦的 cell 流，没有行边界，行宽只能按固定宽度恢复。外层是若干个 `[npc]` 块，
一个块 = 一个商人：

```
[eplp wait time] 3 · [price random] 10 · [cash user stackable count] 100
[add slot cash user stackable count] 100
[dungeon npc]        <dungeonId> <npcId> <w1..w5>     × 619 行（全库）
[npc] <npcId>                                         × 18 个块
   [dungeon]          <dungeonId> <marker> [ <6 个数> ]*
      [difficulty]    <difficultyId> [ <6 个数> ]*
   [dungeon cash item]  同上形状，走点券
   [dungeon item difficulty]  <dungeonId> <marker> <difficulty> <flag> [ <6 个数> ]*
```

- **商品组 = 6 个数**：`模板 0 价格 0 数量 权重`（第 2、4 列在数据里恒为 0，保留原值）。
- **收尾标签有两套**：`[/dungeon]`（136 次）与 `[/dungeon item]`（45 次）混用，
  解析器必须**都认**，否则会把后半段的库存并到前一个副本名下。
- `[dungeon npc]` 行宽恒为 7（4333 = 619×7），`[level npc]` 也是 7（280 = 40×7）。

### 42.3 概率模型（两条不变量把它钉死）

1. **`[dungeon npc]` 每一列恰好合计 10000**（逐列、逐副本都成立，导入器硬校验）。
   五列 = 商店的 **1..5 格**；第 2..5 列「不出现」都降到 9726 ⇒ 格子越多越容易出现。
2. **每个 (商人, 副本, 难度) 的商品组是一份概率空间**，掷骰按**该清单自己的合计**归一。
   绝大多数清单合计恰好 1e6，但**不是全部**：`100002823` 只有一个 100000 的组。

第 2 条是被数据逼出来的，不是选的。若按"权重/1e6 的绝对概率、余数是空奖"读，
`100002823` 的那个物品每场只有 0.02%，而社区统计到 0.35%（见 42.4）；按归一读是 0.20%，
落在区间里。**导入器因此只校验"清单非空且合计非零"，不再要求合计等于 1e6**。

⇒ 单场出现概率 = 商人权重/10000（体验服无黑钻 ⇒ 1 格 ⇒ **2.06%**），
出现时必给 1 件（不是"有概率给"）。

### 42.5 协议（1.15 客户端静态逆向，非猜测）

包名取自 `analysis/dumps/opcodes.tsv`；**处理函数是从客户端的注册表里找出来的**，方法：
`.text` 里所有 `lea r8, <handler>` + `mov edx, <id>` + `call <注册器>` 的调用点（4,480 处 /
52 个注册器），按注册器的最大 id 判族 —— `cmd` 最大 2428，`noti` 最大 5073，
所以 max id > 2428 的注册器就是 noti 那一族。

| 包 | id | 处理函数 | 载荷 |
| --- | --- | --- | --- |
| noti `SECRET_SHOP_NPC` | 279 | `sub_1452B40A0` | **u32 = 商人模板 id**（客户端把 **1000 映射成 0** —— 正是表里那一行）|
| noti `SECRET_SHOP_ITEM_LIST` | 280 | `sub_1452B3CD0` | **u32 件数 + 每件 22 字节** |
| cmd `SECRET_SHOP_BUY_ITEM` | 296 | `sub_145246160` | 客户端**收**的回包布局已读到（下面）|
| cmd `SECRET_SHOP_OPEN_CLOSE` | 297 | — | 未定 |

NOTI 280 每件的读序（`sub_146EA0BA0` = 读 u32，`sub_146EA09F0` = 读 1 字节）：

```
u32 模板 · u8 · u32 价格 · u32 ? · u32 数量 · u32 ? · u8
```

**22 字节里那两个 `u32 ?` 是唯一没被证据钉住的字段**，实现里编 0（常量
`secretShopUnknownU32A/B`，见 `cmd/wireprobe/secretshop_flow.go`）。其余字段按 etc 里
6 个数的列序对上。实机截图一看就知道对不对。

⚠️ **还没抢到的一块**：cmd 296 / 297 的**请求**布局。我们只反编译到回包解析端
（`sub_145246160` 的 `a2 == 0` 是失败分支，错误码 4/10/17/19/60/95 各有文案）。
所以服务端现在**只把请求原样记进 `events.jsonl`**（`secret_shop_buy_item_request` /
`secret_shop_open_close_request` 带 `plain_hex`）—— 实机点一次就能读出格式，
比在这里猜一个结构然后赌它对要诚实。

## 43. 【实机修正】秘密商店的货架必须在「开窗之后」发（2026-09-27 18:5x）

> 上一节（§42）把协议形状逆出来了，但第一次实机是**半成功**：商店窗口出来了
> （标题「神秘商店」+ 商人头像都对），**货架是空的**。这一节记下根因与修正；
> 它订正 §42.5 的「下发时机」和 §42.7 的待办 1/2。

### 43.1 现象与现场数据

`events.jsonl` 里两条通知都发出去了，载荷也是完整的：

```
secret_shop_npc_sent   id=279  c5ebf505                            -> npc 100002757（benyboo 材料商）
secret_shop_item_list_sent id=280  01000000 6fc39e00 00 28880400 00000000 03000000 00
                                  count=1 · 模板 10404719 · 价格 297000（300000 ±10%）· 数量 3
secret_shop_open_close_request id=297  01000000 00000000 00000000 00000000   （开窗）
```

进本（10:50:41.894）与开窗（10:50:51.001）**相差 9 秒**，货架却是空的。

### 43.2 根因：列表挂在「本玩家的商店槽」上，而槽在开窗那一步才就位

`sub_1452B3CD0`（noti 280 的处理函数）干的是：

```c
v22 = 0; sub_146EA0BA0(&v22);                       // 读 u32 件数
v13 = sub_145F13700(qword_14E683C20,                // 按当前玩家/区域找到那个商店槽
                    sub_145F12D90(qword_14E683C20));
if (v0 != 0) {                                       // v0 = 由「当前商店 NPC id」建出来的对象
  *(u32*)(... + 4064) = v22;                         // 存件数
  *(... + 4048) = *(... + 4040);                     // ★ 先把槽里的列表清空
}
for (i = 0; i < v22; ++i) { 读 22 字节 -> sub_145EAD730 写 56 字节行结构
  if (v13 != 0) sub_145EFB1B0(v13, v29);             // 挂到槽上（v13 == 0 时这一行直接丢）
  ...
}
...
if (窗口存在) sub_146ABBC60(窗口, 1);                 // 刷新，才会重画格子
```

两个要害：

1. **`v13 == 0` 时整批行被静默丢掉**。`v13` 是按「当前玩家/区域」索引出来的槽，
   没开过窗的那一步之前它并不在。
2. 即使 `v13 != 0`，处理函数还会**先把列表清空**再填 —— 所以**进本时（窗口还没开）
   发的列表，等玩家真正开窗时已经被抹掉了**。

客户端开窗时会主动发 **CMD 297**（载荷第 1 个 u32：非 0 = 开、0 = 关；这一次开、离场前
关各发了一次）——它就是「我开窗了」的信号，也是服务端应该跟着补货架的时机。

### 43.3 修正

| 时机 | 之前 | 现在 |
| --- | --- | --- |
| 进本 | 279 + 280 一起发 | **只发 279**（让商店出现），并**掷一次库存**记在本场会话上 |
| 客户端开窗（CMD 297，flag≠0） | 只记原始包体 | **发 280**（把那一场的货挂到当时的槽上），窗口随后自行刷新 |
| 客户端关窗（flag=0） | 同上 | 什么都不发 |
| 同一场重复开窗 | —— | 发**同一份**货（`secretShopRolled` 保证一场只掷一次） |

`rollSecretShop` 里「掷不到商店也置 `secretShopRolled`」是刻意的：否则玩家开关一次窗口
就等于多掷一次骰子，出现率会被抬高到表值之上（有测试守这条）。

### 43.4 顺带订正行字段映射（§42.5）

早先 22 字节里那两个「未证实 u32」现在对上了：按 `etc` 那一行的六列顺序落位，
**第二个未证实字段其实就是该行的权重**（商店窗口用它显示每一格的出品率），
末尾多出来的那个 u8 在表里没有对应列，填 0：

| 载荷字段 | 类型 | 来源 |
| --- | --- | --- |
| 物品模板 | u32 | col1 |
| col2 | u8 | col2 |
| 价格 | u32 | col3 |
| col4 | u32 | col4 |
| 数量 | u32 | col5 |
| 权重 | u32 | col6 |
| 末尾标志 | u8 | 表里没有，填 0 |

`internal/loot` 侧的 `SecretShopOfferItem` 因此多了一个 `Weight`：权重不只用来掷骰，
还要**活着到达客户端**（早先它在抽货那一步被丢掉了，等于给客户端发了 0）。

### 43.7 第二次实机：**只发 279 商店根本不出现**（A/B，2026-09-27 19:1x）

§43.3 把「进本」改成了只发 279。结果两场深渊**都没出商店**，而且客户端**一次开窗请求
（CMD 297）都没有**——不是"窗口出来了但货架空"，是货架与窗口一起消失。

对照同一天的第一次实机（进本发 279+280）：商店出现（标题「神秘商店」+ 商人头像），
随后玩家开窗发出 cmd 297。⇒ **280 同时是「商店出现」的必要条件**：

| 进本发什么 | 商店是否出现 | 是否有 cmd 297 |
| --- | --- | --- |
| 279 + 280 | 出现 | 有（进场后约 9 秒）|
| 只发 279 | **不出现** | **没有** |

这与 §43.2 的读法一致：件数是存在「由当前商店 NPC id 建出来的那个对象」上的
（`if (v0 != 0) *(...+4064) = 件数;`），少了这一步商店没有被 arm 起来；而**行**挂在
「按玩家/区域索引的商店槽」上、且开窗会把槽清空，所以进本发的那一批留不住。

**最终规则（两个时机都发，用同一份缓存库存）**：

| 时机 | 动作 |
| --- | --- |
| 进本 | 掷一次（记在本场会话上）+ 发 **279 + 280**（280 让商店 arm 起来）|
| 客户端开窗（CMD 297，flag≠0）| **再发 280**（把被开窗清掉的槽重新填上）|
| 客户端关窗（flag=0）| 什么都不发 |
| 同一场重复开窗 | 发**同一份**货（`secretShopRolled` 保证一场只掷一次）|

代码见 `cmd/wireprobe/secretshop_flow.go` 的 `secretShopEntryPlan` / `secretShopShelfPackets`
/ `secretShopOpenPlan`；测试断言「进本那份货与开窗那份货**逐字节相同**」。

### 43.8 第三次实机仍空 ⇒ 转头读**窗口侧**，拿到两条硬事实（2026-09-27 19:4x）

这一场日志：279 一条 + **280 两条**（进本一条、开窗那一下一条），`cmd 297` 也准时来了
（11:24:08.291）——所以不只是"发早了"的问题。于是这次不猜，直接反编译**窗口**：

**① 开窗流程是「先发 297、再清自己的货架」（`sub_144F07860`）**

```c
sub_146D746E0(v97, 297);                 // 先告诉服务端「我开窗了」
...
do { (**v106)(v106, 0); } while (v106 != v105);   // 清空 a1+2432..2440（货架单元格）
窗口+2440 = 窗口+2432;
子144EE0A10(窗口+2456); 窗口+2464 = 窗口+2456;      // 再清空另一个列表
```

⇒ 服务端**收到 297 就立刻回**的那一份 280（本机 1~3 ms 就到）正好落在这一段清空**之前**，
于是被它自己抹掉。修法不是"晚点发一次"，而是**借客户端每帧心跳补发几次**
（`secretShopShelfResends = 3`，心跳约 0.4 秒一次，见 `secretShopPending`）。

**② 窗口填表读的列表，和 280 写的列表不是同一个（这是"货架空"的结构原因）**

- 窗口填表 `sub_144F210C0(a1, a2)` 上来就按 **56 字节步长**去量 `a2+4040..4048`，即它渲染的是
  **`+4040` 那个向量**；
- 而 noti 280 的处理函数对 `vtbl2416(v0)+4040` 只做**清空**（`*(+4048) = *(+4040)`），
  行被追加到**另一个**向量 `v13+2136`（`sub_145EFB1B0`）。

⇒ 就算时序对上了，**行也没进窗口读的那个列表**。为什么官方能显示仍未解：要么存在一步
「`+2136` → `+4040`」的拷贝（还没找到），要么 22 字节行的字段语义还有一处没对上。

**结论**：本轮先落 ①（补发），它能独立验证；若补发后仍空，就等于用实机把 ② 钉死，
下一仗只打这一个点（拷贝那一步 / 行字段）。
