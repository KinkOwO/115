## 2. 本轮改动

### 2.1 BOSS 死亡即通关

`tryComplete` 不再要求 `RoomCleared()`，仍要求 completionTarget 与房间内每个 rank3 源 BOSS 各自有死亡上报。被 BOSS 清场的普通小怪不再阻塞结算，也不会因此获得经验或掉落（不伪造击杀）。

### 2.2 通关按走过的所有房间结算

`Session.ClearedMaps()` 返回该 run 实际进入过的全部地图（房间切换要求前一间已清空，所以通关时它们都已清）。`MapClear` 改为对每张图结算，此前只认最后的 BOSS 房地图，设在中间房间的目标会被静默漏掉。无移动历史的单房间 run 仍按当前房间结算。

### 2.3 补齐主线缺的两种目标

- `[reach the range]`：六整数 `town area x y w h`，判定为矩形 `[x, x+w] × [y, y+h]`。**这个读法是从三条低等级源行推断的**（3156 `38 3 445 115 400 300`、3160 `40 3 1034 180 100 100`、21094 `40 3 132 160 900 200`）——中心加半径的读法会让 3156 的 Y 变负，故排除。未与原生处理器核对，其它形状一律仍算未实现，不猜。
- `[seek n meet npc]`：奇数个 cell，`(物品 数量)*` + 末尾 NPC。3173 的 `10164787 1 10164789 1 29` 正好是它自己前置 3169/3171 发的两件奖励，然后找 NPC 29。只检查持有，不消耗（消耗语义未取证）。

### 2.4 位置类目标的推进

新增 `quest.ProximityProgress`：移动（CMD35）与切区（CMD36）确认之后，结算由"人站在哪"决定的目标——走进源矩形，以及站到任务指定的 NPC 身旁。NPC 坐标取自源 `[NPC]` 行（`id, 朝向, x, y, flag`，对照 town38/area0 NPC1 `[left] 1227 164 0` 读出），接受距离 `ProximityRadius = 180` 是**本地策略，不是原生值**。接任务（CMD31）后也立即判定一次，因为任务通常就是站在该 NPC 面前接的。

CMD33 对话仍是 `[meet npc]` 的首选路径，这条只是兜底：不站到源坐标就不会推进，不存在凭空完成。

### 2.5 任务可结算性下沉到列表

新增 `quest.Index`（每次目录加载预计算一次）。`Available` 现在还会过滤掉本版无法结算的任务——目标类型未实现、reward type 不支持、grow 条件无法解析的，一律不再出现在可接列表。接到一个永远提交不掉的任务，比看不到它更糟。`[none]` 奖励类型现已支持。

同一份索引供 `MapClear`、`ProximityProgress` 复用，顺带把升级/结算/交任务那一帧的全目录扫描降为哈希查表。

### 2.6 装备掉落

装备类不再被丢弃。掉落池是 `configs/equipment.current35.json` 的可入包投影：1536 行里 1534 件通过 `EquipmentCatalog.Basic` 的同一套验收（`[free]` 挂接、rarity 0..1、可解析耐久），只有 2 件因缺耐久被拒。**池的成员资格与发放用的是同一个判定，所以掉得出来的一定放得进背包。**

类别概率、稀有度掷点、等级窗口全部沿用参考公式与当前源表，与堆叠物完全一致；窗口内的选择是均匀的，因为物品字典自身的 generation 权重仍未恢复——这一点不是原服掉落对等，已写进 `configs/drop.current36.json` 的 note。

装备落地时带源耐久（场景行与背包行同构），入包走装备槽位而非堆叠槽位。

回归测试 `internal/loot/equipment_drop36_test.go`：4000 个确定性种子下，5 级怪掉出 20 件装备、24 个堆叠物，且断言池中每件都能被 `Basic` 接受、装备类不再出现 `equipment_dictionary_pending`。

### 2.7 金币头顶数字

36 档启用 `-solo-party-bootstrap`，入场发 99 字节单人 PARTY_INFO（slot0 为本角色）。金币入账与 NOTI39 此前已在，缺的是浮字读取的队伍槽位。**这一项只有实机看到头顶数字才算修好**，开关打开不算。

### 2.8 新手开头

- `dungeon.SelectTutorial`：普通 `Select` 直接拒绝 `[tutorial dungeon]`，所以此前教程副本永远进不去。客户端自己的教程 CMD15 发送端（`146cce650`）发的是源副本 ID 而非城镇门的 0，之前每一个这样的请求都被拒。现在 CMD15/CMD16 认这条路。
- `character_birth` 表记录一次性出生路线，阶段单向推进（0 待走 / 1 已进本 / 2 已完成待回城 / 3 完成）。
- **既有角色一律回填为"已完成"**：迁移时 `ON CONFLICT DO NOTHING`，只有此后新建的角色才欠这条路线。老角色不会被拖回新手流程，重启也不会把进行中的新角色误标完成。`BIRTH_ROUTE_PASS` 覆盖回填、单向、归属、重启安全、重放拦截。
- 离开教程本（通关、放弃、结算退出任一路径）统一收尾，落到源路线指定的城镇坐标（普通职业均为 `town38 / area0 / (1677,222)`）。
- 15 条普通职业教程副本已用真实房间构建器逐条验证可开启（`audit36 -tutorial-routes`），活动专属路线不会被普通角色选中。

**这条路依赖客户端主动发教程 CMD15。** 客户端何时发由它自己的 SELECT 教程段决定（`146CC6FD0` 读 `tutorial_flag` 与 `tutorial_completed`），这个条件本轮没有取证。所以：客户端若发，现在能正确进本并回城；若不发，行为与现在完全一致（新角色直接进城），不会比现状更差。这是有意选的低风险接法。

## 6. 邮件 / 时装 / 道具使用 / 商城购买

用户追加要求这四块。**本轮没有实现任何一块的业务功能，实现了让它们可被实现的那一步。** 原因不是工作量，是证据。

### 6.1 为什么不能直接写

这四块在项目里完全空白，`dfo_probe_tools` 里也没有任何相关的原生分析。要实现它们，必须知道当前客户端用哪个命令 ID、包体怎么排布、服务端该回什么。项目的硬规矩是"优先读这个客户端的原生协议，90 级版本只能参考思路，不能直接套消息字节"——而 90 版的 opcode 与当前版本不同（35 版已多次踩到：NOTI173 与 2826、party 布局、item move 尾字节都不一样）。

更要紧的是，本轮查明观察器一直在丢弃这些证据：`observedGameRequest` 是个 43 项白名单，**只有已实现的命令才保留包体**。历史采集里客户端发过 50 多个未处理命令——`2127` 六千多次、`623` 358 次、`283` 276 次、`407` 82 次、`2377` 30 次——但其中只有 2 个留下了明文。也就是说，日志能证明"客户端发过命令 407 共 82 次"，却对它装了什么一无所知。

在这种情况下猜四个功能的包格式，错的代价不是"功能不好用"，而是客户端收到无法解析的应答后界面卡死——比不实现更糟。

### 6.2 本轮做的：把猜变成证

观察器改为**按命令采样**：已实现的命令照旧全量保留（回归需要），未实现的每个命令 ID 每连接保留前 8 个明文包体，超出只计数。上限是必须的——单次运行里那个 6331 次的遥测命令会把日志冲爆。

- `cmd/wireprobe/request_scope.go`：新增 `retainRequestBody` 与 `BodySampleLimit = 8`
- 回归测试 `request_scope_sample36_test.go`：已实现命令永不被丢且不消耗配额、未实现命令采到上限即停、配额按命令独立、遥测命令无法灌满日志
- `dfo_probe_tools/feature_capture36.py`：读采集日志，把未实现命令的明文按发送次数和时间列出，并给出与 UI 操作对应的读法
- `dfo_probe_tools/unhandled_commands36.py`：统计历史所有运行里客户端发过、服务端从未应答的命令

这两个脚本都是只读的。

6. 若手上有时装，再脱下来一次。

### 6.5 拿到证据后的实现顺序

1. **道具使用**——数据最全（恢复量、冷却、冷却组、职业限制都在源里），只缺一个请求格式；效果应用与冷却落库是纯服务端逻辑。
2. **时装**——大概率复用现有 C1/19 穿脱，补时装槽位映射与 NOTI13 的时装列表；32 万条定义需要按职业和槽位类型做一次导入（会比 1536 条基础装备重，要单独的导入器与索引）。
3. **邮件**——纯服务端：邮件表、附件、领取的事务与幂等（照 `character_quest_rewards` 的收据模式做），协议只有列表、读取、领取、删除几个动作。
4. **商城购买**——最后做，因为它要动货币与发货，必须事务化、幂等、可审计；cash 道具的价格字段还要先从源里确认（`potion_sharpeye.stk` 这类普通消耗品没有价格段，商城价格可能在单独的商品表里，取证时一并确认）。

四块都不要在协议未确认前写业务分支——这是 35 版在 party 布局和 item move 上已经付过学费的地方。
