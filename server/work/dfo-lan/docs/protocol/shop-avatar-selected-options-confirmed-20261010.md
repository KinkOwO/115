# 商城散件装扮属性购买确认基线

## 问题和来源

购买皮肤或装扮散件时，选择非默认属性会被 `Service.Quote` 拒绝为 `unsupported product option`，没有扣款。原生商品与 MOD 新增入口均可触发：普通装扮目录没有导入可选属性，`Product.Option` 为零；发货路径也未保存购物车中的属性编号。因此仅放宽拒绝检查会导致属性没有正确保存。

属性内容仍只有当前内层 PVF 一个来源：装备索引绑定的 `.equ` 中 `[avatar select ability]`，以及 `[ability case index]` 引用的 `skill/abilitydatas.dat` / `[ability case]`。复用现有装扮重铸的属性行解析器，识别四格普通属性与五格 `[SKILL_LEVEL]` 行。不把 `[avatar type select]` 第一格当作属性数量，也不按商品 ID 或连续编号范围构造可选项。

当前客户端 `14088DFF0` 发送购物车所选编号，`147184690` / `147189710` 保留 PVF 的显式属性键；`145AADC40` 将选中编号写入物品 field58。沿用该编号，不加一、不按行位置重排。字段复用既有 `BagEquipment.Durability` 的装扮语义。

## 修改范围

- `ImportPilot` 从同一只读 PVF 加载所需的属性 case 表，作为内部只读派生目录；不新增运行期 JSON 内容链。
- 仅已通过源分类的散件装扮获得属性允许集合。普通商品的固定选项、商品类型、价格、数量、销售时间和扣款事务沿用原校验。原有零选项购买兼容保留；其他编号必须在该物品的实际源定义中存在。
- `CashOrderLine.avatar_option` 保存经校验的选择，并参与原订单序列化摘要。同一商品在同一购物车选择不同属性分别发货，不修改共享商品缓存。
- 散件发货把属性保存到新装扮已有字段，同时保留原有期限和默认镶嵌孔。礼包及包内发奖继续使用原路径，不推断或附加属性选择。
- 没有客户端 DLL、MOD、PVF、数据库 schema 或历史物品迁移；零属性订单的新字段被省略，旧订单序列化保持原行为。

## 检查与已知失败

在最新主线 `d80919db` 基础上执行 `go build ./...`、`go vet ./...`、`go test ./... -count=1`，均通过。补充测试覆盖稀疏属性键、技能 case 引用、同 SKU 不同属性、错误类型、非法编号、混合购物车失败不改库存、默认选项以及默认镶嵌孔。实际 PVF 中此前失败的九个原生/MOD 商品通过选属性购买与保存回归；没有安装 MOD 的源跳过对应 MOD 捕获商品，不把它们当作原生必备商品。

实际 PVF 全量商城专项仍有 `TestCreatureCurrentSourceCatalog` 的源宠物定义断言和 `TestShopPilotOpenAll` 的固定商品数量断言失败；`charactercheck` 仍报 `quest source experience mismatch`。这些均在未修改的最新主线副本对照复现，不记为通过，不夹带无关修复。
