# 36 轮协议恢复：从参考源码到当前客户端的证据链

编写时间：2026-09-11。用途：记录邮件 / 时装 / 道具使用 / 商城这四块功能的协议是**怎么查出来的**，以及查到了什么。方法可复用于任何未实现的命令。

结论先行：**道具使用已按本客户端自己的格式实现完毕**；另外三块的命令编号与请求布局已恢复，但各自还缺一到两处确认，列在第 5 节。

## 1. 方法

四步，每一步都可复现：

1. **参考源码只用来学字段语义**，不取字节。`work/90us_reference/source/server_proto/opcodes/` 有按功能命名的 opcode 实现，从中知道"使用消耗品"这个动作需要哪些字段（槽位、容器、实例、模板），以及成功/失败应答各自带什么。
2. **从当前客户端恢复它自己的命令表**。客户端的发包序列是固定模式，已由已实现的 CMD1301 证实：

   ```
   call 146d74000      取包构造器
   mov  edx,<command>  命令编号
   call 146d746e0      开始命令
   ...字段写入...
   call/jmp 146d75af0  发送
   ```

   枚举 `146d746e0` 的全部调用点并回收 edx 立即数，得到本客户端的命令表：**3369 个调用点，2849 个解析出编号，1142 个不同命令**。工具 `dfo_probe_tools/command_senders36.py`，输出 `command_senders36.json`。

3. **标定字段写入函数，解析每个命令的请求布局**。用两个已实现命令标定：

   | 写入函数 | 类型 | 标定依据 |
   |---|---|---|
   | `146d746e0` | 开始命令 | CMD1301 空包 |
   | `146d75cc0` | u8 | CMD43 的 `p[4]==0` 位 |
   | `146d76180` | u16 | CMD34 的四个 u16 |
   | `146d75ce0` | u32 | CMD43 的 u32 object |
   | `146d75af0` | 发送 | 三者共有 |

   工具 `command_layout36.py`，`--scan` 导出全部 1142 个命令的布局指纹到 `command_layouts36.json`，可按字段形状反查功能。

4. **用已知答案做对照实验**，再用于未知命令。

## 2. 对照实验结果（方法可信性）

三个独立已知命令，全部逐字段对上：

| 命令 | 恢复出的发送端 | 恢复出的布局 | 与既有实现对比 |
|---|---|---|---|
| CMD34 任务提交 | `14519ff60` | `u16=0x22, u16, u16, u16` = 8B | `DecodeQuestSubmit` 要求 8 字节、首个 u16 等于 34 ✓ |
| CMD43 拾取 | `145af4a70` | `u32, u8=0, u8, u16 …` 共 25B | `DecodePickup` 的 `p[4]==0`、`ActorX` 在 +6、`p[20]` 检查位 ✓ |
| CMD19 装备移动 | `145af6990` | `u8,u16,u32,u32,u8,u16,u32,u32,u32,u8,u8,u8` = 29B | 35 版实测记录的字段序与"正文 29 字节"逐项吻合 ✓ |

`14519ff60`（CMD34）与 `14519fe80`（CMD31）也正是 35 版文档早先独立记下的两个发送端地址。

另一个有力的交叉验证：参考源码的 `opcode0013-move_itemspace` 是 0x13 = 19，当前装备移动**也是 CMD19**——说明相当一部分命令编号在两版之间稳定。但这只提高命中率，**不能省掉逐个验证**：35 版已在队伍布局和装备移动 ACK 尾字节上踩过版本差异。

## 3. 道具使用：已实现

**命令 44。** 三重证据一致：

1. 布局扫描里 CMD44 是 `u16,u8,u32,u32,u32` = **15 字节**。
2. 参考源码的 `use_stackable` 是 `i16 槽位 | u8 容器 | i32 实例 | i32 模板 | u32 保留`，同样 15 字节，**且其 opcode 正是 0x2C = 44**。
3. 客户端注册的 class1 处理器 `14529fd70`：开头 `test dl, dl` 说明成功标志是框架传入的参数而非包体字段；成功分支读 `u16, u8, u32, u32`（11 字节），失败分支读 `u8, u32, u32`（9 字节）。与参考记录的"成功 1+11 / 失败 1+9"一致。

据此实现：

| 方向 | 格式 |
|---|---|
| 请求 C1/44 | `u16 槽位 \| u8 容器 \| u32 实例 \| u32 模板 \| u32 保留`，15B 填充至 16 |
| 成功 S1/44 | `u8 1 \| u16 槽位 \| u8 容器 \| u32 实例 \| u32 模板`，共 12B |
| 失败 S1/44 | `u8 0 \| u8 容器 \| u32 模板 \| u32 实例`，共 10B |

**恢复效果由客户端自己应用**：原生成功应答里没有任何"恢复了多少"的字段，所以服务端只负责持久扣减、回执和权威背包刷新，不发明治疗量。这一点与参考源码的说明一致（普通消耗品客户端本地扣 1）。

代码：

- `internal/game/protocol/use_stackable.go` — 编解码，注释记录每个字段的证据来源
- `internal/inventory/consume.go` — `Bag.Consume`：校验槽位归属、物品一致、非空栈；清空的槽位被移除而不是留 0；装备槽不可走此路径
- `internal/loot/consume.go` — `Service.Consume`：与拾取同一套事务与幂等收据。**热键会连发，重放必须只扣一次**
- `cmd/wireprobe/consume_flow.go` + `main.go` CMD44 分支 — ACK 后补发权威背包（NOTI14），避免客户端本地计数漂移

测试：`use_stackable36_test.go`（布局锁定到参考实测包 `03000007090000590400000000000000`、应答宽度 12/10、零模板与脏填充拒绝）、`consume36_test.go`（归属、栈耗尽、空槽再用、错物品、装备槽拒绝）。

**唯一待现场确认的一处**：失败应答里两个 u32 的先后。客户端只读 `u8,u32,u32`，读取顺序本身区分不出哪个是模板哪个是实例；当前按参考记录的"模板在前"实现，已在代码注释里标明。影响仅限失败提示。

## 4. 容器编号

`Consume` 只接受 `list == 0`（普通背包）。参考源码提到共享临时库存用另一个容器编号，其语义未取证，所以其它容器一律拒绝而不是猜着处理。

## 5. 另外三块：已恢复的编号与仍缺的确认

| 功能 | 参考 opcode | 当前命令 | 恢复出的请求布局 | 还缺什么 |
|---|---|---|---|---|
| NPC 商店买入 | `buy_item` 0x15 | **21** | `u32,u32,u32,u32,u8,u32` = 21B | 字段含义分配；商品价格来源 |
| NPC 商店卖出 | `sell_item` 0x16 | **22** | `u32,u32,u8,u8,u16,u32,u32` = 20B | 同上 |
| 商城购买 | `buy_cerashop_item` 0x40 | **64** | `u8,u8,u8` = 3B | 3 字节太短，**大概率不是购买本体**，需重找（商城可能走单独的列表+购买对） |
| 时装合成 | `compound_avatar` 0x63 | **99** | `u16,u16,u32,u16,u32,u8` = 15B | 是合成而非穿戴 |
| 时装徽章 | `use_avatar_emblem` 0xC9 | **201** | `u8,u16,u32,u8,u16,u32,u8` = 15B | — |
| 时装分解 | `disjoint_avatar` 0xCA | **202** | `u16,u32` = 6B | — |
| 时装选项 | `avatar_option_change` 0x1CC | **460** | `u16` = 2B | — |
| 邮件 | 参考源码未实现 | 未知 | — | 需从客户端字符串/UI 反查 |

**时装穿戴的重要判断**：时装是 `equipment/character/<职业>/at_avatar/` 下的装备（32 万条），所以穿脱很可能**直接走已实现的 CMD19**，缺的只是两样东西——时装槽位编号，以及把时装纳入装备目录（当前 `equipment.current35.json` 只有 1536 件基础装备，不含时装）。这条路比新写一套协议短得多，应优先验证。

商城和邮件仍需一次实机取证：商城开界面并买一件、打开邮件界面并领一件附件。观察器已改为按命令采样（每命令前 8 个包体），所以这些动作现在会自动留下明文。用 `dfo_probe_tools/feature_capture36.py` 读出。
