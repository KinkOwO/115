## 1. 已修并已实机验证

### 1.1 ESC 菜单整体失效（回城/换角色/退出）

回城发的是 **CMD42，整帧只有 13 字节**：无参命令没有密文体，而包体会补齐到 16 的
倍数，所以有参数的命令最短 29 字节。旧代码要求 `len(frame.Raw) >= 14` 才解密验签，
无参命令永远过不了这道门，直接记 `checksum failed`。

`command_layouts36.json` 里 body 为 0 的命令：**7（退出游戏）、42、69（副本内）、
63、67、120、1301（城镇回城）**——整条 ESC 菜单都在里面。

改为 `len(frame.Raw) >= wire.ClientHeaderSize`，空包体按长度 0 验签（校验和只覆盖
两个头字节）。旁证：`leaveDungeon` 的分支本来就写着"包体必须为空"，它只是从来没被
执行到。

实机结果：回城正常、换角色不再黑屏。

### 1.2 BOSS 清场后卡在房间

抓包 `20260912T001341`：BOSS 死亡那 3 毫秒内客户端一次上报 6 只怪的死亡，其中
`0x1015 / 0x1019 / 0x101a` 的 killer 是本角色，`0x1018 / 0x101b / 0x101c` 的 killer
是 **0xFFFF**——BOSS 死亡连带清场的那几只。旧规则只允许标了 `NonCombat` 的怪用这个
哨兵值，其余一律 `foreign combat killer` 拒绝，于是服务端不回死亡确认包，客户端一直
留着那几只怪，门不开，只能手动回城。

改为：**killer 0xFFFF 的死亡照常确认并清场，但标记为无主——不给经验、不给掉落**
（掉落连 roll 都不 roll，不占用本次 run 的掉落额度）。指名其他 actor 的外来击杀仍然
拒绝。旧测试里写反的断言一并改掉，并补了"自己打死的不会被标成无主"的反向断言。

### 2.1 部分任务无法提交（难度字段）

全库 2844 个任务：**347 个没有 `[difficulty]` 段**，另有 **81 个把键写成小写**
（`g` 55、`f` 25、`i` 1），而 `n_quest/questparameter.etc` 的键全是大写。两种写法
以前都直接报错，任务永远交不掉——实机日志里任务 2109 连续三次被拒就是这条。

- 没有难度段 → **不给任务经验但正常结算**（不编权重）
- 小写键 → 大小写不敏感匹配；表里每个小写键只对应唯一一个大写键，并加了"若表中
  出现只差大小写的两个键则报错"的歧义保护

回归测试结果：309 个无难度任务 + 81 个小写键任务全部可结算，0 个再因难度被拒。

### 2.3 快捷栏放不进道具

抓包 `20260912T004320`：CMD19 `列表0 槽位65 → 列表0 槽位3`。对照背包策略，

当成纯装备背包，槽位 3 在装备范围外直接拒，而且对堆叠物是显式报错的。客户端收不到
成功就弹通用的"目标背包已满"，跟真实原因无关。

新增 `quick_slots: [0, 8]`（`configs/inventory.current37.json`，与其他段不重叠并有
校验）与堆叠物移动路径：空位移动、占位交换、落到装备上拒绝、跨类型范围拒绝，
可上可下。写库走幂等的角色事件日志，拖拽重发只生效一次。

## 4. 未解决

### 4.1 怪物血量

**公式已完整恢复**。`145c199c0` → `147220e40(描述块, flag)`：

```
基础值 = 解码(描述块+0x00, qword)
xmm6   = 速率(描述块+0x10 的第 4 项) × 基础值
若 flag==0: xmm6 += 解码(描述块+0x48); xmm6 *= (解码(描述块+0x60) + 常量)
若 xmm6 > 常量 且 解码(描述块+0x30) > 0:
    结果 = 解码(描述块+0x30) × xmm6      ← 就是这一步把血打没了
否则 结果 = xmm6
```

实机解码（观察器 `watch_monster_stats36.py`，描述块位于 `actor+0x4810`；每个字段是
"值 + 守卫"对，守卫 == 解码值 + 0xC4 + 存储值，所以抓到一对就能反解出明文）：

| 偏移 | 值 |
|---|---|
| +0x10 / +0x18 / +0x20 / +0x28 | **1.0** |
| **+0x30** | **0.0143018** ← 倍率 |
| +0x38 | 3 |
| +0x40 | 115 / 288（按怪不同，像是血量本身） |

四个相邻速率字段全是 1.0，只有 +0x30 是 0.0143，`115 × 0.0143 = 1.6`，一下就死。

**三条硬事实**（都与之前的假设相反）：

1. 我们发的怪物包里**根本没有血量字段**（只有 entity/level/template/rank/team），
   血量是客户端按模板和等级自己算的，115 / 288 数值本身合理
2. `0x3C6A4A8D`（即 0.0143018）**在整个客户端镜像里搜不到**，不是写死的常量
3. **全镜像没有任何一处代码写 `actor+0x6808`**（`145c08420` 只读它并抄进 +0x30），
   而实测它解码出来是 **0**——也就是说 `145c08420` 这条路径要么没跑，要么跑了会把
   +0x30 置 0（那样 `>0` 判断失败，反而不做乘法，是正确行为）

另外核对过：我们发的怪物记录尾部 `Level, Rank, 0, 0, 255` 与客户端的读取顺序和默认值
（`[rsp+0x7e]` 预置 0xFF 后 `movsx` 取符号）一致，这一段不是问题。

**下一步（最省事的一次取证）**：把观察器扩展到同时 dump **本角色 actor** 的同一描述块。
如果玩家的 +0x30 也是 0.0143，说明它是全局值；如果玩家是 1.0，说明是怪物专属，再去
查 118 个写 +0x30 的函数里与该模块相邻的那几个（`145c0ad80`、`145c42da0`、`145c64370`、
`145d2e3f0`、`147216a30`、`14721d120`）。在根因定死之前不改这个数——项目硬规矩是不许
随意放大 HP。

### 4.2 弓箭手技能面板

拿**鬼剑士的原始布局**做了对照（`runtime/skill-layout35/01-swordman_sp.co.tokens.json`）：

- 鬼剑士未转职页 **27 格**（y=0~6），弓箭手 **7 格**（全在 y=0）
- 但这 7 格两边完全相同：174/190/169/170/186/175/452，连 x 坐标都一样——这是所有职业
  共用的通用行
- 鬼剑士未转职页有 **511**（`armormasteryetc`）在 `x=0,y=1`；弓箭手原始文件没有。
  35 版补的 511 也放在 `0,1`，**与所有段落一致，这一格是对的**
- 35 版补的 **3（CrackArrow）和 7（RisingMoon）坐标抄自 muse 转职段**，而这两个技能
  在鬼剑士那边是明确"未放置"的。（当时据此判断"这两格该撤掉"——**结论是错的**，
  见下一段）
- 179 是 `disjointitem`（分解道具），172 是轻甲精通、181 是合成——这类生活/通用被动
  **在任何职业的任何段落里都没有格子**，本来就不画在技能树上，走面板右侧的 S/C 区域。
  它的入口是 CMD26

**第一次重做用错了判据，已纠正。** 记录下来免得重犯：

我最初的规则是"每个转职段都把该技能放在同一个格子才补进未转职页"。这条测的是
**"是不是五条转职路线共用"**，而不是**"未转职能不能学"**——两者不是一回事。按它生成的
版本把 3 和 7 撤掉了，实机结果是技能页更空、SP 花不出去，比改之前更糟。

正确判据在技能定义里：`[skill fitness growtype]` 对这个职业是 **6 项**（1 个未转职 +
5 个转职），**0 就是未转职**。3（CrackArrow）和 7（RisingMoon）都是 `0 1 2 3 4 5`，
**未转职合法可学**，只是原始布局文件没给它们格子。35 版补进去是对的。

改用该判据重新生成后，产出条目的 SHA-256 是 `62bc01461e1e0e06…`，**与 35 版逐字节
相同**——这就证明 35 版的 `Script.pvf` 就是正确文件，直接复制回客户端即可，不必重新
打包。客户端当前 `Script.pvf` 哈希 `ba2c94feaafdb2d2…`（= 35 版产物）。

这个客户端的数据支持的上限就是 **10 个格子**：7 个通用行 + 3 + 7 + 511。另外 16 个
未转职可学的技能（179 分解道具、172 轻甲精通、181 合成…）**在任何职业的任何布局段里
都没有格子**——它们本来就不画在技能树上。要让未转职页像鬼剑士那样有 27 格，就必须
加原始数据里不存在的格子，那属于改内容而非修复，需要单独决定。

回退：关闭客户端，把 `runtime/client-pvf-backups/Script.before35.pvf` 复制回
`work/dfo_probe_client/Script.pvf` 即回到未打补丁的原始技能页。

### 4.2b 任务奖励的第二道门（已修）

目录补齐后，21650 的报错变成 `special equipment reward requires additional source
state`。原因是 `Basic()` 同时承担两件事：结构校验，以及"怪物能掉什么"的两条规则
（必须 `[free]` 未绑定、稀有度不高于 1）。任务奖励绑定、高稀有度都很正常。

拆成两条：`Reward()` 保留全部结构校验但不管绑定和稀有度，`Basic()` = `Reward()` 加
那两条掉落规则。发放走 `Reward()`，掉落池仍由 `Basic()` 构建。

结果：**可发放 1534 → 2849 条（共 3174 行），掉落池 1534 不变**。任务完成框"确定点不动"
也是同一个根因——客户端等不到完成回包。

### 4.3 结算界面的翻牌奖励

用户报告"任务结算会把正常的翻牌奖励挤掉"。日志里的时序（run `..._201846_next37`）：

```
01:25:26.064  CMD69 → card_scroll_ack
01:25:26.074  CMD70 → card_layout_ack   01 01 00 ff×14
01:25:27.256  CMD34 → 任务 3146 完成（带物品奖励，走 id 13 整包背包快照）
01:25:41.404  CMD72 → card_inventory_committed(13) + card_selection_ack(71)
```

两点可疑：`card_layout_ack` 只给了**一张**牌、其余槽位全 `ff`；任务奖励与翻牌**共用
id 13** 这个整包背包快照包号，而任务结算恰好插在发牌与翻牌之间。需要一张结算界面的
截图才能定性是"牌被换掉"还是"位置被占"。

### 4.4 "关闭游戏"按钮无反应

点击期间**客户端一个包都没发**（最后一条是位置保存，之后到强制关窗为止只有心跳）。
服务端没有收到请求，因此不是应答缺失。最可能的解释是这个隔离客户端由 `probe.exe`
直接拉起，不经过原版启动器，而"退出游戏"是把控制权交回启动器。直接关窗口即可，
不影响数据。要确认需静态分析该按钮的处理函数，优先级低。
