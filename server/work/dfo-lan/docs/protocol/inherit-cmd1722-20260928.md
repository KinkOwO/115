# 装备继承 CMD 1722 —— 协议取证与服务端落地

- 日期：2026-09-28
- 涉及命令：`CMD 1722`（继承确认）、`CMD 1690`（打开继承窗口）、`CMD 1720` / `CMD 1721`（窗口内选装备）
- 范围：**纯服务端**。未改客户端、DLL、协议版本号或数据库结构。
- 状态：**待实机验收**。分派、落库、刷新已落地并过单测（21 个用例）。
- ★ 结论：**1722 在客户端双向都没有继承结果通道，任何方向的 1722 出站包都禁止**（详见 §4）。
  成功只发 `kind=0` 的 `NOTI14` 槽位行刷新，拒绝只记日志。

---

## 1. 症状与根因

玩家在继承窗口里放好「有增幅数据的源装备」与「无增幅数据的目标装备」，按下确认后**毫无效果**：
窗口不关、装备数值不变、服务端不报错。

根因只有一条，且与 CHANGELOG 里 CMD205（增幅书）那次完全同构：

```
$ grep -rn 1722 cmd/ internal/ --include=*.go   →  0 hits
```

**CMD 1722 在服务端从来没有分派。** 它既不在 `dungeonRequest()` 白名单里，也不在
`observedGameRequest()` 里，主循环里更没有 `frame.ID == 1722` 分支 ⇒ 请求落到
`unimplemented_sample` 采样门，服务端**既不改状态也不回包**，客户端一直停在等待态。

因此修复不是「改协议」，而是**把这条命令接起来**：解码 → 落库 → 发 `NOTI14` 槽位行刷新（不回结果包，见 §4）。

## 2. 请求包布局（466 字节）

### 2.1 发包点

| IDA 地址 | 作用 |
| --- | --- |
| `sub_14138D120` | 继承窗口确认处理。`case 2` 先过 `sub_14138A210` 校验，再 `sub_146D746E0(w, 1722)` + `sub_146D75B10(w, a1+1512, 466)` + `sub_146D75AF0()` 发送 |
| `sub_146D746E0` | 写 opcode |
| `sub_146D75B10` | 写 body |
| `sub_146D75AF0` | flush |

⇒ 请求体是窗口对象 `+1512` 处的一块 **466 字节**结构体。实机帧长 **480** = 466 + 14 字节分组补位（补到 16 的倍数）。

### 2.2 整体切分

```
14 字节前缀  +  14 × 32 字节记录  +  尾部 u32  =  466
```

依据（`sub_14138A210`）：

```c
*(_BYTE *)(a1 + 1525) = 4;   // 体偏移 13 = 状态字节
v4 = a1 + 1526;              // 体偏移 14 = 记录区起点
do { sub_1471B45D0(v4); v4 += 32; --n14; } while (n14);   // 14 条、步长 32
...
*(_DWORD *)(a1 + 1974) = 0;  // 体偏移 462 = 尾部 u32，只清零、从不写条数
```

⚠️ **尾部 u32 不能当记录数用**：`sub_14138A210` 只把它清 0，实机 7 个样本恒为 0。

### 2.3 单条记录（32 字节）

字段偏移全部来自 `sub_14138A210` 的写字段（`v18` = 记录起点）：

| 记录内偏移 | 体偏移 | 类型 | 含义 | IDA 依据 |
| --- | --- | --- | --- | --- |
| +0 | 14 | u16 | 源装备槽位 | `*(_WORD *)v18 = v24` |
| +2 | 16 | u32 | 源装备模板 | `*(_DWORD *)(v18+2) = *(vtable[152](v21)+24)` |
| +18 | 32 | u16 | 目标装备槽位 | `*(_WORD *)(v18+18) = v26` |
| +20 | 34 | u32 | 目标装备模板 | `*(_DWORD *)(v18+20) = *(vtable[152](v22)+24)` |
| +24 | 38 | u16 | 常量 **257** | `*(_WORD *)(v18+24) = 257`（硬编码） |
| +26 | 40 | u32 | 材料模板 | `*(_DWORD *)(v18+26) = v38`（实机恒 0） |
| +30 | 44 | u8 | 源装备容器 | `*(_BYTE *)(v18+30) = v43` |
| +31 | 45 | u8 | 目标装备容器 | `*(_BYTE *)(v18+31) = n3` |

容器取值与项目既有约定一致：**0 = 背包，3 = 已穿戴**（另见 `internal/game/protocol/inventory.go` 的容器表）。

> 客户端查槽位失败时会把容器改写成 3 再查一次（`sub_145AD5C20` < 0 → `sub_145AD5F80`），
> 所以请求里报的容器**不一定准**。服务端按「先请求容器、再另一个」回退查找，
> 并额外用**模板号**对账（槽位可能被玩家挪过，模板号才是可靠身份）。

### 2.4 未使用记录的残留

未使用的 13 条记录除 `+30` / `+31` 残留 `0x2E`（46）外全 0 —— `sub_1471B45D0` 只做了部分清零。

⇒ **只能按「模板号 == 0 即未使用」过滤**。用容器字段或尾部 u32 判条数都会误判。

## 3. 实机取证（B 阶段：2×2 交叉设计）

2026-09-28 20:38:24 会话是一次完整的 2×2 全交叉：两件有增幅的装备分别继承给两件没有增幅的装备。

| 源槽 | 源模板 | 目标槽 | 目标模板 | 源容器 | 目标容器 |
| --- | --- | --- | --- | --- | --- |
| 9 | 101040829 | 11 | 101040833 | 0 | 0 |
| 10 | 101040830 | 12 | 101021079 | 0 | 0 |
| 9 | 101040829 | 12 | 101021079 | 0 | 0 |
| 10 | 101040830 | 11 | 101040833 | 0 | 0 |

同会话的 `NOTI13` 背包快照（26 行）逐行对账：

- 槽 9 = 101040829，`offset 10 & 0x1f = 20`，`offset 19 = 3` ⇒ **源 A（增幅 +20）**
- 槽 10 = 101040830，`offset 10 & 0x1f = 15`，`offset 19 = 3` ⇒ **源 B（增幅 +15）**
- 槽 11 = 101040833、槽 12 = 101021079，`offset 10 = 0` ⇒ **两个目标**

四个槽位与四个模板号**全部吻合**，u16 = 槽位、u32 = 模板号这条猜想由此坐实。

跨会话复核：旧会话（15:18:51）里 `[32..33] = 57`，而该会话背包快照的槽 57 = 101021079 ✓。
旧会话的 `[44..47] = 3` 表示**源装备正穿在身上**（源容器 3、目标容器 0）。

## 4. ★★ 1722 双向都没有继承结果的接收通道：任何出站包都禁止

### 4.1 根因：客户端的 opcode 表是两套独立命名空间

收包分派器按 `kind` 选表，`1722` 这个编号在两个方向上的含义都与「继承结果」无关：

| kind | 表基址 | 1722 在这一侧是什么 |
| --- | --- | --- |
| `0` | `qword_14E683700`（NOTI 表） | `sub_143348A90`：读 8 字节（i32 v1 + u32 v2）→ **小游戏道具使用计数通知**，会弹「道具使用次数已增加」提示窗（与继承无关） |
| `1` | `qword_14E6836F8`（CMD 表） | **客户端自己发出去的那条命令**（继承确认），**没有接收 handler** |

因此服务端不能回包：

- 回 `kind=1 + id=1722`：客户端会把它当成「自己刚发的继承命令」解析，但命令体 466 字节、负载却只有几字节，格式不符、无对应消费路径。
- 回 `kind=0 + id=1722`：命中 NOTI 表的**小游戏道具计数通知**，会弹出「小游戏道具使用次数已增加」的提示窗（`0xA88` 参数就是小游戏弹窗、`v2` 是弹窗计数），与继承结果毫无关系。

### 4.2 最终结论

**CMD 1722 在客户端双向都没有继承结果的接收通道。成功、失败、拒绝都只落库 + 发
`NOTI14` 行刷新，不回任何 1722 包（任何 kind、任何形态都禁止）。**

- 窗口内装备数值的更新由 `id14` 槽位行驱动（与第三方已验证实现一致，见 §5）。
- 「继承确认后窗口如何就地收尾 / 继续下一轮」在所有已验证版本里都未观察到就地解锁，
  玩家目前以重开窗口的方式继续。若未来要钉死收尾通道，必须先拿到新的 IDA / 抓包证据，
  **禁止再拿 1722 的任何一个方向当回包通道**。
- 测试防线：`TestNoInheritReplyBuilderExists`（协议包禁出现任何回包构造函数）与
  `TestInheritNeverSendsAnyOutbound1722`（流程层禁出现任何 1722 出站包）。

## 5. 刷新通道：只有 `NOTI14` 增量行

继承成功后**只发一类包**：

- **`NOTI14` 槽位行**：每条记录的 base + material 各一行：
  - 基础件（接收等级的那一件）—— 带新等级 / 新红字 / 新附魔；
  - 材料件（被清零的那一件）—— 带归零后的数值。

⚠️ **不能退回 `id13` 全量重建**：继承窗口确认后仍持有两件装备的对象引用，
整包重建会打断这些引用，表现是窗口里的数字乱跳或窗口直接失效。
强化 / 增幅路径（`reinforcement_flow.go`、`amplify_flow.go`）早有同一条结论。

此外还会补一次 `WornSpaceUpdate`（穿戴窗口整窗刷新），让角色面板同步。
若所有记录都在背包，这一步产出为空、自动跳过。

## 6. 落库规则

### 6.1 方向：按等级定，不按 UI 槽定

请求体里的 A / B 只是窗口的两个槽，**玩家两件装备怎么拖都行**，没有「源 / 目标」语义。
方向按游戏设计铁律定：

> **高等级件 = 材料件（material，被消耗）→ 低等级件 = 基础件（base，保留并接收等级）**
>
> 两件等级相同 ⇒ 无法判定方向、且继承无意义 ⇒ **拒绝**。

### 6.2 材料件的归宿：清零保留（官方文案取证）

客户端 PVF 字符串表 **dstr 69059**（继承确认弹窗，紧邻 69060「This item can't Inherit.」）：

```
Do you really want to transfer?
The target item can't be Transcended once the transfer is completed.
The material equipment will lose all its Enchantment/Reinforcement/Amplification/Refining levels.
```

⇒ 材料件**失去所有强化 / 增幅 / 精炼等级**，但**不是消失**。

反证：dstr **101033204**（自定义选项提取）明写 *"The material equipment will disappear"*
—— 官方要表达「消失」时会明写「消失」。69059 没写，所以是清零保留。

> 实现上**只清零、不删除** —— 删错不可逆，且 dstr 原文只承诺「失去等级」、未承诺「消失」。

### 6.3 搬运的字段

全部落在 181 字节装备行里，且**服务端本来就有权威定义**（与增幅系统共用同一套常量，
见 `internal/inventory/amplify.go`）：

| 位置 | 含义 | 处理 |
| --- | --- | --- |
| `offset 10` 低五位 | 强化 / 增幅等级 | `baseRow[10] = baseRow[10] &^ 0x1f \| matLevel` —— **保留基础件自己的高三位（再封装次数）** |
| `offset 19` | 次元属性类型（0 = 无红字） | **仅当材料件 ≠ 0 时**覆盖（否则会把基础件原有的红字清掉） |
| `offset 20` | 次元属性数值 | 同上 |
| `offset 14` | 附魔卡（u32，`enchantCardOffset`） | **仅当材料件 ≠ 0 时**覆盖（`enchant.go` 的 `enchantCard` / `setEnchantCard`） |
| `BagEquipment.Refine` | 锻造（精炼）等级 | **仅当材料件 > 0 时**覆盖（用 `refineLevel` 读权威值、`setRefineLevel` 写回） |

材料件侧：`offset 10` 低五位、`offset 19` / `20`、`offset 14` 附魔卡、`Refine` 全部归零，
装备本体留原格。

`offset 19` 必须与等级一起搬：客户端就是靠它是否为 0 来决定把 `offset 10` 渲染成
「增幅 +N」还是「强化 +N」，只搬等级会显示成强化。

### 6.4 多记录与拒绝条件

**一次 1722 请求可以带多条继承记录**（客户端 `sub_14138A210` 遍历窗口里所有
`*(entry+244) == 2` 的条目）。玩家做「多个装备同时轮换继承」时一次会发多条 ——
服务端**逐条独立处理**（后面的记录能看到前面的改动），全部成功才落库。
早期实现要求恰好 2 件，遇到「多个装备同时轮换继承」会因解出超过 2 件而误拒，现已改为按实际记录数处理。

拒绝条件（任意一条记录命中即整单拒绝）：

- 请求被过滤后**没有任何有效记录**
- 某条记录的两件装备等级相同 ⇒ 无法判定方向
- 某条记录的两件解析到同一格（同容器同槽位）
- 模板号对不上（玩家换过装备）
- 任一件不是装备（目录里没有 `[equipment type]`）
- 存档/目录版本不匹配

拒绝时：记 `inherit_refused` 日志，**不发任何包**（存档没变，无需刷新）。

## 9. 实机验收清单

1. 启动服务端（已重建 `bin/wireprobe-handoff-source.exe`）。
2. 进城 → 打开继承窗口 → 源放**有增幅 / 附魔 / 锻造**的装备、目标放**无**这些的装备 → 确认。
3. 预期：
   - 目标装备的 `+N`、红字类型/数值、**附魔、锻造**一起变成源的；
   - 源（材料）装备**仍在**，但等级 / 红字 / 附魔 / 锻造全部归零；
   - **不弹任何小游戏道具计数弹窗**（1722 双向都不回包，见 §4）；
   - 窗口里两件装备的数值立即刷新（目标件带上新数值、材料件归零）。
4. **多装备轮换继承**：一次放多对装备同时继承 → 应全部生效（不再「解出 4 件」拒绝）。
5. 服务端日志里应有 `inherit_committed`（含 `refine` / `enchant_card`）或 `inherit_refused`（含 `reason`）。

## 10. 未决与后续

- ~~`v1` / `v2` 的结果码语义~~ **已关闭**：NOTI 表 1722 是小游戏道具计数通知，
  不是继承结果通道；1722 双向都禁止出站包（§4）。
- **继承窗口的就地收尾 / 下一轮解锁**：所有已验证版本里窗口确认后都需要重开才能
  继续下一轮（装备取下也受影响）。下一个待验证假设：官方服务端会**删除**材料件
  （dstr 101033204 明写 "will disappear"），客户端窗口可能在收到「材料件消失」的
  容器通知后才解锁 —— 若要走这条路，需先取证删除材料件时的官方通知包，再做
  存档兼容评估，**不要在没证据时删装备**。
